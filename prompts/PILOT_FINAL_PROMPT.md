# Задача: финальная доводка пилота HR Manager для одного реального пользователя

Репозиторий: https://github.com/sledovatel61/HR-Manager
База: `main` @ `f3430a9f8afb0e35be45260df19f34559568223e` (CI зелёный, 7/7 jobs).
Работай в своей ветке `arena/<id>-pilot-final`, один PR в `main`.

## Контекст

Пилот делается для ОДНОГО человека: HR-менеджера Марии (она не программист).
Её Windows-ПК — это и сервер, и администратор. Функционально приложение готово
(Phase 0–16). Функции НЕ расширяем: нужно, чтобы Мария ставила программу в
пару кликов, пользовалась ею, присылала владельцу диагностику и ставила
обновления без потери данных.

Решения владельца (обязательны):

1. **Для пилота никаких покупных сертификатов (Authenticode/TSA).** Неподписанный
   или test-подписанный Setup.exe допустим. Предупреждение SmartScreen
   обходится инструкцией «Подробнее → Выполнить в любом случае». Отсутствие
   production-сертификата НЕ блокирует пилот. Существующий fail-closed
   production-пайплайн не ломать и не удалять — в пилоте он просто не используется.
2. **Лицензия** — существующий офлайн-механизм Phase 15 (Ed25519, файл
   `*.hrmlicense`, срок + лимит активных пользователей). Новый механизм не делать.
3. **Второй HR-менеджер** работает с ПК Марии по локальной сети через браузер
   и ничего не устанавливает на свой ПК. Доступ ограничен лимитом лицензии.
4. **Обновление**: владелец присылает новый `HR-Manager-Setup-<версия>.exe`,
   Мария запускает его поверх старого. Данные, пароли и лицензия сохраняются.

## Что нашла ревизия (надо исправить)

- **B1. В сборке нет открытого ключа лицензии.** Файла `infra/license/public_key.b64`
  нет, а `infra/compose.pilot.yml` требует `HRM_LICENSE_PUBLIC_KEY`
  (fail-closed). Значит, Setup.exe из CI у Марии не запустится.
- **B2. Генератор лицензий не выдаётся владельцу.** `tools/license-issuer`
  есть и проверяется в CI (`license-issuer-windows`), но готовый
  `license-issuer-dist.zip` не публикуется как artifact.
- **B3. Нет ярлыков.** В `installer/installer.iss` нет секции `[Icons]`: Мария
  не поймёт, как открыть программу после перезагрузки.
- **B4. Диагностика доступна только через PowerShell.** Мария не сможет
  запустить `hr-manager.ps1 -Action diagnostics`.
- **B5. Доступ только с 127.0.0.1** (`compose.pilot.yml`: порт
  `127.0.0.1:8080`) — второй HR не подключится.
- **B6. Не доказано, что повторный запуск нового Setup.exe делает бэкап перед
  обновлением и откатывается при ошибке.** У `Update-HrmApp` backup gate есть,
  а путь `Install-HrmApp` для существующей установки нужно проверить.

## Что сделать

### 1. Ключ лицензии владельца (B1, B2)
- Научить `installer/build.ps1` брать открытый ключ либо из
  `infra/license/public_key.b64` (его можно коммитить — открытый ключ не секрет),
  либо из GitHub variable/secret `HRM_LICENSE_PUBLIC_KEY` при сборке в CI.
  Если ключа нет, сборка пилотного установщика падает с понятной ошибкой,
  а не собирает нерабочий exe.
- Приватный ключ никогда не попадает в репозиторий и артефакты. Текущие
  гарантии и sweep-проверки сохранить.
- В CI job `license-issuer-windows` загрузить `license-issuer-dist.zip`
  как artifact `license-issuer-owner` (без ключей внутри).
- `docs/OWNER_QUICKSTART.md` простыми словами: скачать artifact → распаковать →
  `run-gui.bat` → «Создать ключи» (один раз) → куда положить открытый ключ
  (или какую GitHub variable заполнить) → «Выпустить лицензию» (имя, срок,
  лимит) → отправить файл Марии. Отдельно: продление срока и увеличение лимита
  для второго HR.

### 2. Ярлыки (B3)
- `[Icons]` в `installer.iss`, на рабочем столе и в меню «Пуск»: «HR Manager»
  (`-Action open`, окно скрыто). Только в меню «Пуск»: «HR Manager — отчёт для
  разработчика» (п.3), «HR Manager — перезапуск», «HR Manager — доступ по сети» (п.4).
- После перезагрузки ПК приложение поднимается само (если запущен Docker Desktop)
  или по ярлыку «HR Manager». Проверить и описать.

### 3. Отчёт для разработчика одним кликом (B4)
- Новое действие движка `-Action support-bundle`: создаёт на рабочем столе
  `HR-Manager-report-<дата-время>.zip`. Внутри: diagnostics (`-Json`), логи
  движка и установщика, последние N строк логов контейнеров backend/worker/
  frontend/backup, версия и `release.json`, состояние лицензии (срок, лимит,
  статус — без подписи), результат health/readiness.
- **Без персональных данных и секретов**: всё пропускать через существующий
  redaction (`Redact-HrmText`). Не включать дамп БД, `pilot.env`, пароли,
  токены, ключи, ФИО/телефоны/e-mail кандидатов. Добавить тест: в логи
  подкладываются фиктивные секреты и PII, в архиве их быть не должно.
- Backend: необработанные ошибки пишутся в лог с trace-id, без тел запросов и
  PII. Если это уже так — достаточно теста.
- В админском разделе диагностики/готовности — подсказка: «Чтобы отправить
  отчёт разработчику, используйте ярлык "HR Manager — отчёт для разработчика"».

### 4. Доступ по локальной сети (B5)
- Действие `-Action lan-access -Enable|-Disable` (по умолчанию выключено):
  публикует порт на LAN, добавляет правило Windows Firewall только для профилей
  Private/Domain (один UAC-запрос при необходимости). Выключение убирает
  правило и возвращает 127.0.0.1. Настройка переживает обновление.
- Ярлык выводит адрес вида `http://<имя-ПК>:8080` и IP для коллеги.
- Безопасность: loopback-only эндпоинты (`/api/setup/*`, owner claim, всё, что
  доверяет `X-Real-IP: 127.0.0.1`) по сети должны оставаться недоступными.
  Проверить тестами, что клиент из сети не может подделать `X-Real-IP`.
  Отсутствие HTTPS в офисной сети задокументировать как принятый риск пилота.
- Тест лимита: при лимите 1 второго активного пользователя создать нельзя,
  при лимите 2 — можно.

### 5. Обновление поверх (B6)
- Setup.exe новой версии поверх старой: автоматический шифрованный бэкап →
  замена файлов → миграции → health-check → при ошибке откат к прежним образам
  и данным. Если `Install-HrmApp` этого не делает, вести его через `Update-HrmApp`.
- Windows CI: поставить сборку N, создать данные (кандидат + лицензия),
  поставить N+1 поверх → данные и лицензия на месте; сломанная N+1 (падающая
  миграция) → автоматический откат, данные на месте.

### 6. Сборка пилотного релиза
- Workflow `pilot-release` (`workflow_dispatch`): собирает
  `HR-Manager-Setup-<version>.exe` с открытым ключом владельца, `SHA256SUMS.txt`
  и `license-issuer-dist.zip`, выкладывает их как artifacts. Без
  production-сертификатов, tag и GitHub Release.

### 7. Документы
- `docs/MARIA_GUIDE.md` (1–2 страницы, очень простой язык): что поставить заранее
  (Docker Desktop — по шагам, с перезагрузкой и включением виртуализации),
  SmartScreen, установка, первый вход, загрузка лицензии, доступ коллеге,
  отправка отчёта, установка обновления, «что делать, если не открывается».
- В `docs/CURRENT_STATUS.md`, `docs/handoff-release-0.14.0.md` и
  `docs/runbook-pilot-release.md` перенести Authenticode/TSA из блокеров в
  раздел «отложено до коммерческого релиза». Пилотный Go/No-Go — по пунктам
  этой задачи. Не затирать остальное содержимое этих файлов.

## Ограничения

- Функциональность продукта (кандидаты, правила, шаблоны и т.п.) не расширять.
- Не запускать production signing, не создавать tag и Release.
- Не коммитить приватные ключи, `*.hrmlicense`, пароли, `pilot.env`.
- Существующие тесты не ослаблять. Весь CI (7 jobs + новые) должен быть зелёным
  на финальном SHA PR.
