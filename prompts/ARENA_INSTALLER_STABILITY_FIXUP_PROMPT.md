## P2. Счётчик подряд идущих отказов обнуляется НАЧАЛОМ каждой попытки — «остановка повторов» недостижима

Факт (по коду):
- `Supervisor.psm1:73-80` (`Set-HrmSupervisorState`): если `-FailureCount` не передан явно, состояние
  «error» увеличивает счётчик, а ЛЮБОЕ другое состояние обнуляет его (`:79`).
- Каждая попытка движка начинается с записи `-State "starting"` БЕЗ `-FailureCount`, то есть обнуляет
  счётчик: `hr-manager.ps1:163` (install), `Supervisor.psm1:536` (`Start-HrmSupervisor`),
  `Supervisor.psm1:662` и `:674` (`Invoke-HrmSupervisorCycleLocked`), `Install.psm1:695` и `:725`
  (`Resume-HrmOperation`), `Tray.psm1:691` (`Invoke-HrmTrayMenuAction`), `Docker.psm1:1419`
  (`Invoke-HrmDockerPrepare`).
- Порог остановки повторов — `Tray.psm1:115` (`$FailureCount -ge $MaxConsecutiveFailures`, порог 3).

Воспроизведение (реальный сценарий пилота, не синтетика): приложение установлено, плагина compose нет.
1. Setup.exe падает на предполётной проверке: `starting` (счётчик 0) → `error` (счётчик 1).
2. Вход в Windows: значок читает счётчик 1 (< 3) → план `normal` → порождает движок → движок пишет
   `starting` (счётчик 0) → падает → `error` (счётчик 1).
3. Повторять пункт 2 сколько угодно: счётчик ходит 0/1 и никогда не достигает 3.

Ожидается: после трёх ПОДРЯД идущих неудачных попыток план значка `retry_exhausted`
(`Tray.psm1:115-121`), `start_engine = $false`, сообщение с причиной и действием; счётчик сбрасывается
только успехом (`ready`) и явным действием человека (`Reset-HrmSupervisorFailureCount`).
Фактически: новая попытка движка на КАЖДОМ входе в Windows — ветка `retry_exhausted` недостижима.
Существующий кейс «D4/D7: значок останавливает бесконечные повторные запуски…»
(`supervisor.tests.ps1`) проверяет только синтетику «три error подряд без единого starting» — он
проходит и при этой регрессии, поэтому регрессию не видно.

Требование:
- Попытка НЕ обнуляет историю: в перечисленных записях `starting`, которые начинают попытку,
  передавать `-FailureCount (Get-HrmSupervisorFailureCount -StateDir $StateDir)`. Обнуление — только
  успех (`ready`) и явный сброс. Порог 3, тексты сообщений и `Get-HrmTrayStartupPlan` не меняй.
- Новый регрессионный тест обязан воспроизводить РЕАЛЬНУЮ последовательность: три полных прохода
  «план значка → запуск цикла/установки → отказ» (например `Invoke-HrmSupervisorCycle` на мок-мире с
  отсутствующим плагином compose, либо `Install-HrmApp`), и только затем assert
  `(Get-HrmTrayCurrentPlan …).mode -eq "retry_exhausted"` и `start_engine -eq $false`. Тест ОБЯЗАН
  падать на `e298202` — докажи это в отчёте (чем именно падал).
- `infra/windows/README.md` (раздел «Поведение значка в трее») и
  `docs/windows-installer-stability-2026-10-12.md` привести в соответствие с фактическим поведением.

## P3. Таймаут установщика Docker Desktop рапортуется как «код -1» и удваивает молчание

Факт: `Start-HrmElevatedAndWait` (`Common.psm1:769-774`) по таймауту (3600 с) возвращает
`ExitCode = -1`, `TimedOut = $true` и процесс НЕ убивает (осознанно). Но `Install-HrmDockerDesktop`
смотрит только на `ExitCode` и `CanceledByUser`: `Docker.psm1:1152` (тихий путь) и `Docker.psm1:1181`
(мастер).
Воспроизведение: повесить тихой установщик Docker Desktop → через 3600 с в журнале «Тихая установка
Docker Desktop не удалась (код -1) — открываем обычный мастер установки» (`Docker.psm1:1160`), после
чего движок ждёт ещё до 3600 с.
Ожидается: отдельный статус (например `installer_timeout`) и сообщение, которое называет ожидание
(«установщик не завершился за 3600 с, процесс не завершён принудительно»), путь к файлу установщика и
следующее действие (дождаться / завершить вручную / повторить), БЕЗ автоматического перехода к мастеру
и без «код -1», выглядящего как ошибка установщика.
Фактически: до ~2 ч молчания и вводящее в заблуждение сообщение (установщик ещё жив).
Требование: различать `TimedOut` в обоих путях (и в `uac_declined`/`manual_required` не сломать
существующее поведение) и покрыть тестом на моке `Set-HrmProcessLaunchMock` с `TimedOut`, который
падает на текущем head.

## P4. Комментарий `hr-manager.ps1:75-77` обещает параметры, которых нет

Комментарий утверждает, что `-Action channel -Watch` ограничен «числом циклов/минут
(-MaxCycles/-MaxMinutes, переменные HRM_CHANNEL_WATCH_MAX_CYCLES/_MAX_MINUTES)». Параметров
`-MaxCycles`/`-MaxMinutes` в блоке param нет — работают только переменные окружения (их принимает
`Start-HrmChannelWatch`, `Channel.psm1:346-353`).
Исправь одно из двух: (а) добавь параметры в param и пробрось их в вызов наблюдателя, либо
(б) перепиши комментарий так, чтобы он называл только переменные окружения. Ложная документация хуже
отсутствующей.

## P5 (хвосты — дешево, сделай если не раздувает дифф)
1. `hrm-tray.ps1:88-99`: проверка идущей операции и порождение движка не атомарны. В окне между
   `Test-HrmEngineOperationInFlight` и `Start-HrmEngineProcess` движок, запущенный Setup.exe, ещё не
   виден → два движка на первые секунды. Сделай как в `Start-HrmTrayAction`: возьми блокировку действия
   в самом значке (`action = "engine"`, pid значка) ДО порождения и передай её ребёнку
   (`Update-HrmActionLockProcess`) — тогда посторонний процесс увидит занятую блокировку.
2. `Supervisor.psm1:277` (reentrant по `action = "engine"`): при рецикле pid блокировку с живым
   «своим» pid и действием `engine` можно принять за свою. Плюс `Invoke-HrmSupervisorCycle`
   (`finally { Exit-HrmActionLock }`) удаляет файл блокировки, принадлежащий значку: повторный вход не
   перезаписывает lock своим pid. Достаточно проверять в `Exit-HrmActionLock`, что запись ещё наша
   (pid/action), и/или перезаписывать lock при повторном входе.
3. `Preflight.psm1:62-71` и `:73-82`: код 124 (таймаут) рапортуется как «Docker CLI не найден» /
   «Демон Docker не запущен». Различай `TimedOut` и говори «не ответил за N с» — иначе причина отказа
   снова становится неправильной.
