# Follow-up prompt #2: герметичный тест D5 (красный обязательный набор на машине с Docker Desktop)

Готовый промпт для того же агента-исполнителя. База — **та же ветка и тот же PR #56**

Контекст: ревьюер прогнал полный Windows runner на машине, **где Docker Desktop реально

ЕСТЬ ПРОВАЛЫ: 1

infra/windows/tests/docker.tests.ps1:571

## Диагностика (проверена чтением кода — использовать как есть, не передиагностировать)

1. Падающий ассерт — `infra/windows/tests/docker.tests.ps1:571`:
   `Assert-HrmFalse ([bool]$result.PluginFound) "флаг найденного плагина недостоверен"`.
2. **Свойство `PluginFound` в production есть и всегда возвращается**:
   `infra/windows/engine/Preflight.psm1:257-260` (вычисление из фактов плагинов) и
   `:312` (`PluginFound = $pluginFound` в возвращаемом объекте). Его потребляет
   диагностика: `infra/windows/engine/Diagnostics.psm1:172-174`
   (`compose_plugin_found` в отчёте/ support bundle).
   → Предложенное ревьюером «добавить явное свойство в production» **не требуется и
   сделало бы тест тавтологичным**: свойство уже часть контракта. Не добавлять
   дубль, не переименовывать, не удалять потребителя.
3. **Настоящая причина — негерметичность теста.** Харнесс мокает только пробу CLI:
   `$world.ComposePluginMissing` (`infra/windows/tests/test-harness.ps1:313`, мок
   `:398-402`) подменяет ответ `docker compose version`. А `PluginFound` считается по
   **реальному скану файловой системы**: `Get-HrmComposePluginFacts`
   (`Preflight.psm1:138`) обходит `Get-HrmComposePluginDirs` (`Preflight.psm1:105`),
   то есть `%USERPROFILE%\.docker\cli-plugins` и `%ProgramData%\Docker\cli-plugins`, и
   `Get-ChildItem -Filter "docker-compose*"`.
   На машине с установленным Docker Desktop там лежит `docker-compose.exe` →
   `$pluginFound = $true` → ассерт падает. На GitHub `windows-latest` этих файлов нет,
   поэтому CI зелёный и дефект не виден.
4. **Это не регрессия PR #56:** идентичный ассерт есть в `origin/main`
   (`infra/windows/tests/docker.tests.ps1:689`). Латентный дефект всплыл на машине,
   где Docker реально есть; чинить нужно, а не откладывать.

## Задача 1. Сделать кейс D5 герметичным (предпочтительно — шов переопределения)

1. Ввести детерминированный шов для фактов плагинов в стиле существующих
   переопределений (`Set-HrmDockerOverride` / `Get-HrmDockerOverrideValue`,
   `infra/windows/engine/Docker.psm1:44-70`):
   - новый ключ `compose_plugin_files` (список имён файлов плагина, по умолчанию —
     ключа нет, поведение unchanged: реальный скан);
   - `Get-HrmComposePluginFacts` (или точка сбора фактов в `Test-HrmComposeVersion`)
     при наличии ключа строит факты из него: пользовательский каталог
     (`searched_by_cli = $true`) содержит перечисленные файлы, машинный — пуст;
   - в тестовых сценариях харнесс/тест обязан задавать ключ явно
     (`compose_plugin_files = @()` или `@("docker-compose.exe")`), иначе тест снова
     станет зависящим от машины. Проверить, что `Set-HrmDockerOverrideDefaults` не
     подставляет ключ неявно.
2. Покрыть **оба** ветвления контракта в `docker.tests.ps1` (кейс D5 или отдельный):
   - `compose_plugin_files = @()` → `PluginFound -eq $false`, вердикт `plugin_missing`,
     отказ по-прежнему называет причину и каталоги (все существующие ассерты кейса
     сохранить, не ослаблять);
   - `compose_plugin_files = @("docker-compose.exe")` при том же
     `ComposePluginMissing = $true` → `PluginFound -eq $true`, проверка **всё равно
     не проходит** (`Passed -eq $false`, `Reason = "plugin_missing"`). Это и есть
     контракт: флаг означает «файлы плагина найдены в каталогах», а не «compose
     работает»; отсутствие ответа плагина — отказ.
3. Сохранить/усилить ассерты сообщения («Плагин Docker Compose», `cli-plugins`,
   `.docker`, `29.2.0`, код возврата, `PluginDirs`) — они должны проходить при
   синтетических фактах так же, как при реальных.
4. В комментарии к шву и к тесту объяснить, зачем он нужен: без него набор зелёный
   только на машинах без Docker Desktop (CI), а на машине пилота — красный.
5. Допустимая альтернатива, если шов переопределения признан неудобным: в тесте
   временно подменить `$env:USERPROFILE` и `$env:ProgramData` на пустые временные
   каталоги с восстановлением в `finally` — но тогда надо доказать, что это не ломает
   другие чтения этих переменных в том же вызове (резолвер CLI, факты CLI).
