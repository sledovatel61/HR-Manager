# Починка штатного recovery установщика: отказ snapshot-guard `files_replaced` (exit 7)

Задача: добиться, чтобы стандартный `Setup.exe` мог доставить исправление существующей
установке (порт 8081, `pilot_created=false`) через **штатный** путь — снимок прежней версии,
секреты и тома Docker сохраняются. Только пользовательский сценарий установщика. Без GitHub,
ротации паролей, подписей релиза и публикации артефактов.

Репозиторий: `C:\Users\User\Documents\HR\pr57-purge-private\repo`

## Что установлено разбором (проверено по коду, не по догадке)

### Д1. Отказ по конструкции не несёт диагностики — это первичный дефект

`Write-HrmSnapshotResultFile` (`infra/windows/engine/Snapshot.psm1`) пишет в
`setup-snapshot.json` только `status`, `reason`, `release_sha` (= `$identity`, идентификатор
**установленной** версии), `files`, `digest`, `written_at`. В файл **не попадают**:

- `$fileSha` — `release_sha`, фактически лежащий в `{app}\release.json`;
- `$NewReleaseSha` — `release_sha` пакета;
- текстовое сообщение, в котором названо расхождение.

`Invoke-HrmSnapshotCli` печатает `Format-HrmSnapshotReason` — **обобщённый** текст — и
отбрасывает `$result.message`, единственное место, где живёт строка вида
«…уже не совпадают с установленной версией ({fileSha} вместо {identity})». Inno в журнал
пишет только `status=`/`reason=` из файла результата.

Итог: две ветки `files_replaced` (`$fileSha -eq $NewReleaseSha` — файлы уже нового релиза;
`$fileSha -ne $identity` — файлы не совпадают с записью установки) неразличимы ни в
`setup-snapshot.json`, ни в журнале мастера, ни в сообщении пользователю. Поэтому отчёт
приёмки и остановился на «Reason: files_replaced» без причины.

### Д2. Совет пользователю зациклен

`russian.SnapshotFilesReplaced` в `installer/installer.iss`: «…Запустите установку заново: при
повторном запуске копия прежней версии будет создана ДО замены файлов». Повторный запуск не
может изменить состояние, вызвавшее отказ, — второй прогон откажет идентично. Сообщение обязано
называть фактическое состояние и фактический следующий шаг.

### Д3. Главная гипотеза причины: `release_sha` = `git rev-parse HEAD` не различает две сборки одного коммита

`installer/build.ps1` (строка ~169) берёт `release_sha` из `git rev-parse HEAD` (либо
`HRM_RELEASE_SHA`). Сам отчёт приёмки фиксирует: «Build includes uncommitted changes to
Bootstrap.psm1, Secrets.psm1… **HEAD alone does NOT identify these patched bytes**».

Если существующая установка 0.15.0 была получена из `Setup.exe`, собранного на том же коммите
`97df390` (чистое дерево), то `{app}\release.json`.release_sha и `release_sha` нового пакета
**равны** — и срабатывает первая ветка guard-а: «В {app} уже лежат файлы НОВОГО релиза, а
валидного снимка прежней версии нет» → helper exit 3 → Setup exit 7 ещё до замены файлов. Это
согласуется со всеми наблюдениями: та же версия 0.15.0, предыдущий запуск не завершил первый
запуск (`pilot_created=false`), отказ до перезаписи, данные и тома целы.

### Д4. Вторичная гипотеза: guard не сверяет запись установки с целевым `{app}`

`Save-HrmVerifiedPreviousSnapshot` сравнивает `$fileSha` (из `{app}\release.json`) с `$identity`
(из записи установки в StateDir), но **никогда не читает `record.install_dir`**, который
`Install-HrmApp` пишет. Если каталог в записи отличается от `{app}` мастера (в приёмках
использовались нестандартные InstallDir), сравнение смешивает две разные установки и даёт
ложный `files_replaced`.

### Д5. Повтор установки той же версии после неудачного первого запуска не имеет пути

Guard может продолжать только при: нет записи, нет файлов прежней версии, либо есть пригодный
проверенный снимок той же версии. Установка, чей первый запуск не удался (снимка никогда не
было, `pilot_created=false`), при повторном Setup с пропатченной сборкой той же версии не имеет
никакого пути вперёд — только отказ.

## Шаг 1. Немедленная диагностика на существующей машине (без изменения кода)

Прочитать и зафиксировать в отчёте (значения SHA пушить в git и в prompts/ **нельзя**):

1. `%LOCALAPPDATA%\Programs\HRManager\release.json` → `release_sha` (**A**), `version`;
2. `release.json` из staging нового пакета → `release_sha` (**B**);
3. `%LOCALAPPDATA%\HRManager\installed.json` → `release_sha` (**C**), `install_dir` (**D**),
   `port`, `pilot_created`;
4. журнал мастера `%TEMP%\hrm-exchange-recovery-setup.log` — строки `HRM: snapshot decision` /
   `HRM: снимок предыдущей версии`.

Определить ветку: `A == B` → Д3 (первая ветка). `A != C` → вторая ветка; и если `D` не равен
`{app}` мастера → Д4. Зафиксировать, какая из них сработала, и приложить сравнение.

## Шаг 2. Инструментирование guard-а (обязательно, независимо от исхода шага 1)

Расширить `Write-HrmSnapshotResultFile` полями (это git-SHA и пути — не секреты):
`file_sha`, `new_release_sha`, `record_sha`, `record_install_dir`, `target_install_dir`,
`record_pilot_created`, `message`. Печатать из `Invoke-HrmSnapshotCli` **конкретное**
сообщение (`$result.message`), а не обобщённое. Добавить тест: при отказе в файле результата
присутствуют все различающие поля и они непустые для соответствующей ветки.

Без этого шага любое следующее проявление будет так же неразличимо.

## Шаг 3. Исправление причины (выбрать и обосновать; guard не ослаблять)

**Вариант А (предпочтительный) — идентичность по содержимому.** Добавить в `release.json`
(`build.ps1`) построчный `build_digest` — хеш по составу и содержимому staged-дерева
приложения — и использовать его в guard-е вместе с `release_sha`. Тогда «тот же коммит, другие
байты» = разная идентичность (guard продолжает, снимок создаётся), а «ровно те же байты уже
разложены» по-прежнему отказывает — защита сохраняется.

**Вариант Б — признание легитимного повтора.** Если идентичность пакета совпадает с `{app}` и
прежняя установка не завершена (`pilot_created=false` или висящий `setup-run.json`), сделать
проверенный снимок того, что лежит в `{app}`, как снимок прежней версии, и продолжить. Цель
отката сохраняется в любом случае.

**Вариант А и Б сочетаются.** Нельзя: удалять guard, подделывать `installed.json`/метаданные
снимка, объявлять `verified` без проверки, удалять тома или сбрасывать БД.

**Д4 (обязательно при подтверждении):** сравнивать `record.install_dir` с целевым `{app}`; при
расхождении — отдельная причина (например `install_dir_mismatch`) с обоими путями и внятным
следующим шагом, а не обобщённый `files_replaced`. Источником прежней версии считать каталог из
записи.

**Д2 (обязательно):** текст `SnapshotFilesReplaced` должен называть фактическое состояние и
реальный следующий шаг; совет «запустите заново» допустим только когда повтор реально меняет
ситуацию.

## Шаг 4. Тесты (регрессия на каждый пункт)

- тот же коммит, другие байты (или разный `build_digest`) → guard продолжает, снимок `verified`;
- `{app}` побайтово равен пакету → по-прежнему `files_replaced`;
- `record.install_dir` ≠ целевой `{app}` → отдельная причина, оба пути в диагностике;
- повтор после неудачного первого запуска → продолжает с проверенным снимком;
- файл результата при отказе содержит все различающие поля;
- существующие `iteration14.tests.ps1:192` и `iteration15.tests.ps1:213`, утверждающие
  `files_replaced`, обязаны продолжать проходить;
- Windows PowerShell 5.1 **и** pwsh.
