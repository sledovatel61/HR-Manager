## P1 (обязательно): пилот наследует жёсткую публикацию `127.0.0.1:8080` из dev-базы

**Где.** `infra/docker-compose.yml` (dev-база), сервис `frontend`, строки ~78–80:

```yaml
    ports:
      # nginx-unprivileged listens on 8080 inside the container.
      - "127.0.0.1:8080:8080"
```

`infra/compose.pilot.yml` (пилотный оверлей), сервис `frontend`, строки 139–140:

```yaml
    ports:
      - "${HRM_PILOT_BIND:-127.0.0.1}:${HRM_PILOT_PORT:-8080}:8080"
```

**Дефект.** Docker Compose сливает последовательности **добавлением**, а не заменой
(<https://docs.docker.com/reference/compose-file/merge/>: «A YAML sequence is merged by appending
values from the overriding Compose file to the previous one»). Сброс унаследованного значения —
только `!reset` (при нём переданное значение **игнорируется**, атрибут обнуляется), полная замена —
только `!override` (требует Compose **2.24.4+**).

В оверлее сброс сделан у всех сервисов, кроме фронтенда: `ports: !reset []` — `db` (стр. 54),
`backend` (117), `worker` (166), `backup` (196). У `frontend` сброса нет, поэтому эффективная
конфигурация пилота всегда содержит **две** публикации: dev-порт базы `127.0.0.1:8080` и выбранный
порт `${HRM_PILOT_PORT}`. Когда 8080 занят чем угодно ещё, контейнер фронтенда **не стартует вообще**
(`Bind for 127.0.0.1:8080 failed: port is already allocated`), на выбранном порту никто не слушает —
отсюда «приложение не стало готовым». Выбранный порт при этом свободен, и префлайт этого не замечает.

Это ровно сценарий чек-листа `docs/WINDOWS_ACCEPTANCE_CHECKLIST.md` I1 («запустить старый dev-стек HR
Manager на 8080… приложение публикуется на свободном порту… чужой dev-стек не тронут») — он заведомо
непроходим с таким оверлеем. Конфликт с dev-стеком на 8080 уже описан в самом движке:
`infra/windows/engine/Docker.psm1`, `Test-HrmPortServedByPilot`, комментарий про диагностику
12.10.2026 («на 8080 отвечал старый development-стек»). Дефект существует с появления оверлея
(`4d7dca1`) — его просто не задевали, пока 8080 на машине был свободен.

**Что сделать.**

1. `infra/compose.pilot.yml`, сервис `frontend`:

   ```yaml
       # Compose сливает последовательности добавлением: без !override сюда добавилась бы
       # жёсткая публикация dev-базы 127.0.0.1:8080 (infra/docker-compose.yml), и контейнер
       # падал бы с «Bind for 127.0.0.1:8080 failed: port is already allocated», когда 8080
       # занят другой программой. !reset не подходит: значение при нём игнорируется и порт
       # пилота исчезнет совсем.
       ports: !override
         - "${HRM_PILOT_BIND:-127.0.0.1}:${HRM_PILOT_PORT:-8080}:8080"
   ```

2. Префлайт: минимальная версия Compose `2.24` → **`2.24.4`** (`Preflight.psm1`, `$minimumVersion`
   ~стр. 255 и сообщение ~стр. 301, которое упоминает тег `!reset` — отразить `!override`). Проверить,
   что `Compare-HrmCliVersion` сравнивает `2.24.4` корректно (в `docker.tests.ps1` есть кейсы на
   `2.24` — добавить на `2.24.4`, не ослабляя существующие).
3. Python-проверки (`backend/tests/test_pilot_overlay.py`): загрузчик `_ComposeLoader` знает только
   `!reset` (строка ~31) — без конструктора для `!override` весь файл упадёт с `ConstructorError`.
   Добавить конструктор, возвращающий значение как есть.
   - `test_pilot_overlay_publishes_only_loopback_frontend` (~стр. 68) сверяет точную строку порта —
     обновить под `!override`, смысл проверки сохранить.
   - `test_pilot_overlay_needs_compose_v2_24_like_production` (~стр. 210) ждёт `"2.24"` — поднять до
     `2.24.4`.
4. **Главный новый контрпример** (Python): слить базу и оверлей и проверить результат слияния — фикстуры

## P2 (обязательно, малое): отказ должен называть причину, а не «не отвечает приложение»

Bind-ошибка попадает в журнал (08:35:56), но оператору и пользователю показывается только «на порту не
отвечает приложение HR Manager» — реальная причина (порт занят) не видна. В пути неуспешного `up`
(`Start-HrmStack`/`Repair-HrmStack`) распознавать паттерн конфликта порта
(`Bind for … failed: port is already allocated`, `port is already allocated`,
`address already in use`, `failed to set up container networking`) и выдавать понятный отказ с именем
порта и следующим шагом («порт X занят другой программой: освободите его или задайте другой через
`-Port`»). Секреты редактировать как и раньше (`Redact-HrmText`). Существующие коды отказов не
подменять — добавить ветку. Контрпример в `db-password.tests.ps1`: мир, где `up` падает с таким
stderr → сообщение/состояние содержит порт и причину, а не общий `failed`.
