# Промпт для AI-агента: единая база кандидатов

Продолжи разработку HR Manager с этапа «Единая база кандидатов» из
`ROADMAP.md` (это этап 2 роадмапа; в нумерации предыдущих промптов он идёт
третьим — см. `prompts/PHASE_1_PROMPT.md` и `prompts/PHASE_2_PROMPT.md`).

## Перед началом

1. Прочитай `agents.md`, `PRODUCT_SPEC.md`, `ROADMAP.md`, `README.md` и
   `docs/ARCHITECTURE.md`.
2. Изучи принятый в `main` дизайн-трек: `design/IMPLEMENTATION_GUIDE.md`
   (раздел «API-контракты» и словарь этапов), `design/DESIGN_SYSTEM.md`,
   `design/PERSONAS_AND_FLOWS.md` и прототип `design-prototype/`. Прототип —
   визуальный ориентир для будущих экранов этапа 3, а не код для копирования
   в production.
3. Начни строго от актуального `origin/main` и создай отдельную ветку
   `arena/phase-3-candidates`.
4. Не выполняй merge в `main`.
5. Сначала изучи существующий код и проверки, затем кратко сообщи план.

## Цель

Реализуй законченный минимальный контур единой базы кандидатов: backend-API с
правами, миграциями и тестами, плюс минимальный frontend-клиент без экранов:

- схема кандидата: ФИО, телефон, email, источник, должность, ответственный
  `owner_user_id`, этап воронки, даты, комментарии;
- единый словарь этапов из `PRODUCT_SPEC.md` §5: новый, контакт, дозвон,
  собеседование назначено, собеседование проведено, оффер, оформлен, вышел,
  испытательный срок, уволен, отказ — как backend enum и общий контракт;
  не изобретай другие названия (см. риск «двух источников правды» в
  `design/IMPLEMENTATION_GUIDE.md`);
- история взаимодействий по кандидату: автор, тип, комментарий, момент;
- soft delete и восстановление кандидата; физическое удаление запрещено;
- серверные поиск (ФИО, нормализованный телефон, email), фильтры (этап,
  источник, ответственный, даты), сортировка и пагинация;
- права: HR по умолчанию видит и меняет только своих кандидатов;
  руководитель и администратор видят всех и могут фильтровать по
  ответственному; права проверяются на сервере для каждого endpoint;
- защита от дублей: при создании/изменении поиск похожих кандидатов по
  нормализованному телефону/email; API возвращает совпадения, а повторное
  создание требует явного подтверждения пользователя (`PRODUCT_SPEC.md` §4);
- аудит изменений кандидатов: создание, изменение, смена этапа, soft delete,
  восстановление — с записью в существующий `audit_log`;
- frontend: типы и функции API-клиента кандидатов в `frontend/src/types.ts`
  и `frontend/src/api.ts` с unit-тестами. Экраны (таблица, карточка, Kanban,
  корзина, очередь) не реализуй — это этап 3.

Не реализуй функции последующих этапов: передачу кандидата, рабочий
интерфейс HR, события и календарь, аналитику, шаблоны, импорт/экспорт,
backup. Передача кандидата (`POST /candidates/{id}/transfer`) — этап 3.

API-контракт согласовывай с `design/IMPLEMENTATION_GUIDE.md`
(`GET /candidates?query=&stage=&owner_id=&source=&sort=&limit=&offset=`
с пагинацией, `GET /candidates/{id}`,
`GET|POST /candidates/{id}/interactions`); обоснованные отклонения
задокументируй в отчёте.

## Обязательные требования

- PostgreSQL является рабочей БД; изменения схемы оформляй через Alembic
  (следующая миграция после `0002_identity_security`).
- Персональные данные кандидатов маскируй в логах; не добавляй реальные
  персональные данные, `.env`, дампы и секреты.
- Мутирующие endpoint'ы защищай сессией и CSRF-заголовком `X-CSRF-Token`
  как существующие.
- Пагинация и фильтрация — серверные; не выгружай весь список одним ответом.
- Не ломай health 200/503, lifespan с `engine.dispose()`, Docker Compose,
  production hardening и существующий CI.
- Обнови `README.md` (статус, таблицу endpoint'ов) и при необходимости
  `docs/ARCHITECTURE.md`.

## Тесты и критерии готовности

Добавь unit- и PostgreSQL integration-тесты для:

- создания, чтения, изменения кандидата и записи взаимодействия;
- прав доступа: HR видит только своих, руководитель и администратор — всех,
  HR не может изменить чужого кандидата, неаутентифицированный получает 401;
- смены этапа и валидации значения по словарю;
- soft delete, восстановления и исключения удалённых из обычных списков;
- поиска, фильтров, сортировки и пагинации;
- защиты от дублей: похожий кандидат найден → ответ с совпадениями,
  создание без подтверждения отклоняется, с подтверждением — выполняется;
- аудита изменений кандидатов;
- Alembic upgrade, downgrade и повторного upgrade.

Проверь backend, frontend, миграции и Docker Compose. Все GitHub Actions jobs
должны пройти. Не утверждай, что проверка выполнена, если она не запускалась.
