## 1. P1 — ревизия `0018` занята тремя открытыми PR (обязательно решить)

**Где:** `backend/alembic/versions/0018_template_library.py:25-26` —
`revision = "0018"`, `down_revision = "0017"`.

**Что не так.** Сейчас в репозитории **три** открытых PR, и все три добавили миграцию с
`revision = "0018"` и `down_revision = "0017"`, все от одной базы `main` @ `a1a6c30`
(головa цепочки — `0017`):

| PR | Ветка | Файл миграции |
| --- | --- | --- |
| #46 Импорт графика из Excel | `arena/01a0f30d-hr-manager` | `0018_work_schedule_import.py` |
| #48 Вложения кандидатов | `arena/01a0f30e-hr-manager` | `0018_candidate_attachments.py` |
| **#47 этот PR** | `arena/01a0f324-hr-manager` | `0018_template_library.py` |

Git сливает их чисто — имена файлов разные, GitHub рапортует `mergeable: clean`, ничто
не предупреждает.

**Доказано исполнением.** Ревьюер положил все три файла в одно дерево и прогнал
alembic:

```
heads: ['0018', '0018', '0018']
ScriptDirectory.get_revision("0018").path → 0018_work_schedule_import.py
walk_revisions("base","heads") → в цепочку попадает ТОЛЬКО 0018_work_schedule_import.py
```

То есть **две миграции из трёх молча теряются** — alembic разрешает `0018` в один
файл, второй и третий не попадают в цепочку вообще.

**Blast radius проверен отдельно.** Ревьюер собрал схему `document_templates` без
колонок `category`/`summary`/`seed_key` (как на `main` до миграции) и выполнил запрос
моделью:

```
SELECT * FROM document_templates → OperationalError: no such column: document_templates.category
```

Поэтому если миграция этого PR потеряется, упадут не только `/library/materials`, но и
**`GET /document-templates` и весь контур шаблонов Phase 16, включая генерацию
документов** — потому что `template_out` теперь тоже выбирает `category` и `summary`.

**Страж этого не ловит.** `backend/tests/test_migrations.py:146`
(`test_head_revision_matches_the_migration_chain`) строит **множество** имён:

```python
heads = {line.split()[0] for line in result.stdout.splitlines() ...}
assert heads == {HEAD_REVISION}
```

При дубле/тройном дубле получается `{'0018'} == {'0018'}` — тест **проходит**. Ревьюер
прогонял его в сломанном состоянии: `1 passed`.

Твоя собственная задача говорит: «Не объединять эту работу с импортом графика,
вложениями кандидатов, PR #45 или исправлениями других разделов». Ты знал о
параллельных PR — и всё равно взял `0018`, не посмотрев открытые PR и не предупредив.

### Решение (принято ревьюером)

**Порядок слияния: #46 → #47 → #48.**

Обоснование: #46 дальше всех по конвейеру (доработка P3 уже закоммичена, CI зелёный);

## 2. P3 — сопоставление дубликатов при импорте игнорирует `scope`

**Где:** `backend/app/document_templates.py`, `find_same_name_template` (~`:477`).

Функция ищет совпадение по `kind` + `name` и **не учитывает `scope`** — область
применения (пустая строка = вся база, либо этап воронки). При этом у `DocumentTemplate`
`scope` — часть идентичности: «Анкета» с `scope=""` и «Анкета» с `scope="interview"` —
это два разных материала с одинаковым `kind` и `name`.

**Фактически:** импорт файла с именем «Анкета» и `scope="interview"` находит тот
шаблон, что создан раньше по `created_at` — возможно, с другим `scope`. Пользователю
в диалоге 409 показываются только `id`, `name`, `kind`, `revision`
(`backend/app/routers/document_templates.py:157-165`) — **scope не виден**, поэтому
понять, к какому именно материалу предлагается добавить версию, невозможно. Версия
может уйти не в тот шаблон.

**Ожидалось:** сопоставление по полной идентичности (`kind`, `scope`, `name`), а в
структурированном ответе 409 — `scope` существующего материала, чтобы выбор был
осмысленным.

**Сделать:**
* включить `scope` в сопоставление (сравнивать нормализованно, как сейчас для имени);
* добавить `scope` (и человекочитаемую метку этапа, если она уже есть во фронтенде) в
  `existing` ответа 409;
* показать `scope` в диалоге фронтенда;
* тест: два шаблона с одним `kind` и `name`, но разным `scope` — импорт не считает их
  дубликатами и не предлагает версию чужого.

разные». Ревьюер прогнал твой тест в `TZ=UTC`, `America/New_York`, `Asia/Yakutst`,

текстовый, и его разрешает тот, кто мержит вторым.

## 4. P3 — тест «concurrent safe» конкурентность не проверяет

**Где:** `backend/tests/test_integration_library.py:29`,
`test_pg_seed_idempotent_and_concurrent_safe`.

Название и комментарий утверждают: «A second run — **including a racing one** — must
not duplicate anything». Фактически тест делает последовательный второй запуск
`seed_library()` и один ручный `INSERT`, нарушающий частичный уникальный индекс.
Двух **параллельных** запусков `seed_library()` в тесте нет.

**Фактически:** параллельный сценарий не покрыт.

**Ожидалось:** либо настоящий параллельный прогон, либо честное название/комментарий.

Это не дефект кода: `backend/app/main.py:165-178` оборачивает `seed_library` в
`try/except Exception` с `logger.exception`, поэтому гонка не роняет процесс — она
логируется и повторяется на следующем старте. Но название теста и комментарий
переоценивают то, что проверяется.

**Сделать одно из двух:** (а) добавить настоящий параллельный прогон двух
`seed_library()` (две сессии/транзакции, затем проверить, что дублей нет и процесс не
упал); (б) переименовать тест и переписать комментарий по факту — «идемпотентен при
повторном запуске; частичный уникальный индекс отвергает дубль `seed_key`». Вариант
(б) допустим, вариант (а) предпочтительнее.
