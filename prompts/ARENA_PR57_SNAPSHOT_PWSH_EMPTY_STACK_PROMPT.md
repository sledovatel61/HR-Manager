## 2. Дефект (локализация ревьюера, подтверди её эмпирически)

`Get-HrmStackState` (`infra/windows/engine/Compose.psm1:103`) возвращает `unknown` только
когда `Get-HrmComposeContainers` (`Compose.psm1:60-78`) вернул `$null`. В этой функции
`$null` возвращается лишь при `$ps.ExitCode -ne 0` либо при срабатывании **внешнего**
`catch { return $null }`.

Мок (`infra/windows/tests/test-harness.ps1`, ветка `compose ps`) при пустом стеке отдаёт
`ExitCode = 0`, `Stdout = "[]"`. Значит срабатывает внешний `catch`: первый
`@($ps.Stdout | ConvertFrom-Json -ErrorAction Stop)` бросает, затем fallback по строкам на
`"[]"` бросает снова.

Локализация подтверждена исключением:

1. Мок на pwsh работает — 14 остальных кейсов `stack.tests.ps1` и все 31 кейс
   `db-password.tests.ps1` (через тот же мок) зелены.
2. Единственный тест, подающий пустой `[]` в `Get-HrmComposeContainers` и assert-ящий
   `absent`, — `stack.tests.ps1:24`. Он же единственный провал.
3. В `db-password.tests.ps1` состояние `absent` достигается непустым списком контейнеров
   (отсутствует контейнер `db`), поэтому путь пустого списка там не покрыт.

**Почему это важно для пользователя, а не только для CI:** на машине с pwsh 7 и действительно
пустым стеком (чистая машина, первый запуск) состояние определяется как `unknown` —
«Не удалось получить состояние контейнеров» — вместо `absent` — «Контейнеры ещё не созданы».
Дальше по этой ветке принимаются решения о сборке и восстановлении, то есть неверно
классифицируется вход первого запуска.

## 3. Шаг 1. Сначала точно установи семантическую причину (не угадывай)

На машине с **установленным pwsh 7** выполни минимальный репро и зафиксируй вывод **обоих**
хостів в отчёте:

```powershell
# 1) что именно бросает
foreach ($h in @('Windows PowerShell', 'pwsh')) { ... }   # запусти отдельно в каждом хосте
'[]' | ConvertFrom-Json -ErrorAction Stop
"rc=$? ; err=$Error[0]"
@('[]' | ConvertFrom-Json -ErrorAction Stop).Count
'[]' -split "`r?`n" | ForEach-Object { "line=[$_]" }
```

Нужно зафиксировать: бросает ли `"[]" | ConvertFrom-Json -ErrorAction Stop` под pwsh, и чем
именно (текст ошибки), и что возвращает под 5.1. **Не меняй код, пока причина не записана
точным текстом ошибки.**

## 4. Шаг 2. Узкий фикс

Требование к семантике: **«контейнеров нет» и «состояние неопределимо» — разные вещи.**
Пустой (успешно разобранный) список → `absent`. Невозможность получить список (недоступен
Compose/движок, ненулевой exit code, нечитаемый вывод) → по-прежнему `unknown`.

Допустимые приёмы (выбери и обоснуй): явно различать пустой результат и ошибку разбора;
либо возвращать из `Get-HrmComposeContainers` различаемый признак; либо приводить пустой
массив к `@()` до `Where-Object`. Решение должно работать **одинаково на 5.1 и pwsh**.

**Границы правки (жёстко):**

- Не трогать `Remove-HrmPilotDataVolume` и allowlist удаления тома.
- Не трогать топологию, `compose config`, порт-проверки, `Start-HrmStack`,
  `Test-HrmContainerRunning/Healthy`, `Wait-HrmReady`, синхронизацию пароля БД.
- Не менять состояния `stopped` / `partial` / `degraded` / `running` и их тексты.
- Не менять смысл `unknown`: он остаётся признаком «не удалось определить».
- Не ослаблять hygiene-проверку, не менять `.gitignore`, не трогать лицензионные ворота.
