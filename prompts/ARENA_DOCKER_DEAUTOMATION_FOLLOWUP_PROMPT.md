## Задача 1 (P3). Sidecar: сверять SHA256, а не только наличие

Факт: `infra/windows/engine/Docker.psm1:895-908` (`Get-HrmDockerInstallGuide`) называет
локальный путь, если файл существует. Ожидаемый хеш движку недоступен: в `{app}`
попадает `release.json` (`installer/installer.iss:84`), но не `release-manifest.json`.

Требование:

1. `installer/build.ps1`: добавить в `staging/app/release.json` блок
   `docker_desktop_installer` (`available`, `sha256`, `source_url`,
   `automatically_launched = false`), значения взять из уже существующего
   `$dockerInstallerInfo` — не дублировать логику хеширования.
2. Движок: helper (или расширение `Get-HrmDockerInstallGuide`) читает `{app}\release.json`,
   берёт ожидаемый `sha256`, считает `Get-HrmFileSha256` (`Common.psm1:458`) для
   `{app}\docker\DockerDesktopInstaller.exe` и называет локальный путь **только при
   полном совпадении**. Несовпадение или отсутствие ожидаемого хеша → только
   официальный URL + `Write-HrmLog "warn"`; установка при этом НЕ падает (файл
   необязателен и никем не запускается).
3. Не сломать инвариант канала обновлений: `Channel.psm1:211-217` сравнивает только
   `release_sha` — убедиться, что новый ключ в `release.json` проверки не ломает.
4. Тесты (`docker.tests.ps1` и/или `engine.tests.ps1`):
   - файл на месте и хеш совпал → локальный путь назван;
   - файл на месте, хеш не совпал → локальный путь НЕ назван, официальный URL есть,
     установка не падает;
   - sidecar отсутствует → только официальный URL (существующий кейс сохранить);
   - build-контракт: `release.json` содержит блок, значения совпадают с
     `docker_desktop_installer` манифеста (дополнить статический кейс про build).
5. Документация: `infra/windows/README.md` и `installer/README.md` — уточнить, что
   локальный путь показывается только при совпадении SHA256.

## Задача 3 (P3). Проверка подписи опубликованного sidecar (вместо удалённого аудита)

Факт: в PR #56 удалены `infra/windows/tools/Audit-HrmDockerPublisher.ps1` и job
`docker-publisher-audit`; Authenticode/Subject-проверка не восстановлена нигде, хотя
`pilot-release.yml` публикует sidecar.

Требование:

1. Восстановить проверку **локального файла**: инструмент
   `infra/windows/tools/Assert-HrmDockerInstallerSignature.ps1` (или аналог) —
   принимает путь к файлу, проверяет Authenticode (`Get-AuthenticodeSignature`) и
   точный Subject/отпечаток издателя Docker (константы закрепить в самом инструменте,
   не в движке), печатает факты, код 0 — ок, 1 — тревога, 2 — не удалось проверить.
2. Вызов: шаг в `.github/workflows/pilot-release.yml` **только когда sidecar

   запуска владельцем релиза. В `pull_request`/`push` прогонах скачиваний быть не должно.
3. Движок (`infra/windows/engine/*`) этот инструмент НЕ вызывает и не импортирует:
   горячий путь установки остаётся без обращений к подписи и без скачиваний.
4. `infra/windows/tests/static.tests.ps1` уже парсит все `tools/*.ps1` — убедиться,
   что новый файл покрыт (кейс идёт по каталогу, но проверить явно) и что он с BOM.
5. Документация: `installer/README.md` и `docs/DOCKER_RUNTIME_DECISION.md` —

## Задача 4 (P4). Блокировка действия на пути повтора первичной настройки

Факт: `infra/windows/engine/Install.psm1:560-585` — новая ветка `Open-HrmApp` вызывает
`Install-HrmApp` ДО захвата блокировки (`Enter-HrmActionLock` — `Install.psm1:611`).
Двойной клик по ярлыку даёт две параллельные первичные установки. Из трея путь защищён
своей блокировкой, из ярлыка (`-Action open` напрямую) — нет.

Требование: захватывать блокировку до ветки повтора (либо отдельную блокировку `install`
внутри ветки), снимать в `finally`. Занятая блокировка → понятное сообщение, без
исключения-краша. Добавить поведенческий тест: блокировка занята → повторный `open` не
начинает вторую установку (по образцу существующих reentrancy-кейсов supervisor-тестов).
