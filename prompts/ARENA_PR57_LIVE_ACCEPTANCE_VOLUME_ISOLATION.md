## 3. Живая приёмка — blocker подтверждён, выход есть

Локальный агент прав, и вот доказательство из кода (`Compose.psm1`):

```powershell
$script:ProjectName = "hr-manager-pilot"          # строка 7
function Get-HrmProjectName { return "hr-manager-pilot" }   # строки 9-13
$composeArgs += ("--project-name", $script:ProjectName)     # строка 27
```

Имя проекта **захардкожено и передаётся флагом `--project-name`**. Флаг командной
строки сильнее любой переменной окружения, поэтому `COMPOSE_PROJECT_NAME` не
поможет. Том постгреса считается от этого же имени
(`hr-manager-pilot_pilot_pgdata`, `Compose.psm1:747`).

Следствие: «чистая установка» на этом ПК неизбежно обратится к **тому же
проекту и тому же тому**, что и живой пилот от 10.09. При этом критерий приёмки
«старый стек и старые тома не тронуты» на общей демоне невыполним в принципе.
Останавливаться было правильно.

### Путь без второй машины: резервная копия → свежий том → приёмка → откат

Каждый разрушающий шаг имеет резервную копию. Данные не удаляются без неё.

**Шаг 1. Резервная копия тома (обязательно первым делом):**

```powershell
mkdir $HOME\hrm-backup-20261019
docker run --rm -v hr-manager-pilot_pilot_pgdata:/from -v ${HOME}\hrm-backup-20261019:/to alpine tar czf /to/pilot-pgdata-20261019.tar.gz -C /from .
```

**Категорически:** этот архив остаётся на ПК. Не загружать никуда — в нём данные
живого пилота.

**Шаг 2. Остановить пилот, не удаляя тома:**

```powershell
docker compose -p hr-manager-pilot down
```

Без `-v`. Тома остаются.

**Шаг 3. Убрать том, чтобы установщик создал свежий:**

```powershell
docker volume rm hr-manager-pilot_pilot_pgdata
```

Архив из шага 1 делает этот шаг обратимым.

**Шаг 4. Установить в ОТДЕЛЬНЫЙ каталог и StateDir** (файлы живого пилота не
трогаем), запустив `Setup.exe`, собранный CI из `80c3cb9`.

**Шаг 5. Проверить:**

1. код выхода установщика **0**;
2. браузер **сам** открылся на `#setup=<ticket>` — экран «Первый запуск HR
   Manager» с **окном регистрации**, а не сразу ввод логина/пароля;
3. владелец создан **только через этот экран**;
4. приложение открылось и работает;
5. в трее нет «Ошибка»;
6. `setup-run.json` — успешный;
7. с другой машины в той же сети пилот **недоступен** (см. ниже).

**Шаг 6. Вернуть живой пилот:**

```powershell
docker compose -p hr-manager-pilot down          # снять контейнеры приёмки, без -v
docker volume rm hr-manager-pilot_pilot_pgdata   # том приёмки, он одноразовый
docker volume create hr-manager-pilot_pilot_pgdata
docker run --rm -v hr-manager-pilot_pilot_pgdata:/to -v ${HOME}\hrm-backup-20261019:/from alpine tar xzf /from/pilot-pgdata-20261019.tar.gz -C /to
```

Затем поднять прежний пилот его штатной командой и убедиться, что прежний
владелец на месте и пароль не изменён.

**Шаг 7. Повторный проход:** после отката ещё раз открыть приложение — второго
владельца быть не должно, пароль не сбрасывается.

### Проверка отказа сетевому клиенту

С другой машины в той же сети открыть `http://<IP-этого-ПК>:8081` и адрес
доверенного порта. Оба должны быть **недоступны**. Если хоть один отвечает —
правка не достигла цели, сказать immediately, а не после пилота.

## Если есть вторая машина или VM

Там процедура проще: свой Docker daemon, свой проект, свои тома, шаги 1-3 и 6 не
нужны. Это предпочтительный вариант, если он есть.

## На будущее (не сейчас)

Жёсткое имя проекта — это дефект тестируемости: на машине с живым пилотом нельзя
провести чистую установку. Правильное лечение — сделать имя проекта
переопределяемым параметром со значением по умолчанию `hr-manager-pilot`. Но это
правка ядра установщика и лишний круг CI, поэтому на этапе дедлайна объезжаем
резервной копией. Записать в долги.
