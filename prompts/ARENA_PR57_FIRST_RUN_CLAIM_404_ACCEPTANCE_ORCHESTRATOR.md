# Первый запуск: claim отдаёт 404, окно регистрации не появляется

Статус: **открыто.** Это и есть причина, по которой «установка падает, а приложение
работает». Задача — довести первый запуск до рабочего состояния и проверить его на
генуинно чистой установке.

Связанные документы: `ARENA_PR57_SNAPSHOT_RECOVERY_ACCEPTANCE_ORCHESTRATOR.md`
(приёмка recovery), `ARENA_PR57_PILOT_RELEASE_TRUSTSTORE_FIX_PROMPT.md` (сборщик).

---

## 1. Ответ на вопрос «почему установка падает, но приложение работает»

Это **две разные вещи**, и их нельзя путать.

### Сборщик — уже починен

Дефект `Pilot release (Windows)` найден и исправлен исполнителем:

```
$buildArgs = @("-Version", $version)
& ./installer/build.ps1 @buildArgs
```

PowerShell связывал параметры **позиционально**, а не по именам:

- `$Version = "-Version"`
- `$TrustStoreFile = "0.15.0"`

Поэтому сборка искала «файл хранилища доверия» с именем `0.15.0`.

Исправлено: позиционный массив заменён на **именованный hashtable**, параметры
Docker sidecar тоже передаются по именам. `installer/build.ps1` и fail-closed
проверка trust store **не менялись**.

- коммит `dcbc8d2`, ветка `fix/pilot-release-named-arguments`
- репро на `pwsh 7.4.6`, regression-проверки прошли
- Windows PowerShell 5.1: **348/348**

### Установка «падает» — это другой, более старый дефект

Мастер установки отработал правильно: файлы легла, и он **честно** доложил
«приложение не готово», код выхода **10**. Приложение при этом действительно
работает — страница входа открывается на `127.0.0.1:8081`.

Причина в трее:

```
Состояние: Ошибка
  Claim первого запуска не удался (последний статус 404).
```

**404 = бэкенд не принимаетclaim, потому что у него не настроен токен обмена.**

Цепочка в коде (проверена ревьюером, файлы на `6ae189a`):

1. `backend/app/routers/setup.py:301` — эндпоинт `/setup/owner/claim` отдаёт
   `404 "Первоначальная настройка недоступна."` когда `loopback_client_ok()` = false.
2. `backend/app/setup_owner.py:236` `_first_run_enabled()` =
   `environment == "test" or bool(settings.pilot_bootstrap_exchange_token)`.
   То есть **404 ⟺ у бэкенда пустой `PILOT_BOOTSTRAP_EXCHANGE_TOKEN`.**
3. `backend/app/setup_owner.py:315` — та же проверка и внутри `claim_owner`.
   Несовпадение/битый токен дало бы **403**, а не 404. Значит токена в контейнере
   **нет вообще**.
4. Токен попадает в бэкенд через `infra/compose.pilot.yml:95`:
   `PILOT_BOOTSTRAP_EXCHANGE_TOKEN: ${HRM_EXCHANGE_TOKEN:?...}` — из `pilot.env`,
   который пишет движок.
5. `infra/windows/engine/Compose.psm1:7` — **имя Compose-проекта захардкожено**:
   `$script:ProjectName = "hr-manager-pilot"` (и `Get-HrmProjectName` возвращает ту же
   строку). Новый StateDir **не** создаёт изолированный проект и **не** создаёт новые
   тома: `hr-manager-pilot_pilot_pgdata` и `hr-manager-pilot_pilot_backups` общие для
   всех установок на машине.

**Вывод:** вы удалили программу, но каталог состояния и тома Docker уцелели, а
Compose-проект один и тот же. Поэтому движок подключается к **старому стеку**, и
бэкенд в запущенных контейнерах не получает актуальный токен обмена. Claim
отдаёт 404, владелец не создаётся.

**Почему «приложение работает»:** nginx и фронтенд поднимаются и отдают страницу
входа независимо от того, есть ли владелец. Логин-страница — не признак того, что
настройка прошла.

## 2. Ответ на вопрос про окно регистрации

**Окно регистрации уже существует.** Новый экран делать не нужно.

- `frontend/src/components/FirstRunSetup.tsx` — экран «Первый запуск HR Manager»:
  пароль, часовой пояс, рабочие дни, тихие часы.
- `frontend/src/App.tsx:77` — экран показывается, когда в адресе есть
  фрагмент `#setup=<одноразовый тикет>`.
- `infra/windows/engine/Bootstrap.psm1:141` — движок открывает браузер ровно на
  `$baseUrl/#setup=$($result.Ticket)`.

То есть регистрация появляется **только после успешного claim**. Claim упал →
тикета нет → браузер открывается на обычную страницу входа → войти нечем, потому
что владелец не создан. **Это тупик, и он и есть то, на что вы жалуетесь.**

## 3. Два дефекта в движке, которые надо починить (исполнителю)

### 3.1. Повтор при 404 бессмыслен

`Bootstrap.psm1:80`:

```powershell
if ($response.StatusCode -eq 404) {
    # Обмен отключён (нет токена в конфигурации бэкенда): повторим
    # после перезапуска, если бэкенд ещё не перечитал env.
    Start-Sleep -Seconds $interval
    continue
}
```

Комментарий в `setup_owner.py:268` утверждает, что claim «повторяется, пока бэкенд
не сообщит 127.0.0.1». Но повторный POST **не может** изменить ни адрес источника,
ни наличие токена в контейнере: 404 здесь детерминирован. Итог — 12 попыток по
5 секунд (минута пустого ожидания), а потом отказ. Надо либо перезапускать стек и
перечитывать env, либо отличать «ещё не готово» (повторять) от «настройка
недоступна» (сразу внятная ошибка).

### 3.2. Пустой токен → тихий «владелец уже создан»

`Bootstrap.psm1:40`:

```powershell
$token = Get-HrmSecret $StateDir "HRM_EXCHANGE_TOKEN"
if ([string]::IsNullOrEmpty($token)) { return @{ AlreadyCreated = $true } }
```

Если токен пуст, движок считает, что владелец уже есть, пишет «Владелец уже
существует; первый запуск пропущен» и **не открывает браузер**. Пользователь
остаётся перед страницей входа без аккаунта и без объяснения. Пустой токен — это
не «уже создан», это сломанное состояние; он должен давать отказ с причиной.

### 3.3. Легаси-починка ловит только ровно 32 hex

`Bootstrap.psm1:115`: `if ($legacyToken -match '^[0-9a-fA-F]{32}$')`. Если токен
пуст, имеет префикс `retired-` или иную длину — починка не срабатывает, и сценарий
уходит в 3.1/3.2. Нужен явный разбор всех состояний токена, а не только одного.

**Нельзя:** ослаблять fail-closed проверки trust store и loopback; удалять тома
и данные; подменять ошибку текстом, чтобы прогон стал зелёным.

## 4. Что делать локальному агенту — по шагам

### Шаг 1. Снять доказательства (ничего не меняя)

Сначала зафиксировать состояние, **до** любих запусков:

```powershell
# каталог состояния
$sd = "$env:LOCALAPPDATA\HRManager"
Get-ChildItem $sd -Force | Select-Object Name,Length,LastWriteTime

# токен обмена: длина и префикс (НЕ печатать значение)
$s = Get-Content "$sd\secrets.json" -Raw | ConvertFrom-Json
$t = [string]$s.HRM_EXCHANGE_TOKEN
"len=$($t.Length) retired=$($t.StartsWith('retired-')) empty=$([string]::IsNullOrEmpty($t))"

# что реально ушло в контейнер
Get-Content "$sd\pilot.env" -Raw

# журналы
Get-ChildItem "$sd\logs" | Select-Object Name,Length,LastWriteTime

# какой стек поднят и когда
docker ps -a --filter "name=hr-manager-pilot" --format "{{.Names}}\t{{.Image}}\t{{.Status}}\t{{.CreatedAt}}"

# ГЛАВНАЯ ПРОВЕРКА: есть ли токен в ЗАПУЩЕННОМ бэкенде
docker exec hr-manager-pilot-backend-1 env | Select-String "PILOT_BOOTSTRAP_EXCHANGE_TOKEN" |
  ForEach-Object { "найден, длина=$($_.Line.Split('=')[1].Length)" }
```

Ожидание по диагнозу: токен в `pilot.env` есть, а в запущенном контейнере — **нет**
(или контейнеры старые, от предыдущей установки). Это и подтвердит причину 404.

Имя контейнера бэкенда может отличаться — уточнить через `docker ps`.

### Шаг 2. Гenuinely clean installation с изолированным проектом

Новый StateDir **сам по себе не изолирует** — проект `hr-manager-pilot`
захардкожен (`Compose.psm1:7` и `:12`). Поэтому изоляция делается так:

1. В **тестовой копии** дерева (не в рабочей) временно заменить имя проекта, например
   на `hr-manager-pilot-clean-<дата>`, в обоих местах: `$script:ProjectName` и
   `Get-HrmProjectName`.
2. Собрать из этой копии тестовый `Setup.exe` (`installer/build.ps1 -Version 0.15.0`).
3. Поставить с **новым StateDir** (например `%LOCALAPPDATA%\HRManager-clean-<дата>`).
4. Убедиться, что поднялись именно новые контейнеры и новые тома:
   ```powershell
   docker volume ls --format "{{.Name}}" | Select-String "hr-manager-pilot-clean"
   ```
5. Проверить, что старый стек и старые тома не тронуты:
   ```powershell
   docker ps --filter "name=hr-manager-pilot" --format "{{.Names}}\t{{.Status}}"
   docker volume ls --format "{{.Name}}" | Select-String "^hr-manager-pilot_"
   ```

**Это не удаляет ничего** — просто создаётся второй, независимый стек.

### Шаг 3. Проверить сценарий, который просит владелец

1. Запустить `Setup.exe`, дождаться финальной страницы.
2. **Ожидание:** мастер завершается успешно, код выхода **0**.
3. **Ожидание:** браузер сам открывается на
   `http://127.0.0.1:8081/#setup=<тикет>` и показывает экран
   **«Первый запуск HR Manager»** — а не страницу входа.
4. Задать пароль владельца **только через этот экран** (никаких команд).
5. **Ожидание:** после сохранения приложение открывается, владелец в системе.
6. В трее состояние — не «Ошибка».
7. `setup-run.json` содержит успешный статус.

Если хоть один пункт не выполнен — прислать текст ошибки или скриншот.

### Шаг 4. Что именно считать подтверждением

- Окно регистрации появилось **само**, без ручного ввода адреса.
- Владелец создаётся один раз; повторный проход не создаёт второго и не сбрасывает
  пароль (ожидание 409 → «Войдите в приложение»).
- После создания владельца токен обмена гасится (`retired-…`), сырой токен нигде
  не печатается.
- Старые тома `hr-manager-pilot_pilot_pgdata` и `hr-manager-pilot_pilot_backups`
  не удалялись и не изменялись.

## 5. Жёсткие ограничения

- Не удалять тома и данные, не выполнять `down -v`, не трогать порт `8080` и
  работающий пилот.
- Пароль владельца — только через штатный экран первого запуска, не в обход.
- Не печатать секреты, `pilot.env`, значения токенов и пароли. Достаточно длины и
  префикса.
- Evidence и бэкапы — в приватный bundle, не в git и не в чат.
- PR #57 остаётся draft / NO-GO. Не мержить, не релизить.
- **Пароль, который вы прислали в переписке, для этой диагностики не нужен. Он
  попал в переписку — смените его.**

## 6. Почему это важнее, чем оставшаяся приёмка recovery

Приёмка recovery ждёт безопасного baseline. Первый запуск — это то, без чего
пилотную программу нельзя отдать пользователю вообще: без него нет владельца, а
значит нет и входа. Поэтому порядок такой:

1. починить дефекты 3.1–3.3;
2. подтвердить первый запуск на изолированной чистой установке (шаги 2–4);
3. и только потом возвращаться к приёмке recovery на живой установке.
