## 1. P3-1 — имя загруженного файла нужно санитизировать на сервере

**Где:** `backend/app/routers/work_schedule.py:963`

```python
file_name=(file.filename or "график.xlsx")[-255:],
```

**Почему это дефект.** Задача требует буквально: «путь к файлу не отправлять и не
хранить». Через браузер в multipart уходит только базовое имя, поэтому обычный
сценарий безопасен. Но **сервер не имеет права доверять `file.filename`**: API
принимает произвольный multipart, и прямой клиент (curl / Postman / скрипт) может
прислать `Content-Disposition: ...; filename="C:\Users\User\Documents\HR\HR Manager
Desktop\LLM\30.09.2026\График приемов .xlsx"`. Текущий код возьмёт `[-255:]` от этой
строки и **запишет полный Windows-путь владельца в `schedule_imports.file_name`** —
ровно то, что запрещено.

**Требование:**

* Санитизировать имя **на сервере**, до записи: оставить только последний сегмент
  пути (разделители и `/`, и `\`), отбросить букву диска и всё, что до неё, убрать
  управляющие символы и кавычки, ограничить длину.
* Если после санитизации ничего осмысленного не осталось (имя — только путь, или
  пустое) — использовать нейтральное значение по умолчанию, а не «график.xlsx»,
  выдуманное из непроверенных данных.
* В сохранённом значении не должно остаться ни одного разделителя пути и буквы
  диска — при любом входе.
* Применить тот же санитайзер везде, где `file.filename` используется (сейчас это
  только подтверждение импорта), и в preview, если имя там вообще попадает в ответ.

**Тесты (обязательны):**

1. Загрузка с `filename` = полный Windows-путь → в БД оказывается только
   `График приемов .xlsx`.
2. Загрузка с `filename` = `C:\Users\User\` (путь без базового имени) → нейтральное
   значение по умолчанию, без разделителей.
3. Загрузка с очень длинным именем → длина ограничена, хвост не обрезает посередине
   многобайтового символа.
4. Юнит-тест самой функции санитизации на таблице входов: путь, только путь, имя с
   кавычками, имя с управляющими символами, пустая строка, `None`, юникод.

## 2. P3-2 — сырой комментарий из файла не должен попадать в аудит

**Где:** `backend/app/routers/work_schedule.py:757-758`

```python
if row.comment and candidate.start_comment != row.comment:
    note("start_comment", candidate.start_comment, row.comment)
```

`changes` из `_apply_start_fields` склеивается в детали аудита на `:1064`:

```python
details="; ".join([*changes, f"import={import_record.id}"])[:1000],
```

**Почему это дефект.** Задача требует: «Не логировать ФИО, телефоны, email и полное
содержимое строк» и «без помещения полного Excel, содержимого строк и личных данных в
audit/logs». Ревьюер проверил: ФИО, телефонов и email в аудите **нет** — создание
пишет только `source/owner/import`. Но `start_comment` — это свободный текст колонки
G плюс «уехавшие» вправо колонки (`schedule_import.py:830-861`), то есть
**содержимое строки файла**, и оно уходит в аудит дословно. В реальном файле это
заметки вида «на сборку к девочкам, 13 проходит медосмотр», «отправили делать
военник; 442.0» — сами по себе не ПДн, но если пользователь когда-нибудь напишет в
комментарий телефон или e-mail, они окажутся в аудите. Это нарушение требования,
которое сегодня просто не проявилось.

**Требование:**

* В аудит **не помещать текст комментария**. Фиксировать сам факт изменения, а не
  содержимое: например `start_comment: — -> <изменён, 137 симв.>` (или
  `start_comment: <был> -> <изменён>`). Имя поля должно остаться, чтобы изменение
  было отслеживаемым.
* Остальные поля (`start_date`, `start_time`, `start_organization`,
  `start_department`, `position`, `shift`) оставить как есть — они структурные, не
  свободный текст, и ни одно из них не является ПДн.
* Обрезку `[:1000]` сохранить.
* Сам комментарий по-прежнему пишется в карточку кандидата (`candidate.start_comment`)
  — это штатное поле записи, его не убирать. Речь только об аудите.

**Тесты (обязательны):**

1. Импорт файла, где в колонке комментария написаны телефон и ФИО → в
   `AuditEvent.details` для этого кандидата нет ни телефона, ни ФИО, но есть
   `start_comment` и отметка об изменении.
2. Регресс: тот же тест на **обновлении** существующего кандидата (путь `action=match`),
   а не только на создании — оба места используют общий `_apply_start_fields`.
3. Убедиться, что другие поля по-прежнему попадают в аудит полностью (дата, время,
   организация) — тест не должен превратиться в «аудит ничего не пишет».

## 3. P3-3 — уточнить формулировку про колонки с телефонами

**Где:** описание PR #46 (и при необходимости `docs/`).

**Почему.** В PR сказано: «телефоны в колонках H and G». В реальном файле телефон
есть и в колонке **I** (`I101`). Парсер его находит не потому, что колонки
зашиты, а потому что ищет в колонке комментариев и в `MAX_EXTRA_COLUMNS = 8`
колонках правее неё (`backend/app/schedule_import.py:843`) — то есть поведение
правильное, а формулировка в PR неполная и вводит в заблуждение.

**Требование:**

* В описании PR заменить формулировку на точную: телефон ищется в колонке
  комментариев и до 8 колонок правее неё, поэтому H, G и I обрабатываются
  одинаково; фиксированных номеров колонок нет.
* Рекомендуется (не обязательно): юнит-тест, где телефон стоит в колонке заметно
  правее колонки комментариев, — проверить, что он распознаётся как телефон и **не**
  оседает в тексте комментария.
