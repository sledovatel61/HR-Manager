## Дефект, который нужно исправить

`Get-HrmDockerCliPath` (`infra/windows/engine/Docker.psm1:143`) находит CLI контейнеров в известных
каталогах, включая пользовательский `%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin`, и по нему
движок решает, установлен ли Docker. Но фактические вызовы используют **голое имя**, которое резолвится
только через `PATH` процесса. Проверенные точки вызова (10 штук — список полный, но перепроверь сам):

- `infra/windows/engine/Common.psm1:293` — `Invoke-HrmDocker` (через него идёт весь Compose);
- `infra/windows/engine/Docker.psm1:420` — `Test-HrmDockerEngineReady`;
- `infra/windows/engine/Docker.psm1:437` — `Test-HrmDockerLinuxEngineReady`;
- `infra/windows/engine/Preflight.psm1:66, 77, 89, 178`;
- `infra/windows/engine/Diagnostics.psm1:15, 17, 198, 200, 295`.

Сценарий (подтверждён на уровне кода как рассогласование «детекция ↔ вызов»; **на машине пользователя
не воспроизводился** — там `PATH` резолвит docker): Docker установлен без администратора в
`%LOCALAPPDATA%\Programs\DockerDesktop`; детекция сообщает «установлен»; реальный вызов `docker` через
`PATH` не находится (особенно из elevated-процесса или при изменённом окружении) — установка снова
заканчивается ошибкой или таймаутом. Это исправление корректности для чистой Windows-машины, а не
починка наблюдавшегося сбоя. **Не выдавай этот сценарий за своё воспроизведение.**

## Обязательные изменения

1. **Единая точка разрешения.** Каждый вызов docker идёт через разрешённый путь:
   - `Invoke-HrmDocker` (`Common.psm1`) резолвит CLI через `Get-HrmDockerCliPath` (`Docker.psm1`) и
     вызывает `Invoke-HrmExternal -Name <разрешённый путь>`. Резолвер остаётся в `Docker.psm1`; вызов
     из `Common.psm1` допустим — все модули движка импортируются вместе (см. `test-harness.ps1:99-101`).
   - Если путь не найден — **структурированный результат**, а не исключение из `Process.Start`:
     `ExitCode = 127`, `Stdout = ""`, `Stderr` с понятным текстом и перечнем проверенных мест.
     Существующие проверки `ExitCode` должны работать без изменений: диагностика → `missing`,
     готовность Engine → `false`, предполётная проверка → отказ с текстом.
   - Все остальные точки вывода на ту же точку (через `Invoke-HrmDocker` или общий резолвер). Список
     исправленных точек пришли в отчёте — он должен быть не короче проверенного выше.
2. **Логирование.** Фактически выбранный путь CLI пишется в постоянный журнал один раз на процесс
   (и при отказе). Без секретов и без дампа окружения.
3. **Сохранить мок-шов.** `Invoke-HrmExternal` остаётся единственной мокабельной границей:
   - в `Initialize-HrmTestEngine` (`infra/windows/tests/test-harness.ps1`, рядом с пином
     `Set-HrmDockerOverride @{ port_free = $true }` на строке 137) добавь
     `Set-HrmDockerOverride @{ cli_path = "docker.exe" }` — иначе на раннере с реальным Docker
     резолвер вернёт полный путь и все существующие моки перестанут совпадать по имени;
   - мок-мир (`New-HrmMockWorld`) должен диспатчить по **базовому имени** (`Split-Path $Name -Leaf`),
     чтобы работали и зафиксированное голое имя, и разрешённый полный путь. Это усиление, не ослабление.
4. **Статические тесты не ослаблять.**
   - «внешние процессы запускаются только через `Invoke-HrmExternal`» (`static.tests.ps1:83`) — запрет
     прямых вызовов должен продолжать работать;
   - «разрешённые имена внешних команд — только белый список» (`static.tests.ps1:93`) — после перехода
     на переменную с путём литерала в вызове не останется; если белый список перестаёт что-то проверять,
     усиль его (например: имя в `Invoke-HrmExternal` может быть переменной только если она получена из
     единственного резолвера), а не удаляй и не ослабляй. Любое изменение статики — с обоснованием в PR.
5. **Регрессионные тесты** (поведенческие, по существующим соглашениям harness'а):
   - **(a)** CLI есть ТОЛЬКО в пользовательском каталоге: `Set-HrmDockerOverride @{ cli_path = "<путь
     вида %LOCALAPPDATA%\Programs\DockerDesktop\resources\bin\docker.exe>" }`. Убедись, что вызовы
     docker уходят с разрешённым путём (мок записывает `Name`), что compose/`info`/readiness при этом
     работают (диспатч по базовому имени) и что отката на голое имя нет.
   - **(b)** CLI не найден нигде: `Set-HrmDockerOverride @{ cli_path = "" }`. Движок получает чистый
     отказ (`ExitCode` 127 + сообщение, без исключения), `Test-HrmDockerEngineReady` → `false`,
     `Get-HrmDockerState` → `missing`.
   - **(c)** С пином харнесса (`docker.exe`) поведение не изменилось: существующие тесты проходят без
     правок под новый баг.
