Статус: CI #621 на `80c3cb9`. `Backend checks` **зелёный** — пять тестов закрыты.
Упал только `Compose stack smoke test`, и только на **первом** шаге:
`check_pilot_ports.py` → `before_plain_ports: unexpected frontend port publications`.

**Это не дефект приложения.** Скрипт сверяет порты реального мерджа Compose и
ждёт старую топологию. Новая топология задумана и реализована так:

| сервис | публикации в пилоте |
|---|---|
| frontend | `${HRM_PILOT_BIND:-127.0.0.1}:${HRM_PILOT_PORT:-8080}:8080` + `127.0.0.1:${HRM_PILOT_TRUST_PORT:-18002}:8081` |
| backend | `127.0.0.1:${HRM_PILOT_CLAIM_PORT:-18001}:8000` |
| db, worker, backup | `!reset []` — нет |

Всё на loopback по умолчанию. `0.0.0.0` — только через `HRM_PILOT_BIND`.

## Задача 1. Починить `infra/scripts/check_pilot_ports.py` (быстро, механически)

Ожидания считать из переменных окружения, которые скрипт сам пишет в
`pilot.env`, а не хардкодить. `HRM_PILOT_CLAIM_PORT` и `HRM_PILOT_TRUST_PORT`
в `required` не входят (там `:-`, не `:?`), поэтому Compose берёт значения по
умолчанию 18001 и 18002.

Ожидаемые публикации по сценариям (host = `HRM_PILOT_BIND`, port = `HRM_PILOT_PORT`):

| сценарий | host | port | frontend | backend |
|---|---|---|---|---|
| `before_plain_ports` | 127.0.0.1 | 8081 | dev `127.0.0.1:8080→8080` + `{host,8081,8080}` + `{127.0.0.1,18002,8081}` | dev `127.0.0.1:8000→8000` + `{127.0.0.1,18001,8000}` |
| `after_default` | 127.0.0.1 | 8080 | `{127.0.0.1,8080,8080}` + `{127.0.0.1,18002,8081}` | `{127.0.0.1,18001,8000}` |
| `after_alternate` | 127.0.0.1 | 8081 | `{127.0.0.1,8081,8080}` + `{127.0.0.1,18002,8081}` | `{127.0.0.1,18001,8000}` |
| `after_lan` | 0.0.0.0 | 8091 | `{0.0.0.0,8091,8080}` + `{127.0.0.1,18002,8081}` | `{127.0.0.1,18001,8000}` |

Порядок в списке не важен — сортировка уже есть, её сохранить.

**Проверку сервисов сделать по сценариям, а не общую:**

- для `after_*`: `db`, `worker`, `backup` — без портов (как сейчас);
- для `after_*`: `backend` — **ровно** публикация claim и ничего больше;
- для `before_plain_ports`: `db`, `worker`, `backup` — без портов, а вот
  `backend` **обязан** унаследовать dev-порт. Это и есть смысл отрицательного
  контроля: без `!override` публикации протекают. Проверить это явным
  утверждением, а не ронять ошибкой.

**Смысл отрицательного контроля сохранить.** `before_plain_ports` существует
чтобы доказать, что `!override` несёт нагрузку. Раньше протекал один сервис,
теперь два — контроль стал строже, не слабее.

**Запрещено:** удалять сценарий `before_plain_ports`; удалять проверку сервисов;
ослаблять `after_lan` до «не проверяем»; хардкодировать 18001/18002 вместо
чтения из `values`.

После правки: прогнать `python3 infra/scripts/check_pilot_ports.py --output
pilot-port-merge.json` локально и убедиться, что все четыре сценария `ok`.
