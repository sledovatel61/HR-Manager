## 1. P2 — фильтр активного содержимого PDF обходится (обязательно)

**Где:** `backend/app/candidate_attachments.py:422-452` (`validate_pdf`),
`PDF_FORBIDDEN_MARKERS` — `:124-131`.

**Что не так.** Проверка — поиск подстроки в сырых байтах:

```python
for marker in PDF_FORBIDDEN_MARKERS:
    if marker in payload:
        raise AttachmentRejected(415, ...)
```

Это закрывает только один способ записи. Ревьюер прогнал payload'ы **через реальный
HTTP API** (`POST /candidates/{id}/attachments`) и получил **HTTP 201 — файл загружен**
во всех случаях ниже. Контрольный необфусцированный `/JavaScript` даёт 415, то есть
фильтр работает ровно настолько, насколько написан.

### Класс обхода 1 — пробельные символы внутри имени действия

PDF допускает white-space внутри name-токена, поэтому `/JavaScript` может быть записан
как `/Java Script`, `/Java\nScript`, `/Java\tScript`, `/Java\rScript`. Сырой поиск
подстроки их не видит.

```
/JavaScript + ' '  → HTTP 201      /Launch + ' '      → HTTP 201
/JavaScript + '\n' → HTTP 201      /EmbeddedFile+' '  → HTTP 201
/JavaScript + '\t' → HTTP 201      /XFA + ' '         → HTTP 201
/JavaScript + '\r' → HTTP 201      /RichMedia + ' '   → HTTP 201
/JS + ' '          → HTTP 201      /JS + '\n'         → HTTP 201
```

### Класс обхода 2 — hex-эскейпы `#xx` внутри имени

PDF 32000-1:2008 §7.3.5: символ `#` внутри имени — escape, за ним две hex-цифры.
**Каждый** conforming-ридер декодирует это, так что это не причута парсера, а
нормативная запись того же самого имени.

```
/J#61v#61Script  → ПРИНЯТ   (это /JavaScript)
/Java#53cript    → ПРИНЯТ   (это /JavaScript)
/J#53            → ПРИНЯТ   (это /JS)
/Laun#63h        → ПРИНЯТ   (это /Launch)
/Embedded#46ile  → ПРИНЯТ   (это /EmbeddedFile)
/X#46A           → ПРИНЯТ   (это /XFA)
```

### Класс обхода 3 — конструкция внутри сжатого потока FlateDecode

В PDF 1.5+ объекты лежат в object streams, сжатых FlateDecode, поэтому маркера в сырых
байтах нет вовсе. Это то, чем штатно генерируют современные Word/LaTeX/pdftk.

```python
inner = b"1 0 obj<</S/JavaScript/JS(app.launchURL('c:/x.exe'))>>endobj\n"
comp = zlib.compress(inner)          # маркера в payload нет
# → HTTP 201
```

### Почему это важно, даже если сервер PDF не рендерит

Сервер действительно ничего не исполняет, и на сервере Execution нет. Но смысл фильтра —
не дать HR открыть в Acrobat на Windows файл, который что-то запустит. Сейчас этот файл
можно загрузить и сохранить. Кроме того, комментарий в коде (`:126-130`) утверждает, что
`/OpenAction` и `/AA` «сами по себе безобидны, но указывать могут только на уже
запрещённые конструкции» — это рассуждение верно **только** если запрещённые конструкции
находятся надёжно. С обходом оно перестаёт быть верным.

**Заявление в PR — «PDF — отклоняются /JavaScript, /JS, /Launch, /EmbeddedFile,
/RichMedia, /XFA» — надо либо сделать правдой, либо честно переписать как эвристику с
перечислением известных обходов.**

### Требование

Сделать проверку устойчивой ко всем трём классам. Рекомендуемый подход — сканировать не
один вид payload, а несколько нормализованных:

1. **Нормализация имён.** Пройти по токенам вида `/<name>`: декодировать `#xx`
   (`bytes([int(hh, 16))]`), убрать white-space **внутри** токена. Сканировать
   полученный вид.
2. **Распаковка потоков.** Найти все `stream ... endstream` с `/Filter /FlateDecode`,
   распаковать `zlib` с жёстким лимитом на размер и **с обработкой ошибок** (битый
   поток — не повод уронить загрузку), сканировать и распакованное, и его
   нормализованные имена.
3. Сканировать и сырой payload тоже — как и сейчас.

Важно про ложные срабатывания: нормализация имён (а не «выкинуть все пробелы из файла»)
сохраняет точность — посторонний текст в документе не начнёт совпадать. Если выберешь
более грубый вариант, честно напиши в PR, какую цену это имеет.

Если посчитаешь, что полная защита выходит за рамки задачи, — это допустимо, но тогда:
(а) в PR и в `docs/candidate-attachments.md` явно напиши, что проверка **эвристическая**,
и перечисли известные обходы; (б) не утверждай, что маркеры «отклоняются». Молча
оставить как есть — нельзя.

## 2. P1 — ревизия `0018` занята двумя открытыми PR (обязательно решить)


**Фактически:** после слияния обоих `alembic upgrade head` применит только миграцию
PR #46, таблица `candidate_attachments` **не создастся никогда**, приложение и

**Ожидалось:** единственный head с уникальным номером ревизии.

**Страж этого не ловит.** `test_migrations.py:146` (`test_head_revision_matches_the_migration_chain`)


При дубле получается `{'0018'} == {'0018'}` — тест **проходит**. Ревьюер прогнал его в
сломанном состоянии: `1 passed`. То есть CI не защитит и в этот раз.

Важно: твоя собственная задача говорит «Это отдельный PR: не объединять с импортом
Excel». Ты знал о параллельном PR и всё равно взял занятый номер, не скоординировав и
не предупредив. В промпте это не как упрёк, а как причина, почему в следующий раз нужно
смотреть на открытые PR до выбора номера ревизии.

### Решение (принято ревьюером)

**Порядок слияния: сначала PR #46, затем PR #48.** Обоснование: PR #46 дальше по
конвейеру (доработка P3 уже закоммичена, CI идёт), а PR #48 всё равно требует ещё
круга на P2. Поэтому **ваша миграция становится `0019`**.

### Что сделать

1. Переименовать файл `0018_candidate_attachments.py` → **`0019_candidate_attachments.py`**.
2. `revision: str = "0019"`.
3. `down_revision` должен указывать на ревизию, которая будет **предшествовать** вашей в
   `main` на момент вашего мержа. PR #46 занимает `0018`, поэтому:
   `down_revision: str | None = "0018"`.
   **Важно:** `0018` в `origin/main` пока нет (PR #46 не смержен). Поэтому порядок такой:
   * сделать `git fetch origin`;
   * **перебазировать ветку на `origin/main` ПОСЛЕ того, как PR #46 будет смержен**, и
     только тогда выставить `down_revision = "0018"`;
   * если PR #48 почему-то мержится первым — наоборот: оставить `revision = "0018"` /
     `down_revision = "0017"` как есть, и тогда **PR #46** должен переномероваться в
     `0019` с `down_revision = "0018"`. Прямо напиши в PR, какой из двух сценариев
     актуален на момент сдачи.
4. Обновить `HEAD_REVISION` в `backend/tests/test_migrations.py:24` → `"0019"`.
5. Обновить две коллатеральные правки, которые ты уже делал под `0018`:
   * `backend/tests/test_event_reminder_link.py:306` → `"0019"`
   * `backend/tests/test_work_schedule.py:889` → `"0019"`
6. Не трогать `backend/alembic/versions/0018_work_schedule_import.py` — это файл чужого PR.

### Обязательно: закрыть дыру в страже (независимо от порядка слияния)

Усилить `test_head_revision_matches_the_migration_chain` (`backend/tests/test_migrations.py:146`),

## 3. P3 — «в памяти не более 1 МиБ» — неправда

**Где:** PR body против `backend/app/candidate_attachments.py:242-268` и `:527`.

Ты написал: «Загрузка читается потоково: в памяти не более 1 МиБ, остальное — временный
spool-файл». Spool действительно есть, но `read_upload_limited` заканчивается
`return buffer.read()` (`:267`) — весь payload материализуется в RAM и уходит в
`content=payload` (`:527`).

**Замер ревьюера:** DOCX 5 МиБ → **+19,8 МиБ пикового RSS** (~4× от файла). При
допустимом конфигом максимуме 64 МиБ одна параллельная загрузка стоит ~250 МиБ. Для
пилота с одним администратором и дефолтом 10 МиБ это не опасно, но формулировка неверна.

Честная формулировка уже есть в docstring `read_payload` (`:652-662`) — «Размер строки
ограничен конфигурацией, так что пик потребления памяти известен заранее».

**Сделать одно из двух:** (а) переписать абзац в PR по факту; (б) если хочешь реально
держать пик низким — писать в БД потоково из spool-файла. Вариант (б) не обязателен.
Просто не оставляй утверждение, которое не соответствует коду.
