# Первый запуск: настоящая причина 404 и как её чинить

Статус: **открыто.** Заменяет разделы 1 и 3 документа
`ARENA_PR57_FIRST_RUN_CLAIM_404_ACCEPTANCE_ORCHESTRATOR.md` — там была неверная
гипотеза о причине 404. Диагностика локального агента верна, выводы ниже её
подтверждают по коду.

---

## 0. Признание ошибки ревьюера

В предыдущей инструкции я утверждал, что 404 доказывает отсутствие токена обмена
у бэкенда. **Это неверно.** Локальный агент проверил живой стенд и опроверг:

- в работающем backend токен обмена **есть**, длина 64, среда `pilot`;
- в `pilot.env` токен тоже есть;
- работающий nginx **перезаписывает** `X-Real-IP` адресом клиента.

Бэкенд отдаёт 404 и при отказе loopback-проверки, поэтому по одному коду ответа
причину не определить. Дальше — проверка по коду, которая объясняет оба факта.

---

## 1. Настоящая причина: claim не может пройти ни разу

Цепочка (файлы на `6ae189a`, всё проверено ревьюером):

1. `infra/windows/engine/Common.psm1:695` — `Get-HrmBaseUrl` даёт
   `http://127.0.0.1:<порт пилота>`. Движок шлёт claim именно туда
   (`Bootstrap.psm1:55`).
2. `infra/compose.pilot.yml:142` — этот порт публикует **frontend** (nginx):
   `"${HRM_PILOT_BIND:-127.0.0.1}:${HRM_PILOT_PORT:-8080}:8080"`.
3. `infra/compose.pilot.yml` — у **backend** `ports: !reset []`, то есть
   **собственного опубликованного порта у бэкенда нет вообще**. Единственный путь
   к нему — через nginx.
4. `frontend/nginx.conf:33` — `proxy_set_header X-Real-IP $remote_addr;`
   nginx **затирает** заголовок, который прислал движок.
5. `$remote_addr` при публикации порта Docker — это адрес шлюза контейнерной сети
   (например `192.168.65.1`), **не** `127.0.0.1`.
6. `backend/app/setup_owner.py:258` — `loopback_client_ok` берёт `x-real-ip`,
   видит шлюз, `_is_loopback` возвращает false → **404**.

**Итог: заголовок `X-Real-IP: 127.0.0.1`, который движок ставит осознанно
(`Bootstrap.psm1:47`), гарантированно уничтожается nginx. Claim не может удаться
никогда — это не флак, а детерминированный отказ.**

Перезапуск и повторы здесь не помогают: адрес источника от них не меняется.

### Почему нельзя «просто довериться заголовку»

`infra/windows/tests/pilot-final.tests.ps1:345` — есть тест, который **требует**
перезаписи:

```
nginx перезаписывает X-Real-IP на remote_addr (защита от подделки)
  Assert-HrmContains  'proxy_set_header X-Real-IP $remote_addr;'
  Assert-HrmNotContains 'proxy_set_header X-Real-IP 127.0.0.1;'
```

Причина правильная: если nginx начнёт пропускать клиентский `X-Real-IP`, любой
клиент из локальной сети пришлёт `X-Real-IP: 127.0.0.1` и создаст владельца.
Комментарий в `backend/app/setup_owner.py:266` это и описывает.

Значит два требования действительно конфликтуют, и лечить надо **архитектурно**, а
не ослаблением проверки. Старое дерево, где nginx хардкодил `127.0.0.1`,
возвращать нельзя — это ровно та дыра.

---

## 2. Правильное решение: отдельный loopback-порт бэкенда

Заменить `ports: !reset []` у `backend` на публикацию **только на loopback**:

```yaml
backend:
  ports: !override
    - "127.0.0.1:${HRM_PILOT_CLAIM_PORT:-8000}:8000"
```

и направить claim движка **напрямую в бэкенд**, минуя nginx.

Почему это безопасно:

- порт привязан к `127.0.0.1`, поэтому клиент из локальной сети **физически не
  может подключиться** — Docker откажет. Угроза подделки `X-Real-IP` к этому
  порту неприменима;
- nginx в пути нет, заголовок движка доходит нетронутым;
- одноразовый токен (64 hex) по-прежнему обязателен;
- анти-спуфинг правило nginx остаётся как есть — браузерные и сетевые клиенты
  по-прежнему отвергаются loopback-проверкой.

Это ровно то, что задумано комментарием `setup_owner.py:245`: «in pilot the backend
has no externally published port at all, so any request with a loopback address is
by definition a local process». Реализация нарушила замысел, потому что путь к
бэкенду пролегал через nginx.

Требования к реализации:

- порт настраиваемый и **один и тот же** в compose и в движке (нельзя, чтобы они
  разъехались);
- движок берёт адрес claim из этого же источника, а не из `Get-HrmBaseUrl`;
- браузер по-прежнему открывается через nginx — меняется только канал claim;
- значение порта писать в каталог состояния, чтобы диагностика могла его показать.

## 3. Недостроенные состояния токена (исполнителю)

`Get-HrmSecret` (`Secrets.psm1:49`) **сам создаёт** отсутствующий секрет:
`"HRM_EXCHANGE_TOKEN" { New-HrmHex 32 }` — то есть 64 hex, правильная длина. Но
`Start-HrmFirstRun` (`Bootstrap.psm1:115`) разбирает только ровно 32 hex:

```powershell
$legacyToken = Get-HrmSecret $StateDir "HRM_EXCHANGE_TOKEN"
if ($legacyToken -match '^[0-9a-fA-F]{32}$') {
    $repairedToken = Set-HrmSecret ... (New-HrmHex 32)
    $null = Write-HrmPilotEnv ...
    Invoke-HrmCompose ... @("up", "-d")
    Wait-HrmReady ...
}
```

Если токен **отсутствовал или пуст**, `Get-HrmSecret` молча сгенерирует новый и
запишет в `secrets.json` — но `pilot.env` **не перезапишется** и стек **не
перезапустится**, потому что это происходит только внутри `if`. Бэкенд так и не
увидит новый токен → снова 404.

Нужна полная классификация состояний:

| состояние токена | что делать |
|---|---|
| отсутствует / пуст | сгенерировать (уже умеет `Get-HrmSecret`), **перезаписать `pilot.env`**, перезапустить стек, дождаться готовности |
| ровно 32 hex (legacy) | починить на 64 hex + перезаписать env + перезапуск (уже есть) |
| 64 hex | идти дальше |
| `retired-…` и прочий мусор | не считать, что владелец есть; внятный отказ с причиной |

Уже сделанное локальным агентом сохранить: 404 падает сразу с диагностикой вместо
12 повторов; пустой/пробельный/погашенный токен больше не трактуется как
подтверждение существования владельца; 409 и временные повторы не тронуты.

## 4. Что делать дальше — по шагам

### Шаг 1. Закончить правки (исполнителю)

1. Loopback-порт бэкенда + claim напрямую в бэкенд (раздел 2).
2. Классификация состояний токена (раздел 3).
3. Не трогать: анти-спуфинг nginx, fail-closed проверку trust store, loopback-проверку
   бэкенда, обработку 409.
4. Регрессионные тесты: claim идёт на прямой адрес бэкенда; nginx по-прежнему
   перезаписывает `X-Real-IP`; отсутствующий токен приводит к перезаписи env и
   перезапуску; `retired-…` не считается владельцем.
5. Прогон на **обоих** хостах: Windows PowerShell 5.1 и pwsh. Сейчас 350/350 на 5.1.

### Шаг 2. Изолированная чистая установка

Менять StateDir недостаточно: проект `hr-manager-pilot` захардкожен
(`Compose.psm1:7` и `:12`). Нужна полная изоляция:

- отдельное имя Compose-проекта;
- отдельный каталог состояния;
- **свободный порт** (не 8081 — он занят живым пилотом);
- отдельные теги образов.

Порядок:

1. В тестовой копии дерева заменить имя проекта, порт и теги образов.
2. Собрать `Setup.exe` из `6ae189a` + правок, **записав provenance**: коммит, дату,
   и SHA256 самого `Setup.exe` и манифеста.
3. Поставить, дождаться финальной страницы.
4. Проверить: код выхода **0**; браузер **сам** открылся на
   `http://127.0.0.1:<порт>/#setup=<тикет>` и показал экран
   **«Первый запуск HR Manager»**, а не страницу входа.
5. Задать пароль владельца **только через этот экран**.
6. Проверить: приложение открылось, в трее нет «Ошибка», `setup-run.json` успешный.
7. Проверить, что старый стек и старые тома не тронуты:
   ```powershell
   docker ps --filter "name=hr-manager-pilot" --format "{{.Names}}\t{{.Status}}"
   docker volume ls --format "{{.Name}}" | Select-String "^hr-manager-pilot_"
   ```

### Шаг 3. Поведение при повторном проходе

- повторный запуск не создаёт второго владельца и не сбрасывает пароль;
- после создания владельца токен гасится (`retired-…`), сырой токен нигде не
  печатается;
- владелец в живой базе пилота **не сбрасывается** — проверка идёт на изолированном
  стеке.

## 5. Ограничения

- Не удалять тома и данные, не выполнять `down -v`, не трогать порт `8080` и
  работающий пилот на `8081`.
- Пароль владельца — только через штатный экран первого запуска.
- Не печатать секреты, `pilot.env`, значения токенов и пароли. Достаточно длины и
  префикса.
- Не возвращать хардкод `X-Real-IP: 127.0.0.1` в nginx.
- Evidence и бэкапы — в приватный bundle, не в git и не в чат.
- PR #57 остаётся draft / NO-GO. Не мержить, не релизить.
- Пароль, присланный в переписке, сменить — он попал в переписку.

## 6. Почему именно в таком порядке

Приёмка recovery ждёт безопасного baseline и идёт **после** того, как подтверждён
первый запуск. Без работающего первого запуска пилот нельзя отдать пользователю:
нет владельца, нет входа.

Отмечать «исправлено» можно только после шага 2, пункты 4–6: код 0, экран
регистрации открылся сам, владелец создан через штатный экран. Успешная компиляция
и зелёные тесты движка этого не доказывают.
