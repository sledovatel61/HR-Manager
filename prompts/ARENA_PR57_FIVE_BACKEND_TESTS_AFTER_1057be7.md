# Пять упавших backend-тестов из `1057be7`: что чинить и как честно

Статус: **открыто.** Прогон CI `39245382046`, задание `Backend checks`, шаг
«Unit tests»: **5 failed, 1210 passed, 146 deselected**.

Причина внешняя (переход `ubuntu-latest` на Ubuntu 26) **не подтвердилась** — все
пять падений напрямую следствия правки первого запуска. Это ожидаемый «радиус
поражения»: менялась топология compose и конфиг nginx, а Python-тесты кодируют
старые инварианты. PowerShell-аналоги локальный агент обновил, Python — нет.

**Главный риск здесь не «кто напишет», а «сведут ли тесты к зелёному, потеряв
инвариант».** Поэтому ниже для каждого теста: какую защиту он проверяет и как
переписать так, чтобы защита осталась.

---

## 1. `tests/test_compose_license_chain.py::test_script_env_lines_match_secrets_psm1_writer_exactly`

**Что защищает:** два источника правды про `pilot.env` — PowerShell-записчик
`Write-HrmPilotEnv` и Python `engine_env_lines` — не должны разъехаться. Иначе в
контейнер уедет не то, что считает движок.

**Что сломалось:** движок теперь пишет `HRM_PILOT_CLAIM_PORT` и
`HRM_PILOT_TRUST_PORT`, в Python-список они не добавлены (и порядок другой).

```
At index 8 diff: 'HRM_PILOT_BIND' != 'HRM_PILOT_CLAIM_PORT'
```

**Как чинить:** добавить оба имени в Python-список **в том же порядке**, в каком
их пишет `Write-HrmPilotEnv`. Тест сравнивает список целеком, поэтому порядок
значим. Нельзя: удалять имена из PowerShell-записчика, чтобы сравнение сошлось, —
это сломало бы передачу портов в compose.

---

## 2. `tests/test_pilot_final.py::test_x_real_ip_spoof_blocked`

**Что защищает:** клиент не может подделать `X-Real-IP`, чтобы выдать себя за
loopback и создать владельца.

**Что сломалось:**

```python
assert "proxy_set_header X-Real-IP $remote_addr;" in nginx_text
assert "proxy_set_header X-Real-IP 127.0.0.1;" not in nginx_text   # ← теперь false
```

Жёсткая пометка появилась в новом loopback-блоке.

**Как чинить:** сделать проверку структурной.

- первая строка остаётся **без изменений**;
- вторая заменяется на: жёсткая пометка `127.0.0.1` встречается **только** внутри
  серверного блока, который слушает loopback-порт, и **не встречается** в блоке,
  который слушает общий порт;
- добавить утверждение, что блок общего порта по-прежнему использует
  `$remote_addr`.

Нельзя: убрать жёсткую пометку из loopback-блока (сломается первый запуск) или
разрешить её в общем блоке (откроется дыра для сетевых клиентов).

## 3. `tests/test_pilot_overlay.py::test_pilot_overlay_publishes_only_loopback_frontend`

**Что защищает:** пилот по умолчанию не публикует порты наружу.

**Что сломалось:**

```python
assert set(published) == {"frontend"}, published
# стало: {'backend': ['127.0.0.1:${HRM_PILOT_CLAIM_PORT:-18001}:8000'],
#         'frontend': ['...8080', '127.0.0.1:${HRM_PILOT_TRUST_PORT:-18002}:8081']}
```

**Как чинить:** имя теста и его смысл должны отражать новый инвариант — **никакая
публикация не выходит на не-loopback адрес**. Проверять:

- каждая привязка порта в пилоте начинается с `127.0.0.1:` либо использует
  `${HRM_PILOT_BIND:-127.0.0.1}` (значение по умолчанию — loopback);
- ни одна привязка не начинается с `0.0.0.0:` и не использует
  `${HRM_PILOT_BIND:-0.0.0.0}`;
- публикации backend и второго слушателя frontend — обе на `127.0.0.1`.

Нельзя: ослабить до «хотя бы один сервис публикуется на loopback» — это не то же
самое.

---

## 4. `tests/test_pilot_overlay.py::test_merged_pilot_replaces_all_active_service_port_publications`

**Что защищает:** оверлей пилота **заменяет** публикацию разработки, а не
дополняет её. Иначе занятый dev-порт ломает запуск пилота.

**Что сломалось:**

```python
assert merged["frontend"] == ["${HRM_PILOT_BIND:-127.0.0.1}:${HRM_PILOT_PORT:-8080}:8080"]
# стало два элемента — добавился '127.0.0.1:${HRM_PILOT_TRUST_PORT:-18002}:8081'
```

**Как чинить:** проверять именно **замену**, а не конкретный список:

- публикация разработчика `127.0.0.1:8080:8080` в результате **отсутствует**;
- результат равен в точности публикациям пилота (сравнивать с ожидаемым набором из
  оверлея, не с одним элементом);
- поведение при `ports: !reset []` и при отсутствии `ports` не изменилось.

Нельзя: сравнивать с константой из одного элемента — тест снова сломается при
любом добавлении порта и перестанет что-либо значить.

---

## 5. `tests/test_pilot_overlay.py::test_plain_ports_counterexample_inherits_dev_publication`

**Что защищает:** контрпример — сервис с обычным `ports:` (без `!override`)
наследует публикацию разработки, и оверлей обязан это учитывать.

**Что сломалось:** та же причина — список публикаций изменился.

**Как чинить:** пересчитать ожидание с учётом новых публикаций, сохранив смысл:
контрпример по-прежнему показывает, что без `!override` остаётся dev-публикация.

## Порядок работ

1. Обновить пять тестов по инвариантам выше. **Python и PowerShell должны
   проверять одно и то же**, иначе следующая правка снова разъедется.
2. Прогнать backend-тесты **в Linux** (контейнер или CI). На Windows они не
   идут: `backend/app/backup_runner.py:26` — безусловный `import fcntl`.
3. Прогнать оба Windows-хоста: 5.1 и pwsh. Сейчас 354/354 на обоих — не уронить.
4. Закоммитить и запушить. Прислать коммит — ревьюер запустит CI вручную на ветке.
5. Критерий: `Backend checks` зелёный, оба Windows-хоста зелёные, и ни один
   инвариант из списка выше не потерян.
