# Implementation prompt: отказ от автоматической установки Docker Desktop

Готовый промпт для агента-исполнителя. База — head PR #55 `1dec06d` (или `origin/main`
после мержа PR #55). Сопутствующий аудит с доказательствами:
`prompts/ARENA_DOCKER_DEAUTOMATION_REVIEW.md`. Все пути — относительно корня репозитория,
номера строк соответствуют `1dec06d`; **перед началом работ перепроверь их `git grep -n`**
на своей базе (после мержа PR #55 нумерация может сместиться).

> Контекст для исполнителя: около недели предпринимались попытки сделать надёжную
> автоматическую установку Docker Desktop из установщика HR Manager. Принято решение
> **отказаться от неё**: продукт проверяет наличие Docker и понятно объясняет, что
> делать; установку Docker Desktop пользователь выполняет вручную. Код автоустановки,
> добавленный в PR #55 (P3-таймаут установщика, `docker-pending` resume, действие
> `docker-install`), удаляется **целенаправленно** — это не регрессия, а сама задача.

## A. Контекст и цель

На Windows-машине без Docker Desktop текущий установщик пытается сам скачать и запустить
`Docker Desktop Installer.exe` (~600 МБ), перезапускать мастер, писать pending-маркеры и
требовать нажать несуществующую кнопку. Нужно:

1. Убрать всю автоматизацию вокруг Docker Desktop: скачивание, запуск (в любом виде:
   тихий, визард, через elevated-обёртку), установочные pending-резюме, связанные
   CLI-действия, задачи мастера, параметры-флаги и тесты этой функциональности.
2. Сохранить и усилить **проверки и диагностику**: найден ли Docker CLI, запущен ли
   демон, доступен ли Compose, состояние WSL2/виртуализации/прав/места/порта.
3. Дать пользователю **понятное, исполнимое сообщение** без Docker: что установить,
   откуда (официальный URL + локальный путь к приложенному файлу, если он есть),
   и что делать после установки.
4. Распространять `DockerDesktopInstaller.exe` как **внешний файл-компаньон** рядом с
   дистрибутивом с фиксацией URL и SHA256; **никогда не запускать его автоматически**
   и не принимать лицензию за пользователя.

Жёсткие правила поведения (проверяются приёмкой):

- Без Docker → понятное сообщение со ссылкой на docker.com и (если файл приложен)
  локальным путём; никаких «нажмите кнопку, которой нет».
- «Демон не готов» ≠ «Docker не установлен»: состояния различаются текстом.
- Никаких destructive-действий без явного подтверждения пользователя; volumes,
  `down -v`, `volume prune`, удаление Docker Desktop при uninstall — вне задачи.
- Пароли/секреты не попадают в argv, логи и диагностику (проверено на текущем коде —
  не ухудшать).

## E. Новое поведение (контракт)

### E.1. Состояния и тексты

`Get-HrmDockerReadiness`/`Format-HrmDockerReadiness` должны различать минимум:

| Состояние | Условие | Текст (образец; подстроки обязательны) |
|---|---|---|
| `docker_missing` | Docker CLI не найден | «Docker Desktop не установлен. Установите Docker Desktop с официального сайта: https://docs.docker.com/desktop/setup/install/windows/ (или запустите приложенный DockerDesktopInstaller.exe: {путь, если файл на месте}). После установки запустите Docker Desktop и нажмите «Продолжить» — HR Manager сам проверит Docker Engine и Compose.» |
| `engine_not_running` | CLI есть, демон не отвечает | «Docker Desktop установлен, но Docker Engine не запущен. Запустите Docker Desktop и дождитесь статуса Running, затем повторите.» |
| `compose_missing` | демон есть, `docker compose` недоступен | «Docker Engine работает, но плагин Compose недоступен. Обновите Docker Desktop до актуальной версии.» |

Требования к текстам:

- Обязательные подстроки для совместимости с `ci-silent-smoke.ps1:200-215`
  (паттерны `:206`: «Docker Desktop» / «Docker Engine» / «Linux-движок» / …): отказ
  «нет Docker» **обязан** содержать «Docker Desktop» и/или «Docker Engine».
- Согласованность с уже корректными текстами preflight: `Preflight.psm1:79`
  («Установите Docker Desktop только с официального сайта docker.com (лицензия
  принимается вручную)») и `:100` («Демон Docker не запущен…»). Сейчас движок
  противоречит сам себе: `Invoke-HrmDockerPrepare` велит нажать кнопку, preflight —
  установить вручную. Новые тексты должны быть единообразны (допустимо переиспользовать
  формулировки preflight).
- Никаких ссылок на несуществующие кнопки/действия («нажмите “Установить Docker
  Desktop”» — запрещено).
- Упомянуть «Продолжить»/повтор только как действие пользователя в уже существующем UI
  (трей/CLI `resume`, `prepare`), не выдумывать новых точек входа без реализации.

### E.2. Порядок шагов установки (сохранить)

`Invoke-HrmDockerPrepare`: порт → состояние Docker → (новое) отказ/подсказка →
`Assert-HrmPreflight` → env/secrets → compose → readiness. Никаких обращений к сети
и никаких запусков сторонних установщиков на любом шаге.

### E.3. Файл-компаньон `DockerDesktopInstaller.exe`

- Движок ищет файл в `{app}\docker\DockerDesktopInstaller.exe` (куда его кладёт мастер,
  см. §F) и/или рядом с дистрибутивом.
- Если файл найден **и его SHA256 совпадает** с ожидаемым (из манифеста/пина) —
  сообщать локальный путь («запустите приложенный DockerDesktopInstaller.exe: …»).
- Если файла нет или хэш не совпал — только официальный URL; молча игнорировать
  отсутствие файла (это не ошибка).
- **Никогда не запускать файл, не передавать ему аргументы, не принимать лицензию.**

### E.4. Tray / CLI / Setup

- Трей: убрать режимы/подсказки, относящиеся к установке Docker и reboot-resume;
  режим «Docker не готов» показывает текст §E.1 и команду повторить проверку
  (существующий `prepare`/`docker-status`).
- CLI: убрать `docker-install` и `-InstallDocker`; оставить `docker-status`,
  `docker-start`, `prepare`, `install`, `resume`, `update`, `uninstall`.
- Setup: обновить `DockerNote` (и при возможности финальную заметку) так, чтобы было
  честно видно: «HR Manager установлен. Для первого запуска нужен Docker Desktop:
  установите его вручную (см. инструкцию), затем запустите HR Manager из трея.»
  Учесть, что Inno не пробрасывает код возврата `[Run]` — мастер сам не покажет ошибку
  движка.

1. **Не встраивать** `DockerDesktopInstaller.exe` в `Setup.exe` (размер дистрибутива,

   официальный URL (пиннинг). Если файл не найден рядом — не падать, пометить
   `present: false`.
3. `.github/workflows/pilot-release.yml` (`:139-160`, `:181-190`): публиковать
   `DockerDesktopInstaller.exe` в артефакты релиза и включить его в `SHA256SUMS.txt`
   (если присутствует); иначе — явно указать в примечании релиза, что файл не приложен.
4. `installer/installer.iss` `[Files]`: `external` + `Check:` — копировать
   `docker\DockerDesktopInstaller.exe` в `{app}\docker\` **только если файл существует**
   рядом с мастером; отсутствие файла не является ошибкой установки.
5. Никаких `[Run]`-записей, запускающих установщик Docker; никаких `--accept-license`.
6. Проверка подписи/SHA256 приложенного файла — в аудите/диагностике (§G.4),
   не в горячем пути установки.

  вырос) — краткая инструкция: минимальные требования, ссылка на официальную
  установку, проверка `docker version`/`docker compose version`, частые причины
  отказов (WSL2, виртуализация, права, антивирус).

## I. Безопасность, пароли, guardrails

- Не добавлять и не ослаблять защиту: никаких destructive-действий без подтверждения;
  тома пилота не пересоздаются; `down -v`/`volume prune` не появляются в движке.
- Пароли/секреты: не в argv, не в логи, не в `SupportBundle`. Существующий механизм
  (`Secrets.psm1`, env-файл) не менять в этой задаче.
- Удаление тома данных (`Remove-HrmPilotDataVolume`, allowlist) не трогать; uninstall
  **не удаляет** Docker Desktop и **не удаляет** volumes без явного подтверждения.
- Приложенный `DockerDesktopInstaller.exe` — только как файл для ручного запуска:
  проверка подписи/SHA256 в диагностике, без авто-запуска и без принятия лицензии.

## J. Порядок работ и самопроверка исполнителя

1. Создать ветку от актуальной базы, перепроверить якоря (`git grep -n` по каждому
   пункту §C).
2. Удаление автоустановки и связанных параметров/состояний (Docker.psm1, Common.psm1,
   Install.psm1, Supervisor.psm1, Update.psm1, Tray.psm1, hr-manager.ps1, installer.iss).
3. Новые тексты/состояния и логика файла-компаньона (§E).
4. Упаковка (§F): манифест, SHA256SUMS, `[Files] external`+`Check:`.
5. Тесты и инварианты (§G), затем документация (§H).
6. Самопроверка (обязательно выполнить и приложить вывод к PR):
   - `git grep -n "InstallDocker\|docker-install\|dockerinstall\|AllowInstall\|PendingDockerOperation\|docker-pending"` → только ожидаемые остатки
     (`docker-start`, `docker-status`) или их отсутствие.
   - `git grep -rn "accept-license"` → пусто (или явный гвард-тест).
   - Полный прогон PowerShell Suite на Windows (или ссылка на зелёный CI-run).
   - Проверка, что `installer/output/` и `SHA256SUMS.txt` содержат запись о
     `DockerDesktopInstaller.exe` при наличии файла и корректно обходятся без него.
7. Один PR в `main` с описанием: что удалено, что сохранено, как проверено,
   ссылки на изменённые тесты; без изменений в чужих ветках и без force-push.

## K. Acceptance criteria

Функциональные:

1. Движок и установщик **никогда** не скачивают, не проверяют по сети и не запускают
   установщик Docker Desktop (ни тихим режимом, ни визардом, ни через elevated-обёртку).
2. При отсутствии Docker CLI пользователь получает сообщение `docker_missing`,
   содержащее «Docker Desktop», официальный URL и — если файл-компаньон найден и SHA256
   совпал — локальный путь; кнопок/действий, которых нет в UI, сообщение не требует.
3. Различаются состояния: не установлен / движок не запущен / Compose недоступен;
   «неготовый демон» не выдаётся за «Docker не установлен».
4. `docker-pending.json`, pending-функции и reboot-resume для Docker отсутствуют;
   остальной resume (обновления, обычные операции) работает.
5. CLI не содержит `docker-install`/`-InstallDocker`; мастер не содержит задачи
   `dockerinstall`; `GetEngineDockerArgs` не добавляет флаг установки Docker.
6. `docker-start`, автозапуск уже установленного Docker Desktop и ожидание движка
   сохранены.
7. `DockerDesktopInstaller.exe` не встроен в `Setup.exe`; публикуется рядом с
   дистрибутивом, в `SHA256SUMS.txt` и `release-manifest.json` (URL + SHA256);
   копируется в `{app}\docker\` только при наличии; никогда не запускается;
   отсутствие файла не ломает установку и не ухудшает сообщение (остаётся URL).
8. Подпись/SHA256 приложенного файла проверяются в аудите/диагностике; job
   `docker-publisher-audit` не качает 600 МБ на каждом прогоне.
9. Volumes и данные пилота не затрагиваются; uninstall не удаляет Docker Desktop;
   destructive-действий без подтверждения нет; пароли не попадают в argv/логи/диагностику.

Нефункциональные:

10. Все PowerShell-тесты и статические инварианты зелёные в CI на реальном прогоне
    (не «пропущенные ради зелёного»); Suite и `ci-silent-smoke` согласованы с новыми
    текстами.
11. Документация приведена к единой формулировке (§H), противоречия устранены;
    для пилотного пользователя есть пошаговая инструкция ручной установки Docker.
12. PR один, в `main`, с описанием и выводом самопроверки (§J.6).

## Что не входит в эту задачу

1. **Восстановление/смена пароля PostgreSQL в существующем volume** — отдельная задача
   (пилотный инцидент: `POSTGRES_PASSWORD` применяется только при первой инициализации
   тома; пароль расходится с сохранённым `hr-manager-pilot_pilot_pgdata`). Здесь только
   guardrails: тома не пересоздавать, `down -v` запрещён, пароли не в argv/логах,
   SQL-команды — через stdin, бэкап перед любым изменением.
2. Миграция или восстановление данных пилота.
3. Изменение топологии Compose, замена runtime (Docker → Podman/…), смена образов.
4. Любые destructive recovery-действия: удаление/пересоздание volumes, `volume prune`,
   сброс секретов.
5. Улучшения, не связанные с отказом от автоустановки Docker: новый UI трея, редизайн
   мастеров, рефакторинг supervisor/journal (кроме удаления Docker-веток), исправления
   несвязанных дефектов — отдельными задачами.
