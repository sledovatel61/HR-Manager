## 3. Read-only диагностика — почему отказался старый прогон

**Где что лежит (частая путаница):** `release.json` — в **InstallDir** (`{app}`), а
`installed.json` — в **StateDir**. Отсутствие `release.json` в StateDir не является проблемой.

Из checkout с патчем:

```powershell
& .\infra\windows\tools\Compare-HrmSnapshotInputs.ps1 `
    -InstallDir <реальный {app} из мастера> `
    -StateDir <фактический StateDir> `
    -PackageReleaseFile <release.json ИЗ СТАРОГО staging> `
    -PrivateReportFile <приватный файл отчёта>
```

Каталог отчёта создайте заранее с ограниченными ACL — скрипт откажется создавать его сам,
откажется перезаписывать существующий файл и писать внутрь InstallDir/StateDir/checkout.
Скрипт читает ровно три JSON метаданных, не вызывает Docker, SQL, snapshot-adoption и
генерацию секретов. В консоль — только предикаты, без SHA и путей.

Ожидаемые исходы (прогноз по коду, не результат):

- `record_directory_equals_target=false` → смешение каталогов, причина `install_dir_mismatch`;
- `file_equals_record=false` при непустых SHA обоих файлов → отказ `files_replaced`
  (`guard_branch=record_identity_mismatch`); **простая пересборка его не снимает** — нужны
  соответствующие записи файлы или проверенный снимок;
- `file_equals_package=true` → первая ветвь.

Сверьте с двумя строками журнала мастера (`HRM: snapshot decision`, `HRM: снимок предыдущей
версии`) локально. Если исходное staging отсутствует — значение пакета неизвестно, гипотезу
не объявляйте доказанной.

**Важно:** Setup, собранный из нового чистого коммита, имеет другой `release_sha`, чем
установленный 0.15.0, поэтому ветви same-SHA на 8081 не задействуются — guard пойдёт
обычной ветвью. Это прогноз, а не факт.

## 5. Пересборка из ТОЧНОГО коммита

Дождитесь push-а исполнителя (pwsh-фикс + Bootstrap/Secrets), затем:

1. `git fetch` ветки PR, запишите **точный** SHA коммита, из которого собираете.
2. Убедитесь, что checkout чистый: `git status --porcelain` пуст. `installer/build.ps1`
   сам откажется от dirty checkout — это ожидаемо, не обходите.
3. На **Windows PowerShell 5.1** (не только pwsh):
   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File infra\windows\tests\run-tests.ps1
   ```
   Ожидание: все тесты зелёные на **обоих** хостах (5.1 и pwsh). Зафиксируйте числа и host.
4. ```
   powershell -NoProfile -ExecutionPolicy Bypass -File installer\build.ps1 -Version 0.15.0
   ```
5. Запишите SHA256 нового `Setup.exe` и SHA коммита. Без этой пары прогон ничего не
   идентифицирует.
6. **Собирайте локально, не сверяйтесь с SHA256 из CI-PR.** В `ci.yml` триггер
   `on: push: branches: [main]` — пуш в ветку CI не запускает; автоматический прогон идёт
   только по `pull_request`, а для него checkout берёт **merge-коммит** (`refs/pull/N/merge`),
   то есть код `main` + код ветки. Для `b600416` это был `476056fc…` с родителями `75cd9c8…`
   и `b600416…`. Поэтому SHA256 из аннотации задания «Pilot Setup.exe» относится к другим
   байтам и другому `release_sha` — **сравнивать с ним локальную сборку нельзя**, расхождение
   было бы ложным.
   Собирайте из чистого checkout **точного** коммита ветки: `git fetch`, `git checkout <SHA>`,
   убедитесь, что `git status --porcelain` пуст (иначе `build.ps1` справедливо откажет), затем
   `installer\build.ps1 -Version 0.15.0`. Запишите пару «SHA коммита + SHA256 Setup.exe» —
   только она идентифицирует проверяемые байты.
   Если нужна сборка из точного коммита именно через CI, её запускает владелец вручную:
   Actions → CI → Run workflow → ветка `arena/3cadc6a9-hr-manager` (`workflow_dispatch`
   разрешён, при ручном запуске checkout берёт коммит ветки). Зелёный PR-прогон при этом
   остаётся сигналом merge-readiness, но не идентификатором байтов ветки.
   **Ручной запуск CI — предпочтительный путь получить `Setup.exe` из точного коммита, если
   локально нет ISCC.** Задание `Pilot Setup.exe` не имеет условия запуска и выполняет
   `HRM_RELEASE_SHA: ${{ github.sha }}`; при `workflow_dispatch` это коммит ветки, а при
   `pull_request` — коммит слияния (об этом прямо сказано в комментарии к шагу). Артефакт
   забирайте из прогона и сверьте его SHA256 с аннотацией.

## 6. Приёмка recovery на 8081

1. Запустите стандартный `Setup.exe` (без побочных сценариев).
2. **Пока setup pending:** запишите SHA256 `secrets.json` ДО и ПОСЛЕ. Хеш всего файла
   **обязан измениться** — разрешённая замена exchange token меняет файл. Проверяйте не
   равенство хеша, а **состав изменений**: отличается **только** exchange token; пароль,
   ключи резервного копирования/подписи и все прочие поля побайтово неизменны.
3. Пройдите owner claim → установку пароля (только через stdin штатного первого запуска) →
   вход на 8081.
4. Зафиксируйте: код возврата Setup, `setup-snapshot.json`, `setup-run.json`, `supervisor.json`,
   и что приложение реально открылось и ответило.

**Что считается доказательством, а что нет.** Не принимайте как доказательство: факт
компиляции `.exe`, зелёные mock-тесты, файлы в staging, `git diff --check`. Доказательство —
живой прогон с кодами возврата и содержимым перечисленных файлов.

## 8. Финальная сверка целостности

Здесь важно различать фазы — иначе проверка противоречит сама себе:

- **Recovery на 8081 (п.6):** хеш `secrets.json` **должен измениться** (замена exchange
  token), и изменение **только** в нём. Пароль, ключи резервного копирования/подписи,
  прочие поля — побайтово как в baseline из п.2.
- **Чистая установка (п.7) и сценарии с отказом:** если `secrets.json` уже существовал,
  он должен остаться **побайтово** тем же (сверьте SHA256 с baseline). При genuinely clean
  установке прежнего файла нет — это не расхождение, а отсутствие baseline.
- **Тома** `hr-manager-pilot_pilot_pgdata` и `hr-manager-pilot_pilot_backups` на месте.
- **Защиты snapshot не обойдены:** повторный отказ по несовпадению по-прежнему дает отказ,
  а не успех.

## 8А. Не используйте workflow «Pilot release (Windows)» — он сломан

Отдельный дефект, не связанный с приёмкой: workflow `Pilot release (Windows)`
(на `main`, `.github/workflows/pilot-release.yml`) падает при сборке.

- прогон `38918703168` (workflow_dispatch на `main`, `release_sha` = `6ae189a`)
- шаги `Resolve version and SHA`, `Build autonomous license-issuer bundle`,
  `Prepare optional pinned Docker Desktop sidecar` — success
- шаг **`Build HR Manager Setup.exe (pilot, unsigned)`** — failure на
  `installer/build.ps1:280`:

```
Resolving trust store: 0.15.0 (cwd D:\a\HR-Manager\HR-Manager)
Exception: installer\build.ps1:280
  { throw "TrustStoreFile not found: $TrustStoreFile (cwd ...)" }
```

То есть строка версии `0.15.0` попадает в параметр `-TrustStoreFile`, и сборка
отказывается искать «файл хранилища доверия» с именем `0.15.0`. Пилотная сборка
хранилища доверия не использует вовсе.

Уже проверено ревьюером (повторно не проверять):

- param-блок `installer/build.ps1` побайтово одинаков на `main` и на `6ae189a`
- `$TrustStoreFile` нигде не перезаписывается в `build.ps1`
- `pilot-release.yml` передаёт только `$buildArgs = @("-Version", $version)` со
  сплаттингом; слова `TrustStore` в файле нет
- `pilot-release.yml` идентичен на `main` и на ветке; в истории `main` у него один коммит
- `.gitignore` строка 32 — `dist/`, поэтому сборка лицензионного бандла **не** грязнит
  дерево и guard «чистый checkout» проходит

Отброшено: «грязнит дерево» (`dist/` игнорируется), «патч сломал param-блок»
(идентичен `main`), «не тот коммит» (шаг резолва прошёл, checkout = `6ae189a`).

Задание исполнителю выдано отдельно: `ARENA_PR57_PILOT_RELEASE_TRUSTSTORE_FIX_PROMPT.md`.
Там требование — сначала repro на Windows с pwsh, только потом правка.

**Для приёмки это не blocker:** `ci.yml` работает, Setup.exe уже получен. Но это путь,
которым владелец делает настоящий пилотный релиз, так что при мерже PR сломается
штатный релизный сценарий.
