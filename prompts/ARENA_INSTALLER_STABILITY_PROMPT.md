## Этап 2. Находки (по severity, с файлом: строкой и причинной связью)

Ниже — дефекты, **подтверждённые чтением кода**. Ты обязан проверить каждый сам (чтение + тест),
исправить или обоснованно отказаться (в PR — с объяснением). Дополнительно сам найди Race Conditions,
retry/polling без timeout/cancellation, orphaned-процессы и parallel startup tasks — ревьюер будет
искать то, что ты пропустил.

- **D1. `Invoke-HrmExternal` — вечное зависание и deadlock труб** (`engine/Common.psm1:225-230`):
  `Process.Start` → `StandardOutput.ReadToEnd()` → `StandardError.ReadToEnd()` → `WaitForExit()`
  **без таймаута**. Последовательное чтение stdout-потом-stderr — классический pipe deadlock: ребёнок,
  написавший в stderr больше буфера (~64 KB), вешает родителя навсегда (`docker compose build` пишет в
  stderr много). `WaitForExit()` без аргумента не ограничен ничем: `docker info`/`compose ps` к
  подвешенному Docker Desktop висят вечно → движок навсегда «Запускается», процессы не умирают,
  пользователь перезапускает Setup — и процессы накапливаются. Тот же дефект у
  `Start-HrmElevatedAndWait` (`Common.psm1:568`, установщик Docker).
- **D2. Цикл запуска не единственный** (`hrm-tray.ps1:70` + `engine/Supervisor.psm1:409`): трей
  спавнит скрытый движок (`-Action supervise`/`resume`) **без проверки**, что такой цикл уже идёт, а
  `Invoke-HrmSupervisorCycle` **не захватывает** мьютекс единственности (его берёт только процесс
  трея, `hrm-tray.ps1:43`). Каждый вход в Windows (ярлык автозапуска) и каждый повторный запуск
  Setup.exe добавляет ещё один движок → параллельные `compose build/up` → перегрузка Docker/WSL.
- **D3. Блокировка действия «протухает» молча** (`Supervisor.psm1:148-181`, порог 60 минут на
  строке 166): зависший (но живой) процесс перестаёт блокировать новые операции → ещё один движок
  поверх зависших. Пользователь не получает честного «операция зависла».
- **D4. Трей долбит Docker каждые 5 секунд** (`Tray.psm1:378-419`): `$refresh` по таймеру
  (`Interval = 5000`) вызывает `Get-HrmTraySnapshot` → `Get-HrmStackState` → `docker compose ps` +
  два HTTP по 10 с; тики перекрываются, кэша нет, во время работы движка опрос не приостанавливается.
  На подвешенном Docker каждый тик — ещё один висящий `docker.exe` и ещё один дочерний процесс.
- **D5. Предполётная проверка `compose` падает без диагностики причины** (`Preflight.psm1:84-108`):
  `docker compose version --short` даёт ненулевой код — движок пишет «Плагин Docker Compose v2 не
  найден», но НЕ проверяет и не сообщает, где искал плагин. По документации docker/cli (#1534) на
  Windows плагины ищутся ТОЛЬКО в `%USERPROFILE%\.docker\cli-plugins` и
  `C:\ProgramData\Docker\cli-plugins` — **не рядом с `docker.exe`**; а второй путь удалён из поиска в
  docker CLI ≥ 29.2.0 (GHSA-p436-gjf2-799p, исправлено 04.03.2026). Отсюда реальный сценарий: `docker
  --version` и `docker info` зелёные, а `docker compose` падает — ровно наблюдаемый симптом
  («провал только compose»).
- **D6. Резолвер CLI может выбрать не тот `docker.exe`** (`Docker.psm1:164-176`):
  `Get-HrmDockerCliDirs` перебирает машинный `%ProgramFiles%\Docker\…` **раньше** пользовательского
  `%LOCALAPPDATA%\Programs\DockerDesktop\…`. При двух установках (устаревшая машинная + текущая
  пользовательская) движок возьмёт первую и не скажет, что нашлась вторая. Это не ломает поиск
  плагинов (он не привязан к пути CLI), но выбор неправильного CLI — источник расхождений версий.
- **D7. Установка умеет «полузавершаться» навсегда** (`Install.psm1:366` vs `405`/`432`): первая
  предполётная проверка идёт с `-SkipCompose`, запись установки (`installed.json`) пишется, и только
  потом `Assert-HrmPreflight` **с** проверкой compose (строка 405). Провал compose оставляет
  запись + разложенные файлы; каждый повторный запуск уходит в ветку «повторная установка»
  (строка 432) и падает на той же проверке — установка не может завершиться никогда, а tray-план
  (`Get-HrmTrayCurrentPlan`) показывает `normal`/`resuming` и вечное «Запускается». Разберись
  чтением, какая именно ветка даёт на экране `Состояние: Запускается` при уже записанной ошибке
  (состояние `starting` не должно нести текст провала предполётной проверки — это должна быть
  `error` с действием).
- **D8. Мёртвый код наблюдателя канала** (`Common.psm1:407`): `Start-HrmChannelWatcherProcess` не
  вызывается нигде; при этом `Start-HrmChannelWatch` (`Channel.psm1:328-355`) — `while ($true)` без
  точки выхода. Либо заведи вызов осмысленно, либо удали/задокументируй — но не оставляй «канал
  якно работает».
- **D9. `vmmemWSL` ≈ 1.8 GB**: оцени по фактам (Этап 1) — сколько контейнеров поднято, была ли
  параллельная сборка. Для WSL2-backend Docker Desktop порядок величины нормальный при поднятом
  пилотном стеке; **симптом** — рост при остановленных контейнерах или параллельных сборках (см. D2).
  Добавь факт в диагностику и опиши ожидаемый диапазон в README. Удаление пользовательской среды
  как «исправление» запрещено.

## Этап 3. Исправления (критерии приёмки — по каждому)

1. **Таймауты + отмена + чтение труб без deadlock (D1).** В `Invoke-HrmExternal`: асинхронное чтение
   stdout/stderr (не последовательное `ReadToEnd`), `WaitForExit(таймаут)` с параметром
   `-TimeoutSeconds` (разумные дефолты по типу команды; точные значения — в отчёте с обоснованием).
   По таймауту: убить **дерево** процессов (не только корень — иначе остаются `docker.exe`/`wsl`),
   вернуть структурированный результат (напр. `ExitCode = 124`, текст в `Stderr`) и/или бросить
   информативное исключение; записать в журнал. Убийство дерева — через мокабельную точку (внешняя
   команда с `/T /F` или аналог), с добавлением имени в белый список статики **с обоснованием**.
   `Start-HrmElevatedAndWait` — таймаут ожидания установщика. Существующие таймауты ожиданий
   (Engine 300 с, readiness 180 с и т.п.) НЕ увеличивать.
2. **Единственность цикла запуска (D2).** `Invoke-HrmSupervisorCycle` захватывает именованный мьютекс
   (`Get-HrmSupervisorMutexName`, переопределение `HRM_SUPERVISOR_MUTEX`) и при занятости возвращает
   честный результат «уже выполняется» вместо второго цикла. `hrm-tray.ps1` перед спавном движка
   проверяет признак идущей операции (action-lock с живым pid или `supervisor.json` c `busy=$true` и
   живым pid) и не спавнит дубль. Критерий: два входа подряд → один движковый цикл (считает мок
   запуска процессов).
3. **Блокировка действия не протухает (D3).** Пока процесс операции жив, новая операция не
   стартует; при долго висящем процессе — журнал + `supervisor.json` с понятным текстом
   («операция зависла, нужен перезапуск/отчёт для поддержки»), а не молчаливое разрешение второго
   процесса.
4. **Трей не перегружает Docker (D4).** Тик не перекрывает тик (признак «обновление идёт»); при
   идущей операции движка трей показывает сохранённое состояние без похода в docker; интервал опроса
   в установившемся состоянии больше, чем при старте; состояние error/ready не переопрашивается
   вхолостую. Критерий: в покое ≤ 4 обращения `docker compose ps` в минуту (или иное обоснованное
   число), тик не перекрывается.
5. **Compose-проверка с точным диагнозом (D5).** `Test-HrmComposeVersion` различает: CLI не
   запустился / плагин не найден / версия не разобрана / версия < 2.24. Для «плагин не найден» —
   сообщение с перечнем проверенных каталогов плагинов и действием (положить/обновить плагин;
   предупредить, что `C:\ProgramData\Docker\cli-plugins` не ищется docker CLI ≥ 29.2.0). Проверку
   **не ослаблять** (не превращать в warn). Диагностика (`Get-HrmComposeFacts`,
   `Get-HrmDockerFacts`, `Diagnostics.psm1:196-218`) дополнится фактами: разрешённый путь CLI, версия
   CLI, где искали плагин и что нашли, stderr пробы.
6. **Резолвер выбирает правильный CLI (D6).** Собирать всех кандидатов; выбирать тот, что
   соответствует работающему Docker Desktop (или единственный рабочий — `--version` исполняется);
   все найденные пути писать в журнал (пути + версии); правило выбора и порядок — в комментарии и в
   тесте. Критерий: при устаревшем машинном + актуальном пользовательском CLI выбирается актуальный,
   журнал упоминает оба.
7. **Установка не «полузавершается» (D7).** До записи `installed.json` проверять доступность compose
   и отказывать точным текстом (установка либо завершается, либо честно «не установлена» с
   работающим resume); ветка «повторная установка» при уже существующей записи должна либо чинить
   причину, либо давать точную инструкцию и `error`-состояние; показанное в трее состояние при
   провале — `Ошибка` с действием, не вечное «Запускается». Критерий: регрессия «плагина compose нет»
   → отказ ДО записи `installed.json`, повторный запуск после устранения причины проходит.
8. **Наблюдатель канала (D8).** Осмысленное решение + тест/документация; безусловный `while ($true)`
   не остаётся без точки выхода, если код достижим.
9. **vmmemWSL (D9).** Факт в диагностике + ожидаемый диапазон в README; подтверждение, что движок не
   создаёт параллельных compose-операций.

## Тесты (по соглашениям harness, поведенческие, без реальной машины)

- таймаут `Invoke-HrmExternal`: мок-процесс, который висит и/или пишет много в stderr → движок
  возвращает 124/бросает с текстом и НЕ висит; вызов убийства дерева зафиксирован моком;
- единственность supervise: два «процесса» (подход из `supervisor.tests.ps1`, см. коммит про
  Start-Job и mutex) → один цикл;
- трей не спавнит второй движок при идущей операции (мок запуска процессов считает вызовы);
- action-lock: живой зависший pid → новая операция отклонена с сообщением; мёртвый → блокировка снята;
- compose: плагин отсутствует → отказ `compose` с текстом про каталоги плагинов; установка не пишет
  `installed.json`; повторный запуск после появления плагина проходит;
- резолвер CLI: два кандидата → выбирается актуальный, в журнале оба;
- тик трея: не перекрывается; при идущей операции обращений к compose нет.
Старые 237 тестов должны проходить без правок «под новый баг»; существующие таймауты и поведение,
уже покрытые тестами, не меняются молча.
