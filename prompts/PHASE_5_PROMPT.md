# Промпт для AI-агента: события и календарь

Продолжи разработку HR Manager с этапа «События и календарь» из
`ROADMAP.md` (это этап 4 роадмапа; в нумерации промптов он идёт пятым,
после `prompts/PHASE_4_PROMPT.md`). Этап «Рабочий интерфейс HR» уже принят
в `main` merge-коммитом `649f6a606d6a89ba256ef4d899d821b84993b886`.

6. Сначала изучи код и доступные API, запусти baseline-проверки, затем кратко
   сообщи план и только после этого меняй файлы.

## Цель

Реализуй законченный контур событий и календаря на реальном backend API:

- события, связанные с кандидатом: звонки, собеседования и напоминания;
- исполнитель, срок, напоминание и история изменений;
- состояния «запланировано», «выполнено» и «отложено»;
- редактирование и перенос события;
- календарное представление и списки ближайших/просроченных событий;
- серверные права и фильтры по периоду, ответственному, кандидату, типу и
  состоянию;
- рабочий UX напоминаний в пределах реально поддерживаемой архитектуры.

Все production-экраны получают данные только из backend API. Не добавляй
демонстрационные переключатели, тестовые события или client-only операции,
которые исчезают после перезагрузки.

## Сначала зафиксируй контракт

До миграции и реализации добавь в отчёт или архитектурную документацию
краткие, однозначные определения:

- типов и состояний события и допустимых переходов между состояниями;
- семантики `from`/`to`, границ периода и часового пояса;
- просроченного события и ближайшего напоминания;
- видимости событий после soft delete кандидата;
- различия между событием и существующей записью взаимодействия;
- того, какая история изменения события нужна как бизнес-история, а что
  остаётся только security audit.

Не создавай второй источник правды для этапов кандидата или взаимодействий.
Значения API и БД должны быть стабильными enum-контрактами; русские подписи —
только представление во frontend.

## Backend: данные и миграция

Добавь отдельную сущность события через следующую Alembic-миграцию после
`0004_candidate_transfers`. Минимально событие должно поддерживать:

- `id`, `candidate_id`, автора и исполнителя;
- тип (`call`, `interview`, `reminder`);
- непустое краткое название и необязательную заметку;
- timezone-aware срок/начало и, если нужно типу, окончание;
- состояние (`scheduled`, `completed`, `postponed`);
- момент выполнения;
- дату создания и изменения.

Если для неизменяемой истории переносов/смен состояний нужна отдельная таблица,
добавь её. Не подменяй бизнес-историю audit log. Не добавляй типы или состояния
«на будущее» без требования этапа.

Требования к данным:

- PostgreSQL остаётся рабочей БД; схема меняется только через Alembic;
- внешние ключи, индексы и ограничения целостности заданы явно;
- валидируются пустые значения, порядок дат и согласованность состояния с
  `completed_at`;
- время хранится однозначно (предпочтительно UTC), API использует ISO 8601 с
  timezone, а UI отображает локальное время предсказуемо;
- миграция поддерживает upgrade, downgrade и повторный upgrade;
- физическое удаление событий обычным пользователем не добавляй.

## Backend API

Реализуй и документируй типизированные контракты:

### `GET /events`

Поддержи серверные параметры `from`, `to`, `owner_id`, `candidate_id`, `type`,
`status`, `limit`, `offset` и стабильную сортировку по времени и `id`.
Результат должен быть пагинированным и достаточным для календаря, ближайших и
просроченных событий без выгрузки всей базы.

### `POST /events`

Создаёт событие для доступного кандидата. Проверяет кандидата, тип, даты,
активность и допустимость исполнителя, обязательные поля и права назначения.

### `GET /events/{id}`

Возвращает событие только в зоне видимости текущего пользователя.

### `PATCH /events/{id}`

Поддерживает редактирование разрешённых полей, перенос, отметку «выполнено» и
«отложено». Переходы состояний валидируются сервером. При конкурентном
изменении нельзя молча затирать более новую версию: выбери минимальную
совместимую с проектом стратегию optimistic concurrency или блокировки,
реализуй её и задокументируй.

Для событий кандидата используй `GET /events?candidate_id=...`. Добавляй
`GET /candidates/{id}/events` только если это действительно упрощает текущую
архитектуру и не создаёт дублирующий контракт.

Не добавляй endpoint физического удаления. Если отмена действительно нужна,
она должна быть явным состоянием с историей, но не расширяй словарь без
обоснования в отчёте.

## Права доступа

- Неаутентифицированный пользователь получает `401`.
- HR видит, создаёт и изменяет события только доступных ему неудалённых
  кандидатов; чужие кандидат и событие скрываются принятой семантикой `404`.
- `manager` и `admin` видят события всех доступных кандидатов, фильтруют по HR
  и могут назначать активного исполнителя в пределах текущей модели ролей.
- Неактивного или неподходящего по роли пользователя нельзя назначить новым
  исполнителем.
- После передачи кандидата старый HR теряет доступ к его событиям, новый HR
  получает доступ; неизменяемая история при этом сохраняется.
- События soft-deleted кандидата не появляются в обычном календаре. Выбранную
  политику административного просмотра таких событий задокументируй и покрой
  тестами, не раскрывая данные обычному HR.
- Права проверяются backend на каждом запросе; скрытие кнопки — только UX.
- Мутирующие endpoint'ы используют текущую session/CSRF-защиту.

Не создавай новый общий permissions/scopes framework без отдельного
утверждённого контракта.

## Аудит и атомарность

Используй существующую систему аудита для создания, изменения, переноса,
завершения, откладывания и смены исполнителя. Audit details могут содержать
технические идентификаторы и безопасные названия изменённых полей, но не ФИО,
контакты, заголовок/текст заметки или иные PII.

Мутация события, запись обязательной бизнес-истории и audit event должны
фиксироваться одной транзакцией одним `commit`. Добавь regression-тест:
искусственный сбой записи audit должен полностью откатывать изменение события
и его бизнес-историю.

## Frontend

Добавь в существующую workspace-навигацию production-раздел календаря и
интеграцию событий в карточку кандидата. Реализуй:

- календарное desktop-представление с понятным выбранным периодом;
- ближайшие и просроченные события;
- серверные фильтры по периоду, типу, состоянию и HR для разрешённых ролей;
- переход из события в карточку кандидата;
- создание и редактирование события;
- перенос, выполнение и откладывание;
- loading, empty, error/retry и disabled/submitting states;
- обновление интерфейса только после подтверждённого успеха API либо
  корректный optimistic rollback;
- существующую обработку `401`/`403` и session flow.

Используй существующие design-system, toast/error patterns, тему и density.
Диалоги должны иметь labels, focus trap и возврат фокуса; календарные действия
должны иметь keyboard-альтернативу, фокус должен быть видимым, смысл не должен
передаваться только цветом, а motion должен учитывать `prefers-reduced-motion`.

Не копируй `design-prototype/` как production-код и не импортируй из него
`mockData`.

## Напоминания и уведомления

Сначала изучи текущую архитектуру. Если background worker/cron ещё отсутствует,
не имитируй email, push или browser delivery и не добавляй тяжёлую инфраструктуру
ради этапа. В этом случае реализуй хранение срока напоминания и серверную выдачу
ближайших/просроченных напоминаний в workspace, а внешнюю доставку явно укажи
как ограничение. API не должен блокироваться ожиданием фоновой задачи.

## Явные ограничения scope

Не реализуй в этом этапе:

- аналитику, KPI, конверсии и аналитический dashboard;
- экспорт аналитических отчётов;
- saved views;
- импорт/экспорт кандидатов;
- документы кандидата;
- контент, формы и шаблоны;
- backup/deployment-функции;
- интеграции с внешними площадками;
- микросервисную архитектуру;
- фиктивную доставку уведомлений.

Не ломай уже принятые auth/session/CSRF, роли, аудит, кандидатов, soft delete,
duplicate confirmation, атомарную передачу кандидата, health 200/503, lifespan
с `engine.dispose()`, Docker Compose, production hardening и CI.

## Обязательные требования

- Не записывай PII и приватные заметки в application/audit logs.
- Не добавляй реальные персональные данные, `.env`, дампы и секреты.
- Не добавляй новые библиотеки без необходимости; используй текущий стек.
- Обнови `README.md` (статус этапа, endpoint'ы, запуск UI, права и timezone) и
  `docs/ARCHITECTURE.md` (модель, миграция, API, транзакции и frontend-модуль).

## Тесты и критерии готовности

Добавь backend unit- и PostgreSQL integration-тесты для:

- создания, чтения, редактирования, переноса, выполнения и откладывания;
- фильтров по периоду/кандидату/HR/типу/состоянию, стабильной сортировки и
  пагинации;
- границ периода и timezone-aware дат;
- обязательных полей, некорректных дат и недопустимых переходов состояния;
- прав HR, manager, admin и ответа `401`;
- чужого, переданного и soft-deleted кандидата;
- несуществующего/неактивного/неподходящего исполнителя;
- бизнес-истории и audit без PII;
- полного rollback события и истории при ошибке audit;
- конкурентного изменения без потерянного обновления;
- Alembic upgrade, downgrade и повторного upgrade, реальных FK/CHECK/index.

Добавь frontend unit/component/integration-тесты с React Testing Library и
Vitest для:

- loading, empty, error/retry и данных;
- передачи фильтров, периода и пагинации именно в API;
- создания, редактирования, переноса, выполнения и откладывания;
- валидации, серверной ошибки и отсутствия ложного успеха;
- ролевой видимости фильтров/действий и обработки `401`/`403`;
- перехода в карточку кандидата и событий внутри карточки;
- keyboard-альтернатив, labels, focus trap и возврата фокуса.

Используй моки API только в тестах. Если Playwright отсутствует, не добавляй
его только ради этого этапа.

В конце обязательно запусти все доступные backend/frontend lint, format,
typecheck, unit/integration tests, production build, Alembic-проверки, Docker
Compose config/smoke и `npm audit`, если он уже входит в проект. Все GitHub
Actions jobs должны пройти. Не утверждай, что проверка выполнена, если она не
запускалась; отдельно укажи невозможные проверки и причину.

Проверь `git diff --check`, статус и содержимое всех изменённых файлов. Не
оставляй TODO, `pass`, заглушки или фиктивные ответы в принятом scope.
