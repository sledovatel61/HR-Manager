# Промпт для AI-агента: рабочий интерфейс HR

Продолжи разработку HR Manager с этапа «Рабочий интерфейс HR» из
`ROADMAP.md` (это этап 3 роадмапа; в нумерации промптов он идёт четвёртым,
после `prompts/PHASE_3_PROMPT.md`). Этап «Единая база кандидатов» уже принят
в `main` merge-коммитом `19caa3df211a431455052df7a825b5099921984a`.

## Перед началом

1. Прочитай `agents.md`, `PRODUCT_SPEC.md`, `ROADMAP.md`, `README.md`,
   `docs/ARCHITECTURE.md` и `docs/phase-3-report-agent2.md`.
2. Изучи существующие backend-контракты кандидатов, frontend-типы и API-клиент.
   Не ломай принятые контракты и единый словарь этапов.
3. Изучи дизайн-трек: `design/IMPLEMENTATION_GUIDE.md`,
   `design/DESIGN_SYSTEM.md`, `design/PERSONAS_AND_FLOWS.md`,
   `design/ACCESSIBILITY.md`, `design/REVIEW_CHECKLIST.md` и
   `design-prototype/`. Прототип — UX/визуальный ориентир, а не production-код
   для слепого копирования: в production запрещены `mockData` и фиктивные
   успешные операции.
4. Начни строго от актуального `origin/main` (он должен включать merge-коммит
   выше) и создай отдельную ветку `arena/phase-4-hr-workspace`.
5. Не выполняй merge в `main`.
6. Сначала изучи код, текущие тесты и доступные API, запусти baseline-проверки,
   затем кратко сообщи план и только после этого меняй файлы.

## Цель

Реализуй законченный рабочий интерфейс ведения кандидатов на реальном API:

- application shell для авторизованного пользователя;
- личную очередь HR и доступный роли общий список кандидатов;
- табличное и Kanban-представления;
- создание, просмотр и редактирование карточки кандидата;
- смену этапа и добавление записей в историю взаимодействий;
- серверные поиск, фильтры, сортировку и пагинацию;
- soft delete, отдельное представление удалённых кандидатов и восстановление;
- UX подтверждения дубля при создании/изменении;
- безопасную передачу кандидата другому HR с обязательным подтверждением,
  причиной и неизменяемой историей операции.

Все production-экраны получают данные только из backend API. Не добавляй
демонстрационные переключатели, тестовых кандидатов или client-only операции,
которые исчезают после перезагрузки.

## Backend: передача ответственности

Добавь недостающий контракт этапа:

`POST /candidates/{id}/transfer`

Тело запроса:

```json
{
  "new_owner_user_id": "uuid",
  "reason": "непустая причина"
}
```

Операция должна:

- выполняться в одной транзакции и блокировать изменяемую строку кандидата от
  конкурентной передачи;
- проверять существование и активность нового ответственного; ответственным
  может быть только активный пользователь роли `hr`;
- отклонять передачу тому же владельцу и пустую/состоящую из пробелов причину;
- разрешать HR передавать только собственного неудалённого кандидата;
  `manager`/`admin` могут передавать любого доступного неудалённого кандидата;
- для чужого/недоступного кандидата сохранять принятую семантику `404`, чтобы
  не раскрывать его существование;
- атомарно менять `owner_user_id`, сохранять инициатора, старого и нового
  ответственного, причину и время в отдельной неизменяемой истории передач,
  а также создавать существующую audit-запись без PII и текста причины;
- возвращать типизированный результат, достаточный для немедленного обновления
  UI без повторного полного запроса.

Добавь пагинируемый `GET /candidates/{id}/transfers` для истории передач с теми
же правилами видимости, что у карточки кандидата. После передачи прежний HR
больше не должен читать карточку/историю через прямой URL. Новый владелец,
руководитель и администратор видят актуальные данные.

Оформи изменение схемы следующей Alembic-миграцией после
`0003_candidates.py`. Не пытайся хранить историю только в audit log или только
в frontend-состоянии: audit log не является бизнес-историей кандидата.

## Frontend: обязательные экраны и сценарии

### 1. Shell и навигация

- Перенеси semantic tokens и необходимые общие примитивы из дизайн-прототипа
  в production-структуру, рекомендованную `design/IMPLEMENTATION_GUIDE.md`.
- Реализуй доступные разделы «Моя очередь», «Кандидаты» и «Kanban», сведения о
  текущем пользователе и рабочий выход из системы.
- Не показывай ссылки на календарь, аналитику и шаблоны как якобы работающие.
- Не ломай восстановление/истечение сессии. Ответы API `401` должны приводить
  к понятному возврату на вход, `403` — к состоянию недостаточных прав.

### 2. Таблица и очередь

- Покажи ФИО, должность, этап, источник, ответственного и дату обновления.
- Используй существующий `GET /candidates` с серверными `query`, `stage`,
  `source`, `owner_id`, `sort`, `direction`, `limit`, `offset`.
- Поиск должен быть debounce-safe и устойчив к ответам, пришедшим не по
  порядку; фильтры/сортировка/страница сохраняются при открытии и закрытии
  карточки.
- Реализуй loading/skeleton, empty, error+retry и permission-denied states.
- HR видит свою очередь в рамках существующего серверного RBAC. Общий список
  всех владельцев и фильтр по ответственному доступны только `manager` и
  `admin`; frontend не должен ослаблять или имитировать серверные права.
- Для выбора ответственного используй реальный доступный API пользователей;
  не загружай секретные или административные поля и не создавай mock-список.

### 3. Kanban

- Колонки строго соответствуют `CANDIDATE_STAGE_ORDER` и `STAGE_LABELS` из
  `frontend/src/types.ts`, включая этап `started` («Вышел»).
- Данные загружаются постранично с сервера; не считай один частичный ответ
  полным Kanban. Выбери и задокументируй ограниченную стратегию загрузки
  (например, пагинация внутри колонок), не запрашивая бесконтрольно всю базу.
- Смена этапа вызывает реальный `PATCH /candidates/{id}`. Допустим optimistic
  UI только с блокировкой повторного действия, серверным подтверждением и
  обязательным rollback при ошибке.
- Drag-and-drop не должен быть единственным способом: добавь доступную
  keyboard-альтернативу через контрол выбора этапа. Не добавляй библиотеку DnD,
  если сценарий надёжно реализуется текущим стеком.

### 4. Карточка кандидата

- Открывай карточку из таблицы и Kanban как доступный drawer/page с корректным
  управлением фокусом и возвратом фокуса после закрытия.
- Покажи и позволь редактировать только поля реального API; добавь явную
  клиентскую валидацию, состояния сохранения и серверные ошибки.
- История взаимодействий загружается из API с пагинацией. Новая запись после
  успешного `POST` появляется в истории без перезагрузки страницы.
- Историю передач покажи вместе с активностью кандидата или отдельной вкладкой,
  не теряя автора, старого/нового ответственного, причины и времени.
- Передача — двухшаговый сценарий: выбор нового HR + обязательная причина,
  затем отдельное подтверждение с именами старого и нового ответственного.
- После успешной передачи собственного кандидата HR закрой недоступную ему
  карточку, обнови очередь и покажи подтверждение. При конфликте/ошибке данные
  не должны визуально считаться переданными.

### 5. Создание, дубли и удаление

- Реализуй форму создания кандидата и UX для `DuplicateCandidateError`:
  покажи найденные совпадения, предложи открыть доступное совпадение либо явно
  подтвердить повторную отправку с `confirm_duplicate: true`.
- Тот же безопасный сценарий нужен при редактировании контактов.
- Soft delete требует подтверждения. Удалённые не остаются в обычной очереди.
- Добавь отдельное представление удалённых с серверным
  `include_deleted=true`, пагинацией и восстановлением. Не добавляй физическое
  удаление.

## Доступность и качество UX

- Соблюдай `design/ACCESSIBILITY.md`: семантическая разметка, видимый focus,
  labels, keyboard navigation, focus trap/restore для modal/drawer,
  `aria-live` для результата действий и `prefers-reduced-motion`.
- Цвет не должен быть единственным признаком этапа/ошибки; мобильное приложение
  не требуется, но интерфейс должен оставаться рабочим на контрольных ширинах
  из дизайн-системы и при горизонтальном скролле таблицы.
- Не смешивай разные наборы иконок и не создавай одноразовые копии общих UI-
  примитивов внутри feature-компонентов.
- Не добавляй новые runtime-зависимости без явной необходимости и обоснования
  в отчёте. React Router или библиотека state management не обязательны:
  сначала оцени текущий небольшой стек.

## Явные ограничения scope

Не реализуй в этом этапе:

- события, напоминания и календарь;
- аналитику, KPI и экспорт отчётов;
- saved views;
- импорт/экспорт кандидатов;
- документы кандидата;
- контент, формы и шаблоны;
- backup/deployment-функции;
- интеграции с внешними площадками;
- новый общий механизм permissions/scopes или расширение видимости HR на
  чужих кандидатов без отдельного утверждённого контракта.

Глобальный Command Palette можно реализовать только как навигацию по реально
доступным разделам. Не дублируй в нём базу кандидатов и не делай mock-поиск.

## Обязательные требования

- PostgreSQL остаётся рабочей БД; схема меняется только через Alembic.
- Мутирующие endpoint'ы используют текущую session/CSRF-защиту.
- Права проверяются backend на каждом запросе; скрытие кнопки — только UX.
- Не записывай ФИО, контакты и причину передачи в application/audit logs.
- Не добавляй реальные персональные данные, `.env`, дампы и секреты.
- Не ломай health 200/503, lifespan с `engine.dispose()`, Docker Compose,
  production hardening и существующий CI.
- Обнови `README.md` (статус этапа, запуск UI, endpoint'ы) и
  `docs/ARCHITECTURE.md` (frontend-структура и контракт передачи).

## Тесты и критерии готовности

Добавь backend unit- и PostgreSQL integration-тесты для:

- успешной передачи HR собственного кандидата и передачи manager/admin;
- запрета HR передавать чужого кандидата с ответом `404`;
- несуществующего/неактивного/не-HR нового владельца, того же владельца и
  пустой причины;
- запрета передачи удалённого кандидата;
- атомарного изменения владельца, записи полной бизнес-истории и audit event;
- отсутствия PII/причины в audit details;
- конкурентной передачи без потерянной или противоречивой истории;
- пагинации и прав чтения истории передач;
- Alembic upgrade, downgrade и повторного upgrade.

Добавь frontend unit/component/integration-тесты с React Testing Library и
Vitest для:

- session loading/login/logout и обработки `401`/`403`;
- таблицы: loading, empty, error/retry, данные, поиск, фильтры, сортировка и
  пагинация именно через параметры API;
- ролевой видимости очереди/общего списка и действий;
- открытия/редактирования карточки, смены этапа и rollback при ошибке;
- загрузки и добавления взаимодействия;
- Kanban и keyboard-альтернативы смены этапа;
- двухшаговой передачи, обязательной причины, успеха и серверной ошибки;
- создания/редактирования с duplicate-confirmation flow;
- soft delete, списка удалённых и восстановления;
- базовой доступности диалогов: labels, focus trap и возврат фокуса.

Используй моки API только в тестах. Если в текущем проекте нет Playwright, не
добавляй его только ради этого этапа; критические пользовательские сценарии
покрой имеющимся стеком React Testing Library/Vitest.

В конце обязательно запусти все доступные backend/frontend lint, format,
typecheck, unit/integration tests, production build, Alembic-проверки и Docker
Compose smoke. Все GitHub Actions jobs должны пройти. Не утверждай, что
проверка выполнена, если она не запускалась; отдельно укажи проверки, которые
невозможно было выполнить, и причину.
