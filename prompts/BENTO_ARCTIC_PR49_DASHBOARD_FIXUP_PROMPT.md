# P1. Тест падает. Прямо сейчас. У меня, на чистом дереве.

## Воспроизведение

```bash
cd /home/user/r8 && git checkout 4d6edd2456cf20c48ebb9ed3532a52d881d597d4
cd backend && APP_ENV=test python -m pytest -q -m "not integration"
```

**Фактически:**

```
FAILED tests/test_queue_dashboard.py::test_all_period_is_bucketed_by_months
1 failed, 1166 passed, 146 deselected, 47 warnings in 307.99s
```

**Заявлено в теле PR:** «**1167 passed**, 146 deselected».

## Почему

`backend/tests/test_queue_dashboard.py:448`:

```python
assert len(payload["created_candidates_series"]) == 15  # 400 дней ≈ 14 месяцев + текущий
```

Арифметика в комментарии неверная: 400 дней ≈ **13,15** месяца. От `now − 400 дней` до `now`
укладывается 13 или 14 месяцев, то есть бакетов **14 или 15**, и сколько именно — зависит
от сегодняшней даты.

Пересчёт:

```
now = 2026-10-01 .. 2026-10-05  → 15 бакетов → тест проходит
now = 2026-10-06 .. 2026-10-15  → 14 бакетов → ТЕСТ ПАДАЕТ
```

CI прогнался **2026-10-05T14:07:57Z** — последний удачный день. Сегодня 2026-10-06, и тест
красный. Зелёный CI — не доказательство: он доказал, что в тот день календарь сходился.

Это не флак-ошибка, это **латентная мина с таймером на дату**, и она уже сработала.

## Ожидалось

Тест не должен зависеть от настенных часов. Один из вариантов:

1. Считать ожидание той же арифметикой, что и production-код (месяцы между границами
   окна + 1), а не константой;
2. Заморозить время в тесте (`_now()` подменить фиксированной датой), тогда `15`
   становится корректной константой;
3. Пересобрать сценарий так, чтобы 400 дней не пересаживались через границу месяца
   (например, `timedelta(days=365)` с заморозкой, или явно задать `created_at` в
   пределах известных месяцев).

Пункт 2 предпочтительнее: он же лечит все соседние тесты, где `_now()` гуляет.

## Приёмка

`pytest -m "not integration"` даёт **0 failed** — и это должно быть воспроизводимо при
любой сегодняшней дате, а не только при той, что была у тебя в песочнице.

# P2. Три «провала AA» не существуют. Один из них вкоммичен в CSS как обоснование.

## В чём дело

Режим `--pair` кладёт первый аргумент **слоем состояния** поверх базовой поверхности.
`print_pair` (`scripts/measure-contrast.py:756`):

```python
for base_name in BASE_SURFACES:
    ...
    background = over(resolve(tokens[base_name], tokens), backdrop)
    if surface:
        background = over(resolve(tokens[surface], tokens), background)
```

`--surface-raised` — это **базовая** поверхность (`BASE_SURFACES`, `scripts/measure-contrast.py:50`),
а не состояние. Передав её в `--pair`, вы накладываете её дважды: один раз как базу, второй
раз как «состояние». Фон получается плотнее, чем в реальности, и контраст падает.

Доказательство (мой расчёт, вашими же примитивами):

```
фон правильно (raised как базовая): rgb(86,173,215) -> --text-tertiary 5.38:1
фон в --pair  (raised дважды):      rgb(137,216,254) -> --text-tertiary 4.13:1
```

## Что заявлено против что есть

| Пара | Заявлено в PR и в CSS | Факт (`--pair - <текст>`) |
| --- | --- | --- |
| `--surface-raised` + `--text-secondary` | **4,31:1 — провал** | **5,61:1 — ок** |
| `--surface-raised` + `--text-tertiary` | **4,13:1 — провал** | **5,38:1 — ок** |
| `--surface-raised` + `--accent-default` | **3,72:1 — провал** | **4,84:1 — ок** |
| `--surface-raised` + `--cat-warning-1` | **4,95:1 / 3,71:1 — провал в тёмной** | **4,55:1 / 4,82:1 — оба ок** |

Воспроизведение:

```bash
python3 scripts/measure-contrast.py --pair --surface-raised --text-tertiary   # 4.13:1 ПРОВАЛ  (артефакт)
python3 scripts/measure-contrast.py --pair - --text-tertiary                  # 5.38:1 ок      (правда)
python3 scripts/measure-contrast.py --pair - --cat-warning-1                  # 4.55 / 4.82 — оба ок
```

Гейт при этом прав: он мерит `state_name is None` как базовую поверхность без состояния и
даёт худшую тёмную пару 4,83:1 — ровно тот же порядок, что и мои 4,84:1. Расходитесь вы с
гейтом, а не гейт с вами.

## Хуже всего: ложный замер вкоммичен в исходник

`frontend/src/features/queue/queue.css:329-336`:

```css
/* Правая ось подписана тем же цветом, что и левая.
   Почему не цветом второго ряда (--cat-warning-1): замер
   `python3 scripts/measure-contrast.py --pair --surface-raised --cat-warning-1`
   даёт 4,95:1 в светлой теме и 3,71:1 в тёмной — ниже AA 4.5:1 для текста.
   Ряд различают форма маркера, тип линии и подпись в легенде, а не цвет
   подписей оси. */
```

Число 3,71:1 — артефакт инструмента. Правильное значение 4,82:1, то есть **проходит AA**.
Решение (подписывать правую ось `--text-tertiary`, различать ряды формой и типом линии)
само по себе грамотное и доступное — но записанное обоснование ложно, и оно теперь лежит
в репозитории навсегда. Следующий, кто пересчитает, получит другое число и решит, что
кто-то врёт.

Справедливости ради: 4,55:1 в светлой теме — впритык к порогу. Если после честного замера
решите не использовать `--cat-warning-1` для подписей — это нормальное решение, но
обоснуйте его настоящими цифрами.

## Ожидалось

1. **Починить `--pair`, чтобы им нельзя было воспользоваться вот так.** Либо отвергать
   первый аргумент, если он не из `STATE_SURFACES` (понятная ошибка вместо молчаливого
   двойного наложения), либо трактовать токен из `BASE_SURFACES` как базу и мерить только
   на ней. Первое надёжнее.
2. **Починить usage-строку.** Сейчас
   `usage: measure-contrast.py --pair <фон-состояния|--text-token> <текст>` —
   невнятица: непонятно, что первый аргумент обязан быть именно *состоянием*.
   Должно быть явно: `<состояние|->`, где `-` = без состояния.
3. **Переписать комментарий в `queue.css:329-336`** настоящими числами и настоящей
   причиной.
4. **Переписать абзац в теле PR** («Найдено попутно, не исправлено…») — либо убрать
   несуществующие провалы, либо, если посчитаете, что показатели стоит поправить,
   предъявить честные цифры.
5. **Добавить тест на сам режим `--pair`**: вызов с токеном из `BASE_SURFACES` должен
   либо падать с внятной ошибкой, либо давать тот же результат, что и `--pair - <текст>`.
   Иначе следующий агент повторит ту же ошибку — интерфейс снова её позволит.

Заодно: `print_pair` делает `return 0` всегда. Если в выводе напечатано «ПРОВАЛ AA», а код
выхода 0 — этот провал нельзя поймать ни скриптом, ни CI. Подумайте, не должен ли `--pair`
возвращать 1 при провале.
