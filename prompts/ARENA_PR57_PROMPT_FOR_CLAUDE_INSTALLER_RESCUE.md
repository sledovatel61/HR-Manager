`SetStep(ssPostInstall, True)` — это документированное поведение, см.StackOverflow 29841276
с цитатой исходного кода Inno и 14358614 «which actually occurs after the [Run] entries»).

Мастер в `installer/installer.iss` писал оба файла в ветке `ssPostInstall`:

```pascal
if CurStep = ssPostInstall then
begin
  WriteFirstRunInput();   // пишет %LOCALAPPDATA%\HRManager\first-run-input.json
  WriteSetupMarker();     // пишет %LOCALAPPDATA%\HRManager\setup-run.json status=running
end;
```

Следствия, оба видны в журнале:

1. **Фамилия терялась.** Движок из `[Run]` вызвал `Get-HrmFirstRunInput`

   в `19:36:08.823`. Файла не было → молчаливый переход к `Invoke-HrmPrompt` →

   содержит правильную `"Перепечай"` — поэтому все прежние проверки «файл верный»
   дефект не находили.

2. **Код 10 при рабочем приложении.** Движок на успехе удаляет `setup-run.json`
   (`hr-manager.ps1:320-325`, `Clear-HrmSetupMarker`). Но `WriteSetupMarker()` в

## 1. Что это за продукт и как он устроен

HR Manager — веб-приложение для HR (кандидаты, вакансии, документы, аналитика).

- **backend/** — FastAPI + SQLAlchemy, PostgreSQL.
- **frontend/** — React + TypeScript + Vite.
- **infra/windows/** — движок на PowerShell 5.1: `hr-manager.ps1` (точка входа) +
  модули `engine/*.psm1` + `hrm-tray.ps1` (значок в трее).
- **installer/installer.iss** — Inno Setup 6, собирает `HR-Manager-Setup-<version>.exe`.
- **infra/compose.pilot.yml** — пилотный стек Docker: `db` (Postgres), `backend`,
  `frontend`, `worker`, `backup`, `mailpit`.

### Порты

| Порт | Что | Правило |
|---|---|---|
| 8080 | **production**, стек `hr-manager` | **НЕ ТРОГАТЬ. Никогда.** |
| 8081 | пилот/приёмка, стек `hr-manager-pilot` | здесь всё тестируем |
| 18001 | claim-порт первого запуска (loopback) | |
| 18002 | trust-порт (страница регистрации, loopback) | |

Если 8080 занят, движок сам выбирает свободный порт (в журнале: `19:35:16 Порт 8080
занят другим приложением... 8081`).

### Целевой сценарий первого запуска

1. Пользователь запускает `HR-Manager-Setup-0.15.0.exe`, выбирает каталог (`/DIR=`).
2. Мастер спрашивает **фамилию владельца** (страница `SurnamePage`), часовой пояс.
3. Мастер копирует файлы, затем в `[Run]` запускает `hr-manager.ps1 -Action install
   -NonInteractive -OpenBrowser`.
4. Движок поднимает Docker-стек, генерирует 64-символьный hex-токен обмена,
   делает `POST /setup/owner/claim` на loopback с `X-Real-IP: 127.0.0.1`,
   получает одноразовый тикет и **сам открывает браузер** на
   `http://127.0.0.1:18002/#setup=<ticket>`.
5. Фронтенд читает тикет **только из фрагмента URL** (`frontend/src/App.tsx:30`),
   показывает форму первого запуска: фамилия (только чтение, из превью тикета),
   пароль ×2, часовой пояс, рабочие дни, тихие часы.
6. Бэкенд создаёт единственного владельца (роль admin + грант `pilot_full_access`).
7. Мастер должен вернуть **код 0** и показать страницу «Готово».

### Сроки жизни (критично для приёмки)

`backend/app/config.py:239-241`:
- `pilot_exchange_ttl_minutes = 60` — токен обмена;
- `pilot_ticket_ttl_minutes = 15` — **тикет после открытия страницы**.

После открытия страницы регистрации учётную запись нужно создать в пределах
**15 минут**, иначе тикет истекает и установку надо перезапускать.

### Лицензия

Без загруженного `.hrmlicense` бэкенд отвечает **403 `no_license`**
(`backend/app/license_guard.py`). Это ожидаемо до загрузки ключа. Но интерфейс
не должен называть это «Backend недоступен» или «Недостаточно прав» — это отдельный
открытый дефект UX, виден на скриншотах 21.10. Публичный ключ сервера
(`infra/license/public_key.b64`) лицензию не заменяет.

## 2. Критерии приёмки (формулировка заказчика, дословно по смыслу)

**Успех = полный путь:** Setup.exe → автоматическое открытие регистрации →
создание учётной записи → лицензия → повторный вход.

Шесть проверок чистой приёмки:

1. `Setup.exe` возвращает **код 0**.
2. Регистрация открывается **автоматически**, без ручного «Открыть».
3. Показывается **форма регистрации**, а не сразу ввод логина/пароля.
4. Фамилия в форме — **«Перепечай»** (кириллица, не `Owner`).
5. Учётная запись создаётся и первый вход проходит с первого раза.
6. Повторный запуск сохраняет учётку на порту 8081.

Дополнительно: production 8080 не изменён (HTTP 200, контейнеры те же).

**Зелёного CI недостаточно.** Оба дефекта уже подтверждались живьём при зелёных
тестах. Любая правка проверяется только реальной установкой.

  (`prompts/`, `google_drive/`, `design-review/`).
- **`gh run download`, `gh run view --log`, `gh api …/logs` проваливаются** (EOF/403).
  Рабочий способ увидеть отказ CI: `gh api repos/sledovatel61/HR-Manager/check-runs/<id>/annotations`.
- **Запуск workflow из песочницы → HTTP 403.** Кнопку нажимает человек.
- **Второй установочный каталог:** Inno хранит прошлый каталог в
  `HKCU\...\Uninstall\...\InstallLocation`. Чтобы получить чистую установку в новом
  каталоге, надо удалить запись деинсталлятора, а не надеяться на `/DIR`.
- **Сброс только тома Postgres недостаточен** для первичной установки: при наличии
  `release_sha` в `installed.json` движок уходит в ветку обновления
  (`Install.psm1:61-78`) и окно регистрации не вернётся. Нужно убрать **каталог
  состояния** `%LOCALAPPDATA%\HRManager`.
- **Штатный purge движка** (`hr-manager.ps1 -Action uninstall -PurgeData -NonInteractive`
  + `$env:HRM_PURGE_CONFIRMATION='УДАЛИТЬ ДАННЫЕ HR MANAGER'`) удаляет только том
  `hr-manager-pilot_pilot_pgdata`; каталог состояния движок оставляет намеренно
  (`Install.psm1:231-232`) — для первичной приёмки убрать вручную.
- **Отсутствие `setup-run.json` при успешном движке — НЕ провал.** Маркер удаляется

- **`Invoke-HrmPrompt` в неинтерактивном режиме молча возвращает пустую строку.**
  Это и есть механизм тихой подстановки `Owner`. Любой новый молчаливый fallback в

- **`[Run]` не умеет получать код возврата.** Схема `setup-run.json` +

- **Backend-тесты Linux-only:** `backend/app/backup_runner.py:26` — безусловный
  `import fcntl`.
- **`config.py:529-533`:** SQLite разрешён ТОЛЬКО для изолированных юнит-тестов

- **Стиль кода в `[Code]` installer.iss** — комментарии `//` с ASCII-пунктуацией.

### Вариант B — переписать установщик с нуля, отдельным PR, новым агентом

Если A не прошёл. Требования заказчика:
- Обязательно **указание каталога установки** (мастер спрашивает куда ставить).
- Обязательно **активация лицензии** в составе сценария.
- Новый PR, не трогать `fix/first-run-claim-6ae189a`.
- Существующие успешные сценарии не ломать.

### Вариант C — портативный пилот с флешки, без Docker

Требование заказчика: все библиотеки и данные на флешке, полноценная работа с неё.
**Лицензия в этом варианте не нужна** — доступ у одного человека, компания
приложение бесплатно не получит.

Что нужно решить (это не тривиально, учитывай при оценке):
- `config.py:529-533` запрещает SQLite вне тестов — нужен либо встроенный
  PostgreSQL, либо осознанное разрешение портативного режима.
- `backend/app/backup_runner.py:26` — безусловный `import fcntl` (Linux-only),
  на Windows не импортируется.
- Состав стека `db/backend/frontend/worker/backup/mailpit` надо сократить до
  одного пользователя: `worker`, `backup`, `mailpit` — кандидаты на отключение.
- Фронтенд — статическая сборка, раздаётся локально.
- Два loopback-порта (18001 claim, 18002 trust) и фрагмент `#setup=<ticket>` должны
  сохраниться, иначе сломается механизм первого запуска.

## 8. Жёсткие ограничения

- **НЕ мержить и НЕ релизить.** PR остаётся draft / NO-GO до приёмки.
- **Production на порту 8080 неприкосновенен.** Любая работа с томами, `down -v`,
  purge — **только** на приёмочном стеке `hr-manager-pilot` и **только** штатной
  командой движка.
- **Пароль только через stdin**, никогда в аргументах командной строки и не в файлы.
- **Маркер состояния честный.** Не показывать успех без подтверждённой готовности
  движка; при отказе — ненулевой код и `setup-run.json` со статусом `failed`.
- **Секреты не печатать.** `secrets.json`, `pilot.env`, дамп БД — не в архив, не в
  репозиторий, не в чат.
- **Журналы и evidence — в bundle**, но **не коммитить** в репозиторий.
- **PII-значения не включать в файлы репозитория.**
- **Историю не переписывать.**
- **Не возвращать хардкод `X-Real-IP: 127.0.0.1` в общий слушатель nginx**
  (`frontend/nginx.conf:33` затирает заголовок движка → 404 на claim).
- **Не ломать существующие успешные сценарии.** 355 тестов должны продолжать проходить.
- **Проверка обязательна на Windows PowerShell 5.1**, не только на pwsh 7.

Заказчик — не программист, он связующее звено между агентами и устал от кругов.
Требования:

  живым прогоном.
