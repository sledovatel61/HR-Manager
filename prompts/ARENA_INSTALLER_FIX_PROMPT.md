# Задача: исправить Windows-установку HR Manager и подготовить PR для независимого ревью

Ты — агент-разработчик HR Manager. Разбери и исправь проблемы установщика Windows, запуска Docker Desktop, обновления и открытия приложения. Работай в отдельной ветке и PR. Дополнительный агент-ревьюер проверит твой PR.

## Рабочий процесс

1. Прочитай `agents.md` / `AGENTS.md`, актуальные handoff, release runbook и правила репозитория. Проверь актуальный `origin/main`, зафиксируй исходный SHA. Локальный checkout для диагностики назывался `HR-Manager-main-pr53`; это не основание начинать работу от устаревшей ветки.
2. Создай отдельную ветку. После первичного анализа и первого содержательного коммита открой draft PR. Продолжай работу и отправляй исправления в эту же ветку и PR. В описании PR перечисли выявленные причины, план и недостающие проверки.
3. Доведи изменения до проверяемого результата, выполни доступные проверки, обнови описание PR под окончательное решение. Отметь PR готовым к ревью после завершения работы. Передай ссылку, точный head SHA и отчёт о проверках.
4. Не выполняй merge. Не включай посторонние изменения. Не перезаписывай существующие локальные правки: диагностические изменения `installer/Test-Setup.cmd`, `installer/Test-Setup.ps1`, `infra/windows/hr-manager.ps1` уже были в локальном checkout; проверь, присутствуют ли они в актуальном main, и перенеси только необходимые изменения осознанно.

## Пользовательский сценарий и доказательства

Открылось приложение со старыми данными; страница лицензии сообщила «Проверка лицензии отключена (dev/test)» и «Лицензия не установлена».

## Что известно о коде, а что ещё нужно доказать

- В `Invoke-HrmDockerPrepare` установка Docker вызывается только при `not_installed`. `-InstallDocker` разрешает установку отсутствующего Docker; он не означает принудительную переустановку имеющегося. Не добавляй принудительную переустановку как способ исправить запуск.
- `Get-HrmDockerDesktopPath` проверяет реестр и стандартные каталоги. В исследованной версии среди стандартных кандидатов отсутствовал `%LOCALAPPDATA%\Programs\DockerDesktop`. Реестр также может дать правильный путь, поэтому отсутствие кандидата — зацепка, а не доказанная единственная причина таймаута.
- Пилотный Compose задаёт `APP_ENV=pilot` и требует публичный ключ лицензии. Надпись dev/test в браузере согласуется с открытием старого development-стека на 8080, а не доказывает отключение лицензирования в пилоте.
- Ошибка `0022` доказывает отсутствие доступной Alembic-ревизии при запуске конкретного контейнера. Нужно установить, почему образ и база рассогласованы: старый образ, откат, неполная сборка/упаковка или другая причина. Не подменяй расследование догадкой.

## Обязательные направления исправления

### 1. Docker Desktop: обнаружение, запуск и диагностика

- Проверь пользовательскую и системную установку Docker, EXE/CLI, реестр, PATH и Docker context. Исправь подтверждённые ошибки обнаружения и запуска, включая актуальный пользовательский каталог, если проблема сохраняется в main.
- Различай Docker отсутствует, установлен/остановлен, процесс запущен/Engine не готов, Engine готов и неверный тип контейнеров.
- Сохрани ограниченное ожидание и понятные сообщения. Ошибка запуска EXE не должна превращаться в неинформативный 300-секундный таймаут.
- Записывай в постоянный лог выбранный путь, факт и результат запуска, PID при наличии, этап ожидания и редактированную причину неготовности Engine. Не записывай секреты и полное окружение.
- Проверь установку отсутствующего Docker через официальный установщик, обработку UAC/отказа/перезагрузки и продолжение установки. Не принимай лицензию Docker за пользователя.
- Уточни текст галочки и пояснений: установка, если Docker отсутствует; использование и запуск имеющегося Docker, если он установлен. Согласуй устаревшие комментарии и документацию с фактическим поведением.

### 2. Единственность операций и постоянные логи

- Проверь порядок Inno Setup → install/update → tray/supervisor, блокировки, владение setup marker и повторный клик по ярлыку. Исключи параллельные конфликтующие операции и бесконечное создание дочерних PowerShell.
- Несколько процессов с разными ролями могут быть штатными. Докажи дефект или отсутствие дефекта по действиям и дереву процессов; не делай вывод только по количеству окон.
- Проверь `HRM_LOG_FILE`, его сохранение/восстановление при запуске дочерних процессов, взаимодействие записи журнала с RedirectStandardOutput, кодировки Windows PowerShell 5.1, коды завершения и свежесть JSON-состояний.
- Диагностический запуск должен различать завершение мастера и завершение фоновой операции, если они разнесены во времени. Не объявляй установку приложения успешной только по коду Inno Setup.

### 3. Нужное приложение на нужном порту

- Проверь занятый 8080 и наличие другого HR Manager/dev-стека. Ярлык, readiness и первый запуск должны подтверждать принадлежность ответа целевому пилоту и ожидаемому релизу, используя существующие механизмы идентификации или обоснованное минимальное расширение.
- Чужой HTTP 200/health не должен считаться успешным запуском пилота. Не доверяй одному имени приложения или совпавшему release SHA, если это не идентифицирует нужную установку.
- Если подбирается другой порт, он должен согласованно использоваться Compose, installed record, supervisor, readiness, first-run URL и ярлыком. Проверь обновление уже существующей записи с занятым портом.
- Не останавливай и не удаляй чужие стеки автоматически. Если запуск невозможен, дай конкретное сообщение вместо открытия старого приложения.

### 4. Обновление, откат и Alembic `0022`

- Сопоставь миграции в актуальном исходном коде, снимке релиза, собранном образе и базе. Проверь стратегию отката после изменения схемы.
- Исправь подтверждённую причину рассогласования или добавь корректную проверку совместимости и остановку до опасного шага, если автоматический откат небезопасен. Не заявляй, что предыдущая версия восстановлена и работает без подтверждения.
- Запрещено «лечить» ошибку удалением томов/данных, сбросом базы, ручным переписыванием `alembic_version`, безусловным `stamp head` или добавлением фиктивной миграции `0022`.
- Не меняй релизный SHA на искусственное значение. Тестовые записи и образы должны оставаться в изолированной тестовой среде.

### 5. Проверка лицензии в настоящем пилоте

- Проверь цепочку публичный ключ → упаковка релиза → StateDir/pilot.env → Compose → Settings → серверная проверка лицензии.
- `APP_ENV=pilot` не должен переходить в development при проблеме конфигурации. Отсутствующий/неверный публичный ключ должен приводить к явному отказу.
- Подтверди сценарии: без лицензии обычная работа блокируется, администратор может загрузить лицензию; действительная лицензия разрешает работу; неверная подпись и просроченная лицензия отклоняются; лимит пользователей соблюдается; продление сохраняет данные.
- Проверь серверные ответы, а не только frontend-баннер. Не встраивай приватный ключ, готовую клиентскую лицензию или обход проверки в приложение/инсталлятор.

## Проверки и критерии готовности PR

- До исправления воспроизведи подтверждённые дефекты доступными способами. Для исправляемой логики добавь содержательные регрессионные тесты по существующим соглашениям; используй уже принятые библиотеки и harness.
- Выполни профильные Windows engine/Docker/supervisor/installer тесты, проверки лицензии, Compose и миграций согласно изменённому коду и CI. Проверь синтаксис PowerShell и `git diff --check`.
- Проверь именно собранный EXE, если среда позволяет. Тест checkout не равен тесту установщика.
- Нужна матрица приёмки: чистая Windows без Docker; Docker установлен/остановлен; Docker уже готов; пользовательская установка Docker; отказ UAC; перезагрузка/продолжение; повторный запуск мастера/ярлыка; занятый порт старым dev-стеком; обновление с данными и откат; лицензия в pilot.
- При невозможности VM/GUI/Docker явно отметь непроверенные пункты. Моки не являются доказательством реальной установки Docker или успешного запуска EXE. Не запускай разрушительные проверки на рабочей машине пользователя.
- Если обнаружишь несколько независимых причин, исправь их в тематических коммитах одного PR; не делай крупный архитектурный рефакторинг ради этой задачи.

## Что передать независимому ревьюеру

В PR и итоговом отчёте укажи:

1. Ссылку на PR, базовый SHA и точный head SHA.
2. Для каждой проблемы: свидетельство, установленную причину, изменение поведения и регрессионную проверку. Раздели исправленные дефекты и оставшиеся гипотезы.
3. Команды проверки, результаты, CI и ограничения реальной Windows-приёмки.
4. Проверку сохранности данных, согласованности миграций/отката, единственности операций, принадлежности readiness-ответа и fail-closed лицензирования.
5. Понятный пользователю сценарий проверки нового установщика на чистой VM и безопасной проверки при существующем Docker. Не предлагай очищать рабочие данные.

Ревьюер должен отдельно проверить, что PR не маскирует проблемы увеличением таймаутов, отключением лицензии, принудительной переустановкой Docker, удалением данных или принятием чужого HTTP-ответа за успешную установку.
