## P2 (обязательно): предпусковая синхронизация пароля выполняется, даже когда контейнер `db` НЕ запущен

**Где:** `infra/windows/engine/Compose.psm1`, `Start-HrmStack`, блок

```powershell
$passwordSynced = $false
if ($current.state -eq "partial" -or $current.state -eq "degraded") {
    $sync = Sync-HrmPostgresRolePassword -InstallDir $InstallDir -StateDir $StateDir
    if (-not $sync.ok) { return $sync }
    $passwordSynced = $sync.synced
}
```

**Дефект.** Условие проверяет только состояние стека, но не то, что контейнер `db` запущен.
`compose exec -T db psql` на остановленном/несозданном контейнере возвращает ненулевой код, поэтому:

- Контрпример: `Get-HrmComposeContainers` отдаёт `[{"Name":"db","State":"exited"},{"Name":"backend","State":"running"}]`
  (реальное состояние после жёсткого выключения машины, падения докера или ручной остановки db).
  Стек — `partial` (1 из 2 запущен), секрет в `secrets.json` есть.
- Ожидалось (и было до PR #57): `up -d` поднимает db, стек становится running — данные целы.
- Фактически теперь: `Sync-HrmPostgresRolePassword` → `exec` падает → `database_auth_failed`,
  `ok=$false`, пользователю — «создайте отчёт для поддержки». Восстанавливаемое состояние превращается
  в отказ с неверной причиной (пароль тут ни при чём).

Моки этого не видят: ветка `compose … exec` в харнессе отвечает успехом на `ALTER ROLE` независимо от
состояния контейнеров, поэтому зелёный CI этот дефект не обнаруживает.

**Что сделать.**
1. Предпусковую синхронизацию выполнять только если база действительно запущена:
   `if (($current.state -eq "partial" -or $current.state -eq "degraded") -and (Test-HrmDbContainerRunning -InstallDir $InstallDir -StateDir $StateDir))`.
   `Test-HrmDbContainerRunning` уже есть в том же файле (`Compose.psm1`, сразу после
   `Get-HrmDbSchemaRevision`) и как раз отвечает на этот вопрос, не меняя тома.
2. В пост-`up` ветке применить ту же защиту: если `db` не запущен, синхронизацию не пытаться делать —
   иначе `database_auth_failed` снова назовет неверную причину. Пусть отрабатывает честный путь
   (`up`/repair/schema), а отказ, если он будет, назовёт реальную причину.
3. Регрессионный кейс в `db-password.tests.ps1` (новый, не ослабляя существующие):
   - мир: секрет есть, `ContainersJson` = `[{"Name":"db","State":"exited"},{"Name":"backend","State":"running"}]`
     (или db отсутствует вовсе), `DbPasswordMismatch = $false`;
   - `Start-HrmStack` → `Assert-HrmEqual 0 $world.DbPasswordSyncCount` (синхронизация не пыталась
     выполняться на остановленной базе), `Assert-HrmTrue ($world.UpCount -ge 1)` (движок пошёл
     обычным путём `up`), результат НЕ `database_auth_failed`;
   - и зеркальный кейс: та же partial-ситуация, но `db` запущен и пароль не совпадает →
     синхронизация выполняется ровно один раз и стек доходит до running (чтобы охрана не отключила
     основной сценарий).
4. Убедиться, что охрана не ломает уже существующие кейсы suite (в них `db` в `partial`/`degraded`
   всегда `running` — они должны остаться зелёными без правок).

## P3.1 — потеряли stderr неуспешного `up` на новом пути

В `Start-HrmStack` после `$up = Invoke-HrmCompose … -IgnoreExitCode` stderr логируется только в
ветке `$after.state -ne "partial" -and $after.state -ne "degraded"`. Если `up` упал, а стек оказался
partial/degraded и синхронизация пропущена (нет секрета), возвращается общий `failed` **без единой
строки журнала о причине** — до PR #57 эта причина всегда попадала в лог. Восстановить
`Write-HrmLog "error" (Redact-HrmText ("Запуск контейнеров не удался: " + $up.Stderr.Trim()))` на всех
путях отказа, порождённых неуспешным `up` (с проверкой, что пароль/SQL в stderr не уйдёт в журнал —
   редактировать как и раньше).

## P3.2 — «последние 5 журналов» могут вытеснить журнал установки

`hr-manager.ps1` теперь создаёт `StateDir\logs\<action>-<timestamp>.log` для **любого** действия
(включая `open` из ярлыка и ручные вызовы). Ярлык «HR Manager» на рабочем столе вызывает `-Action open`,
поэтому после нескольких открытий приложения в `logs-engine.txt` поддержки останутся только
`open-*.log`, а журнал неудачной установки вытеснится. Починить в `SupportBundle.psm1`: сначала брать
журналы `install-*`/`update-*` (последние несколько), затем добирать самые свежие остальные, сохранив
общий предел (5) и `LogTail`. Добавить/поправить кейс в `db-password.tests.ps1`: в каталоге журналов
есть и свежие `open-*`, и более старый `install-*` — в `logs-engine.txt` обязан присутствовать
`install-*`.
