Ты дорабатываешь свою реализацию Phase 10 в PR #14 (`52b6c732`) для репозитория `sledovatel61/HR-Manager`.

Довести PR #14 до состояния, в котором его можно безопасно принять вместо PR #13. Сохрани сильное архитектурное решение PR #14: используй существующий `notification_outbox` и общий worker Phase 8/9. Не создавай второй параллельный механизм очереди без крайней необходимости.

## Обязательные исправления

### 1. Настоящий email double opt-in

Текущий endpoint, который при `granted=true` сразу записывает email-согласие от имени HR (`source="hr_recorded"`), не соответствует требованию double opt-in. Переделай поток:

1. HR инициирует письмо подтверждения для email из актуальной карточки кандидата.
2. Одноразовый криптографически случайный токен имеет срок действия; в БД хранится только его хеш.
3. Письмо подтверждения отправляется через существующий outbox.
4. Публичный endpoint по токену активирует consent только после действия кандидата.
5. Истёкший, уже использованный или заменённый токен отклоняется без изменения согласия.
6. Подтверждение привязано к нормализованному email, который был подтверждён. Изменение email немедленно делает старое согласие недействительным.
7. Отзыв согласия работает немедленно и fail-closed; ожидающие сообщения соответствующего канала должны быть заблокированы/отменены.

HR не должен иметь endpoint, который одним вызовом без подтверждения кандидата переводит email в состояние, разрешающее обычные сообщения. Если в продукте нужен административный override, он должен быть отдельной явно названной функцией, защищённой RBAC, с аудитом и не может маскироваться под double opt-in.

### 2. Сервер должен быть единственным источником содержания интервью

Удали `location` (и аналогичные поля свободного текста, если они используются для формирования интервью) из send/preview API и frontend payload. Клиент может передать только идентификатор события.

Место, время, кандидат и остальные данные интервью должны извлекаться сервером из `event_id`. И preview, и фактическая постановка в очередь должны использовать один серверный renderer.

На HTTP-этапе и непосредственно перед provider call перепроверяй, что событие:

- принадлежит указанному кандидату;
- имеет допустимый тип;
- не удалено и не отменено;
- соответствует типу сообщения;
- не устарело и не изменилось таким образом, чтобы сообщение стало неверным.

Если место отсутствует, используй безопасный серверный шаблон без места либо возвращай понятную ошибку. Не принимай произвольное место от клиента.

### 3. Настоящая идемпотентность HTTP retry

Убери серверный случайный ключ вида `secrets.token_urlsafe(...)` как единственный механизм дедупликации ручной отправки.

Добавь:

- `idempotency_key` в request schema;
- генерацию ключа на клиенте при начале новой операции и сохранение его при retry;
- серверную привязку ключа минимум к пользователю и операции/кандидату;
- уникальное ограничение в БД, если это совместимо с моделью outbox;
- повтор того же ключа с тем же payload должен вернуть исходный результат, а не создать новую отправку;
- тот же ключ с отличающимся payload должен вернуть `409`;
- конкурентные одинаковые запросы должны создавать одну логическую отправку.

Проверка «похожее queued-сообщение уже есть» не заменяет идемпотентность. Не логируй полный ключ и не включай его в пользовательские сообщения.

### 4. Честная и полная история

Проверь backend response и UI. Все реально используемые состояния должны иметь понятные русские подписи и корректный tone:

- `queued`;
- `sending`;
- `accepted`;
- `failed`;
- `cancelled`;
- прочие состояния, если они существуют в модели.

`accepted` означает только принятие сообщения провайдером. Не называй его delivered/read, если достоверного receipt нет. Не симулируй `delivered` или `read`.

Покажи или безопасно раскрой в истории точный сохранённый текст, канал, тип, источник, инициатора, время, число попыток, безопасный класс ошибки, привязанное событие и provider message ID, если это предусмотрено моделью. Не показывай секреты, токены или PII в аудитах/логах.

Отмена через API разрешена только для `queued`; `sending` и завершённые сообщения обычным endpoint отменять нельзя.

## Безопасность и повторные проверки

Сохрани и покрой тестами:

- RBAC для всех endpoint-ов, включая публичное подтверждение токена;
- CSRF для state-changing authenticated endpoint-ов;
- rate limiting для отправки, invite/confirm и публичного token endpoint;
- отсутствие возможности подменить `candidate_id`, `event_id`, канал, получателя или содержание;
- fail-closed при отсутствии consent, отзыве consent, изменении email, удалении кандидата и отмене/изменении события;
- повторную проверку consent, адреса, статуса кандидата, события и отмены непосредственно перед provider call;
- quiet hours и их явное подтверждение там, где оно предусмотрено текущим контрактом;
- bounded retries, backoff, lease recovery и идемпотентную обработку worker-ом;
- аудит действий без PII и provider payload.

Не ослабляй существующие проверки Phase 8/9 и не сохраняй provider secrets в БД.
