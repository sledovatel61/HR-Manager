## 2. P2 — `down_revision = "0017"` создаёт развилок и ломает `upgrade head` (обязательно)

**Где:** `backend/alembic/versions/0019_candidate_attachments.py:48`.

### Что происходит на самом деле

Ревьюер положил твою миграцию и миграцию PR #46 (`revision = "0018"`,
`down_revision = "0017"`) в одно дерево — это ровно состояние «оба PR смержены»:

```
alembic heads -> ['0018', '0019']
дети 0017:  0018 -> 0018_work_schedule_import.py
            0019 -> 0019_candidate_attachments.py
```

`0017` получает **двух** потомков. Дальше:

```
$ alembic upgrade head --sql
ERROR [alembic.util.messaging] Multiple head revisions are present for given argument 'head'; ...
FAILED: Multiple head revisions are present for given argument 'head'
```

**Фактически:** после мержа PR #46 `alembic upgrade head` падает полностью. Приложение
не может провести миграцию — это не «библиотека не работает», это отказ обновления БД
целиком.

**Ожидалось:** единственный head, линейная цепочка.

### Почему выбор в пользу зелёного CI — неверный

* Красный CI с «Can't locate revision identified by '0018'» **невозможно смержать
  случайно** — он заставляет перебазировать ветку сразу после мержа #46.
* Зелёный CI + «готов к ревью» + «нужна ручная правка после мержа #46» — это худшая из
  комбинаций: PR выглядит готовым, его мержат, и ломальник срабатывает уже на `main`.
* Ты сам это описал и в шапке PR, и в разделе «Слияние с PR #46» — но задокументированная
  мина всё равно мина. Первый промпт прямо запрещал этот вариант и объяснял почему:
  «**Не «чини» его, возвращая `down_revision = "0017"` — это создаст развилку (два
  head'а потомка `0017`) и сломает `upgrade head` ещё раз.**» Отступление от прямого
  запрета — это не «осознанное инженерное решение», это обход требования.

1. `down_revision: str | None = "0018"`.
2. Принять, что fast-тест головы цепочки (`tests/test_migrations.py`) будет красным с

## 3. P3 — «необъяснимый» флак-тест: причина найдена, и таких тестов два

Ты честно записал, что `test_upload_never_writes_to_the_filesystem` разово упал и
причину установить не удалось. Ревьюер воспроизвёл: **2 падения в 3 полных прогонах**,
и причина не в `tmp_path`.

### Корень

```
assert bytes(row.content) == build_docx()
E  AssertionError: assert b'PK\x03\x04...' == b'PK\x03\x04...'
E    At index 10 diff: b'\x03' != b'\x04'
```

`build_docx()` **недетерминирован**: `zipfile.writestr(name, data)` подставляет
`date_time = time.localtime()[:6]` в локальный заголовок ZIP, а DOS-время имеет
разрешение 2 секунды. Два вызова, разделённые границей секунды, дают разные байты —
расходятся на индексе 10 (младший байт mod-time).

В тесте фикстура вызывается **дважды**: один раз для загрузки, второй — для сверки с
тем, что лежит в БД. В одиночном прогоне файла тест успевает внутри одной секунды,
поэтому флак не виден; в полном прогоне он занимает дольше и ловит границу примерно
раз в три запуска. Именно поэтому 4 твоих прогона одного файла были зелёными.

Обрати внимание: падает **не** `assert list(tmp_path.iterdir()) == []`, а сравнение
байтов на строке 851. Твоя формулировка «в первом прогоне упал
`test_upload_never_writes_to_the_filesystem`» верна, но если ты диагностировал по
предположению про `tmp_path` — это не оно.

### Таких тестов два

| Тест | Сравнение |
| --- | --- |
| `test_upload_never_writes_to_the_filesystem` | `assert bytes(row.content) == build_docx()` — **флак** |
| `test_download_does_not_leak_internal_storage` | `assert response.content == build_docx()` — **флак** |
| `test_duplicate_name_is_a_conflict` | два вызова, но сверки байтов нет — безопасен |
| `test_foreign_candidate_is_hidden_from_other_hr` | второй вызов для проверки 404 — безопасен |
| `test_unauthenticated_and_csrf` | второй вызов без CSRF — безопасен |
| `test_delete_is_soft_audited_and_hides_the_file` | `len(build_docx())` — длина стабильна, безопасен |

### Что сделать

* В обоих флакающих тестах строить payload **один раз** в переменную и сверять с ней:
  `payload = build_docx()` … `assert response.content == payload`.
* Либо, если предпочитаешь, сделать `build_docx()` детерминированной (фиксировать
  `ZipInfo.date_time`) — но это меняет фикстуру для всех тестов, поэтому вариант с
  локальной переменной предпочтительнее.
* Добавить проверку, что в файле `tests/test_candidate_attachments.py` не осталось
  тестов, сравнивающих содержимое с **свежим** вызовом `build_docx()`/`build_pdf()`.
* В PR убрать формулировку «причину не установил» и написать найденную причину.

## 4. P3 — заявление про точность нормализации имён PDF неверно

В отчёте ты написал: «Нормализуются именно токены, а не «выбрасываются все пробелы из
файла», поэтому посторонний текст совпасть не может.»

Ревьюер проверил — **совпасть может**:

| Вход (внутри строкового литерала PDF) | Результат |
| --- | --- |
| `/Java Script` | **415** |
| `a/Java Script` | **415** |
| `/Java  Script` (два пробела) | **415** |
| `/Java\nScript` | **415** |
| `/J#61v#61Script` | **415** |
| `/X FA` | **415** |

| обычный текст | 201 |

`a/Java Script` тоже отклоняется — значит, паттерн **не привязан к границе токена**, а
является гибким поиском подстроки: после `/` допускаются пробелы и `#xx` между любыми
символами имени.

Практический вес ничтожен: строка `/Java Script` в HR-документе практически
невероятна, и до правки точный `/JavaScript` тоже отклонялся. Но заявление в промпте и
(если оно там есть) в PR/доках — неверно, а первый промпт специально требовал
сохранить точность, чтобы нормализация не превращалась в отказ нормальных файлов.

### Что сделать

* Либо привести реализацию к заявленному: требовать, чтобы `/` был началом
  name-токена (перед ним — не символ имени), и не матчить внутри строковых литералов.
* Либо, если это избыточно, исправить текст: написать, что проверка — гибкий поиск
  подстроки с учётом пробелов и `#xx`, и что редкий текст вида `/Java Script` внутри
  документа даст ложный отказ.
* Добавить тест на границу: документ со словом `/Java Script` внутри текста — зафиксировать
  фактическое поведение (сейчас 415), чтобы оно было осознанным, а не случайным.
