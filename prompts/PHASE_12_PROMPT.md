## Продуктовый контракт

Phase 12 закрывает требование `PRODUCT_SPEC.md`: установка, обновление и
первоначальная настройка выполняются обычным пользователем Windows в несколько
кликов. Пользователь не должен видеть терминал, PowerShell, `.env`, Docker
Compose, PostgreSQL, Alembic, технические логины или сгенерированные секреты.

Целевой сценарий этой фазы — **один локальный пилот на Windows 10/11 x64, где ПК
пилотного администратора одновременно является рабочим местом и локальным
сервером**. Docker Desktop/WSL2 запускает Linux-контейнеры незаметно для
пользователя. Приложение остаётся клиент-серверным web-продуктом с PostgreSQL и
не превращается в Electron-приложение, SQLite-сборку или отдельную
однопользовательскую архитектуру.

Должны появиться:

1. собираемый и распространяемый графический `HR Manager Setup.exe` с русским
   мастером установки; запуск скрипта из checkout не считается готовым
   пользовательским решением;
2. сценарий «запустить → выбрать роль → ввести фамилию → нажать “Установить”»;
3. внутренний идемпотентный automation engine для установки, запуска,
   диагностики и обновления без дублирования логики в GUI;
4. автоматическая безопасная генерация локальных секретов и сохранение состояния
   между запусками;
5. автоматическая проверка/подготовка зависимостей и честная GUI-диагностика;
6. автоматическое создание защищённой пилотной учётной записи, ярлыка и открытие
   готового приложения;
7. безопасный повторный запуск и управляемое обновление с backup, миграцией,
   smoke-check и возвратом предыдущего кода при ошибке;
8. короткая русскоязычная инструкция, рассчитанная на пользователя без
   технических знаний.

Критерий UX жёсткий: если в основном сценарии пользователь должен открыть
PowerShell/терминал, редактировать файл, придумать технический username, работать
с Docker или ввести команду PostgreSQL/Alembic — установка не завершена.

## 1. Поддерживаемый локальный профиль

Создай отдельный явно названный Compose overlay/profile для локального пилота.
Не ослабляй `infra/compose.prod.yml` и не меняй development Compose в скрытый
production-вариант.

Требования:

- PostgreSQL, backend, frontend, worker и backup запускаются в Linux-
  контейнерах одной стабильной Compose project name;
- наружу публикуется только frontend на `127.0.0.1`; БД, backend и worker не
  доступны из локальной сети;
- frontend продолжает проксировать API к backend внутри Compose-сети;
- данные PostgreSQL и зашифрованные backup используют именованные volumes и не
  теряются при обычном stop/restart/update;
- внешние SMTP/Telegram-интеграции по умолчанию выключены и не мешают запуску;
- dev-секреты, dev-пароли и `APP_DEBUG=true` в пилотном профиле запрещены;
- production security guard, Secure/SameSite cookies и фактическая схема
  `http://127.0.0.1` должны быть согласованы. Нельзя получить неработающий login
  из-за Secure-cookie по HTTP и нельзя молча отключить защиту production во всех
  окружениях. Зафиксируй и протестируй выбранную локально-доверенную модель;
- не обещай HTTPS, удалённый доступ или многопользовательский production deploy,
  если сценарий их не предоставляет.

## 2. Графический установщик и внутренний launcher

Добавь воспроизводимую сборку `HR Manager Setup.exe` штатным для Windows
installer toolchain. Выбери один зрелый вариант (например, Inno Setup, WiX или
NSIS), закрепи его версию, добавь исходный installer manifest/script в git и
собирай артефакт в CI. Не коммить бинарный `.exe` в git. Не добавляй
неподдерживаемый самописный загрузчик или GUI-фреймворк только ради мастера.

Графический мастер на русском языке должен:

1. показать название продукта и кратко объяснить, что этот ПК станет локальным
   сервером HR Manager;
2. проверить системные требования до изменения машины;
3. предложить ровно три понятные рабочие роли: **HR**, **Руководитель**,
   **Администратор** — с кратким описанием возможностей;
4. запросить обязательную фамилию, валидировать длину/символы и показать её перед
   подтверждением; не собирать имя, телефон или email без необходимости;
5. показать итог и одну кнопку «Установить»;
6. отображать понятный прогресс без технического потока логов;
7. после smoke-check создать ярлыки «HR Manager» и «Диагностика HR Manager»,
   открыть приложение и показать результат;
8. при ошибке сохранить санитаризированный технический журнал и предложить
   повторить безопасный шаг либо открыть диагностику.

Установщик обязан работать из versioned release-артефакта и проверять целостность
вложенных файлов. Он не должен клонировать git, исполнять произвольный удалённый
скрипт или зависеть от наличия Python/Node/Git на ПК пользователя. Добавь
машиночитаемый release/version manifest и документируй trust boundary подписи
кода. Если в текущей инфраструктуре невозможно реально подписать `.exe`
доверенным сертификатом, подготовь deterministic signing hook и CI/release
инструкцию, но не выдавай неподписанный файл за подписанный.

Внутри установщика используй один основной PowerShell entry point (например,
`infra/windows/hr-manager.ps1`) с закрытым набором действий минимум:

- `install` — preflight, создание локальной конфигурации и пользователя, запуск;
- `start` — идемпотентный запуск уже установленного контура;
- `stop` — остановка без удаления данных;
- `status` — состояние Docker Desktop, контейнеров, health, worker, backup и
  установленной версии без секретов/PII;
- `update` — безопасное обновление;
- `diagnostics` — санитаризированный отчёт для поддержки.

PowerShell — внутренний automation engine, а не основной интерфейс пользователя.
Вся логика должна быть тестируемой, версионируемой и пригодной для вызова
установщиком с параметрами через защищённый state/input file. Фамилию, роль,
пароли и токены запрещено передавать в process command line. Не требуй глобально
менять ExecutionPolicy, вручную запускать терминал от администратора или вводить
Docker-команды. Добавь документированный non-interactive test mode, который не
трогает реальную установку.

Preflight обязан проверять как минимум:

- Windows и поддерживаемую версию PowerShell;
- наличие и доступность Docker CLI/daemon (Docker Desktop должен быть запущен);
- `docker compose` v2 и минимальную версию, нужную overlay;
- доступность обязательных портов;
- возможность записи в каталог локального состояния;
- достаточное свободное место с документированным порогом;
- корректность уже существующей конфигурации без её перезаписи.

Если Docker Desktop/WSL2 отсутствует, мастер должен автоматически провести
пользователя через установку поддерживаемой версии из официального доверенного
источника или открыть один проверенный официальный installer с понятным
объяснением. Нельзя молча принимать лицензию за пользователя или обходить
системные требования. UAC, включение Windows-компонентов, виртуализация и
перезагрузка могут потребовать подтверждения; мастер обязан сохранить state,
создать безопасное одноразовое resume-действие и продолжить с того же шага после
перезагрузки. Пользователь не должен вручную вводить команды или заново заполнять
форму. Не включай Docker Desktop binary в релиз без права на распространение.

Ошибки должны быть по-русски, содержать понятное действие пользователя и
возвращать ненулевой exit code. GUI не должен зависать, а engine не должен ждать
интерактивный prompt в installer/CI/test mode.

## 3. Секреты и локальное состояние

При первом `install` автоматически генерируй криптографически случайные значения
как минимум для signing key, PostgreSQL, bootstrap admin и шифрования backup.

- Не печатай секреты в stdout/stderr, диагностике, process arguments или URL.
- Не коммить и не размещай их внутри repository-tracked файлов.
- Храни конфигурацию в однозначном локальном state directory; добавь его в
  `.gitignore`, если он может оказаться внутри checkout.
- На Windows ограничь ACL текущим пользователем настолько, насколько позволяет
  штатный PowerShell/.NET, и fail closed при невозможности безопасно сохранить
  секреты. Не добавляй тяжёлый secret-manager ради локального пилота.
- Повторный запуск не ротирует ключи и пароли самовольно. Особенно нельзя
  потерять ключ расшифровки существующих backup или инвалидировать сессии без
  явного обновления.
- Пользователь не придумывает и не переписывает технический логин или временный
  пароль. Bootstrap credential должен быть одноразовым локальным способом
  создать и автоматически авторизовать владельца установки, а не постоянным
  общим паролем. Предпочти короткоживущий одноразовый exchange между installer и
  loopback backend с серверной проверкой, хешированным хранением, аудитом и
  атомарным погашением. Если приложению для последующих входов всё же нужен
  пароль, запроси его уже в понятном защищённом UI после первого открытия, а не
  в консоли; обоснуй UX и threat model.
- Не передавай пароль пилота через командную строку, URL, логи или frontend
  bundle.

## 4. Первый запуск в браузере

После успешного запуска установщик открывает только локальный URL приложения.
Имя профиля формируется из введённой фамилии; технический username генерируется
детерминированно и безопасно, но пользователь не обязан его знать для первого
входа. Первый запуск должен быть завершён через UI:

- пользователь видит понятный экран состояния и следующие шаги;
- видит свою фамилию и выбранную при установке рабочую роль;
- получает единственную пилотную учётную запись с полным явно выданным
  `pilot_full_access`, включая scopes Phase 11;
- выбирает часовой пояс, рабочие дни и тихие часы;
- видит, что email/Telegram необязательны, и может пропустить их;
- получает подтверждение готовности backend, БД, worker и backup-контура;
- после завершения setup повторный пользователь не может захватить bootstrap
  flow или создать второго полного пилота.

Выбранные **HR / Руководитель / Администратор** — основной рабочий режим и
стартовый интерфейс владельца пилота, а не способ ослабить контракт пилотного
доступа. По текущей модели полный пилот имеет серверную роль `admin` и явный
`pilot_full_access`; если для сохранения выбранной рабочей роли требуется
отдельное поле профиля, добавь его миграцией и не подменяй им RBAC. В UI честно
объясни, что первый владелец установки имеет полный доступ независимо от
выбранного рабочего режима. После пилота обычным пользователям назначаются
реальные минимальные RBAC-роли через существующее администрирование.

Переиспользуй существующие `/setup/state`, `/setup/pilot`, preferences,
integration status и access grants, но исправь их контракт, если текущий flow
не обеспечивает безопасный first-run. Не создавай unauthenticated admin API.
Bootstrap endpoint/token, если он действительно нужен, должен быть локальным,
одноразовым, короткоживущим, храниться только в виде хеша, защищаться от гонок и
переставать работать после завершения установки. Предпочти более простой
безопасный вариант.

Все mutating endpoints: CSRF после установления сессии, server-side RBAC,
rate-limit там, где применимо, аудит без паролей/токенов/PII и конкурентно
безопасная идемпотентность.

## 5. Update и rollback

`update` должен принимать только явный доверенный источник версии. Не скачивай
и не исполняй произвольный URL/branch и не делай небезопасный `git pull` поверх
грязного checkout. Если полноценная проверка подписанного release-артефакта не
поддерживается текущим release-процессом, реализуй обновление из явно указанного
локального release directory/tag и честно задокументируй trust boundary.

Обязательный порядок:

1. preflight и проверка текущего состояния;
2. сериализация update через lock — два update одновременно невозможны;
3. проверка целевой версии и Compose-конфигурации;
4. **успешный зашифрованный backup и integrity check до миграции**; при ошибке
   обновление прекращается;
5. получение/сборка целевых образов без уничтожения текущих;
6. one-shot Alembic upgrade под существующим PostgreSQL advisory lock;
7. переключение контейнеров;
8. bounded readiness и smoke: frontend, `/health`, `/ops/status` с ожидаемым
   release SHA/version, worker health и отсутствие migration drift;
9. запись санитаризированного результата обновления.

При ошибке после переключения восстанови предыдущие образы/код и проверь их
health. Не выполняй автоматический Alembic downgrade и не заявляй полный rollback
данных после уже применённой необратимой миграции. Покажи пользователю честный
статус: код восстановлен, backup сохранён, требуется операторское восстановление
или forward-fix. Не удаляй предыдущую рабочую версию до успешного smoke.

Повторный `update` после interruption должен либо безопасно продолжить, либо
остановиться с понятной диагностикой; он не должен повторно портить данные.

## 6. Status и diagnostics

Сделай один агрегированный пользовательский результат, где различаются минимум:

- Docker Desktop отсутствует / daemon не запущен;
- приложение остановлено / запускается / готово / degraded;
- база недоступна;
- миграционный head не совпадает;
- worker отсутствует или heartbeat просрочен;
- backup отсутствует, просрочен или последняя проверка неуспешна;
- установленная и запущенная версии различаются;
- необязательные Telegram/SMTP не настроены.

Diagnostics может собирать версии, Compose service states, health codes и
санитаризированные последние логи. Запрещены значения env, connection strings,
cookies, токены, пароли, email/телефоны, ФИО, message bodies и содержимое
кандидатских документов. Добавь автоматические regression-тесты redaction.

## 7. Повторная установка, удаление и границы

Повторный запуск `Setup.exe` должен распознать существующую установку и
предложить только безопасные действия: открыть, восстановить/починить, обновить
или удалить. Он не должен повторно создавать владельца, менять выбранную роль,
ротировать секреты или удалять данные.

Добавь стандартную запись в Windows Apps & Features и деинсталлятор. По
умолчанию uninstall удаляет launcher/ярлыки/контейнеры приложения, но **не удаляет
PostgreSQL и backup volumes**. Удаление данных — отдельное явно подтверждаемое
действие с предупреждением и вводом подтверждающей фразы; перед ним предложи
зашифрованный backup. Удаление HR Manager не должно автоматически удалять общий
Docker Desktop/WSL2 пользователя.

## 8. Совместимость и границы

Обязательно сохрани:

- PostgreSQL как единственную production/пилотную БД;
- миграционный путь от `0012` и все данные фаз 0–11;
- owner-based доступ к документам и `candidate_documents_all`;
- append-only history, outbox/worker, quiet-hours, consent, retry/lease/dedup;
- production Compose/deploy/backup сценарии для серверного контура;
- отсутствие PII и секретов в git, логах, audit, metrics и diagnostics.

В Phase 12 **не входят**:

- Electron/native desktop-клиент, Windows service или обязательный MSI; обычный
  графический `Setup.exe` и деинсталлятор, напротив, входят в фазу;
- встроенная поставка Docker Desktop либо автоматическое принятие его лицензии;
- macOS/Linux desktop launchers (существующие Linux server scripts сохраняются);
- облачный control plane, auto-update daemon и фоновая загрузка релизов;
- удалённая публикация локального пилота в интернет;
- изменение бизнес-функций кандидатов, документов, правил и коммуникаций;
- новая очередь, микросервис, SQLite или хранение секретов в БД открытым текстом.

Не добавляй внешние runtime-библиотеки без доказанной необходимости. Для
PowerShell предпочти штатные средства, Docker Compose и существующие API.

## 9. Тесты

Добавь автоматические тесты минимум для:

1. воспроизводимой сборки installer source и проверки release manifest/hash;
2. чистого графического install из пути с пробелами/кириллицей и повторного
   идемпотентного запуска `Setup.exe`;
3. выбора каждой роли, валидации фамилии и отсутствия лишних обязательных полей;
4. безопасной передачи фамилии/роли без command-line leakage и shell injection;
5. отсутствующего Docker CLI, остановленного daemon и неподдерживаемого Compose;
6. resume после обязательной перезагрузки без повторного создания пользователя;
7. занятых портов, недостатка места и недоступного state directory;
8. генерации уникальных сильных секретов, сохранения между запусками и ACL;
9. отсутствия секретов в выводе, аргументах, diagnostics и tracked-файлах;
10. валидного pilot Compose overlay: наружу только loopback frontend;
11. одноразовой локальной авторизации first-run и single-pilot race;
12. setup RBAC/CSRF/rate-limit/idempotency и невозможности повторного takeover;
13. отображения выбранного рабочего режима при сохранённом `pilot_full_access`;
14. применения preferences и пропуска необязательных интеграций;
15. создания/исправления ярлыка, Apps & Features и безопасного uninstall без
    удаления данных по умолчанию;
16. update lock и повторного запуска после interruption;
17. запрета update при неуспешном backup/integrity check;
18. успешного `0012 -> head` upgrade с сохранением данных;
19. неуспешной миграции, readiness и smoke с проверкой code rollback semantics;
20. совпадения release SHA/version и обнаружения migration drift;
21. status/degraded состояния worker, DB и backup;
22. redaction PII/secrets в диагностическом bundle;
23. регрессий backend/frontend фаз 0–11 и production overlay;
24. PowerShell parser/static checks и сценарных тестов с mockable command runner;
25. installer UI automation/accessibility: keyboard navigation, DPI 125/150%,
    понятные русские ошибки и отсутствие открывающегося терминала.

Гонки, миграции, backup и constraints доказывай настоящими PostgreSQL/Compose
integration tests. PowerShell-логику структурируй так, чтобы ошибки можно было
детерминированно тестировать без реального удаления volumes и пользовательских
данных. Ни один тест не должен трогать реальную локальную установку.

credentials, backup или персональные данные.

## Definition of Done

Фаза принимается только если:

1. обычный пользователь запускает собранный `HR Manager Setup.exe`, выбирает
   роль, вводит фамилию и завершает установку в несколько кликов без терминала,
   `.env` и ручных Docker/PostgreSQL/Alembic-команд;
2. pilot overlay безопасно публикует только frontend на loopback и не использует
   development secrets/debug;
3. секреты генерируются автоматически, защищённо сохраняются, не ротируются при
   повторном запуске и не попадают в вывод/диагностику/git;
4. first-run создаёт ровно одного владельца с выбранным рабочим режимом, явным
   полным пилотным доступом и настройками времени без unauthenticated admin
   backdoor и без передачи credential через command line/URL;
5. update блокируется без валидного encrypted backup, применяет миграции один
   раз и проверяет точную запущенную версию;
6. ошибочное обновление возвращает предыдущий код, не делает автоматический
   downgrade БД и честно сообщает границу восстановления;
7. status/diagnostics различают обязательные и необязательные компоненты и не
   раскрывают PII/секреты;
8. данные и функции фаз 0–11 не потеряны, migration path доказан на PostgreSQL;
9. повторный Setup/repair/update не меняет владельца и секреты, ярлыки работают,
   а uninstall по умолчанию сохраняет БД и backup;
10. release pipeline собирает проверяемый `Setup.exe` из закреплённых исходников;
    статус цифровой подписи указан честно;
11. backend, PostgreSQL integration, frontend, Compose, installer и Windows
    acceptance зелёные для точного итогового SHA;
12. создан `docs/phase-12-report-<agent>.md` с baseline/final SHA, архитектурой,
    threat model локальных секретов/bootstrap/update, migration head, файлами,
    installer toolchain/version, hash/signing status, точными командами и counts,
    CI links, Windows acceptance, ограничениями и handoff.

После реализации закоммить изменения, отправь только рабочую Phase 12 ветку и
открой PR в `main`. Дождись проверок именно для итогового SHA и сообщи URL PR,
ветку, baseline SHA, final SHA и только подтверждённые результаты. Merge
выполняет владелец проекта отдельно.
