Продолжи разработку репозитория `sledovatel61/HR-Manager` и выполни **Phase 8 —
фундамент уведомлений и пилотный режим**.

Работай как coding-agent: самостоятельно изучай репозиторий, вноси изменения,

ограничивайся планом или рекомендациями.

## Обязательный старт

1. Синхронизируй репозиторий и начни строго от актуального `origin/main`:

   ```bash
   git fetch origin --prune
   git switch main
   git pull --ff-only origin main
   git status --short --branch
   git rev-parse HEAD
   ```

2. До любых изменений полностью прочитай:
   - `agents.md`;
   - `PRODUCT_SPEC.md`;
   - `ROADMAP.md`;
   - `README.md`;
   - `docs/CURRENT_STATUS.md`;
   - `docs/ARCHITECTURE.md`;
   - `docs/phase-7-report-agent2.md`;
   - `prompts/PHASE_8_PROMPT.md`.
3. Зафиксируй полный baseline SHA и результаты исходных проверок.
4. Создай отдельную ветку `arena/phase-8-notifications`. Если она уже занята,
   используй короткий суффикс агента. Не разрабатывай в `main` и не выполняй
   самостоятельный merge в `main`.

## Исполнение

- Полным и приоритетным ТЗ является `prompts/PHASE_8_PROMPT.md`: выполни весь
  scope, предварительный аудит и Definition of Done без сокращений.
- Сохрани совместимость с принятыми этапами 0–7. Не откатывай release/backup,
  RBAC, CSRF, audit, события, аналитику и существующие API/UI-контракты.
- Реализуй реальные внутренние уведомления, личные напоминания,
  PostgreSQL transactional outbox/queue, отдельный worker, lease/retry/dedup,
  quiet hours/timezone/DST, пилотного пользователя с явно назначенным полным
  доступом и идемпотентный bootstrap.
- Не имитируй успешную отправку Telegram/email, не добавляй Redis/RabbitMQ,
  новые микросервисы, сообщения кандидатам или универсальный rule engine: это
  scope следующих этапов.
- Не помещай секреты, PII, дампы или реальные персональные данные в код,
  логи, тестовые fixtures, git history и отчёт.
- Не заявляй непроведённые проверки успешными. Если инструмент недоступен
  локально, явно зафиксируй это и подтверди проверку соответствующим GitHub CI
  job.

## Завершение и handoff

1. Выполни все backend unit/integration, frontend lint/typecheck/test/build,
   migration, Compose config/smoke, security/PII и `git diff --check`, указанные
   в полном ТЗ.
2. Добавь `docs/phase-8-report-<agent>.md`: baseline/final SHA, решения,
   миграции, изменённые файлы, точные команды и результаты с числом
   passed/skipped, известные ограничения и handoff для этапов 9–11.
3. Закоммить изменения, опубликуй ветку и открой PR в `main`.
4. Дождись зелёных обязательных GitHub checks для финального SHA ветки. При
   падении CI изучи логи, исправь причину, повторно проверь и обнови PR.
5. В финальном ответе дай ссылку на PR, final SHA, список реализованного,
   фактические результаты тестов и только реальные оставшиеся ограничения.

Начинай с проверки актуального состояния репозитория и чтения перечисленных
файлов, затем реализуй Phase 8 полностью.
