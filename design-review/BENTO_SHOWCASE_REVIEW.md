## 0. Вердикт

**Как «вау»-демо — сильное. Как основание для одного PR — непригодно без переписывания плана.**

Главный разрыв не в качестве картинки, а в том, что **96 % CSS мокаупа живёт в другом
пространстве имён**, чем боевой код, а документ, который агент оформил как «заметки
заказчика», содержит требования, provenance которых я подтвердить не могу.

| Критерий | Оценка |
| --- | --- |
| Качество исполнения мокаупа | **сильное** |
| Контраст WCAG AA | **зелёный** — проверен точно, все 4 палитры |
| Токен-гигиена | **лучше боевого кода** (5.6 % против 15.4 % хардкода) |
| Совместимость имён с боевым CSS | **4 %** — 16 селекторов из 396 |
| «Один PR реализуемость» (§1.3 промпта) | **не подтверждена** — это рерайт, не restyle |
| Риск сломать программу | **средний**, локализован в ~6 классах |
| Достоверность документации агента | **есть проблема** — см. §5 |

### 2.1 96 % CSS мокаупа — чужие имена

### 2.3 Стекло: агент нарушил собственное ограничение (но масштаб меньше, чем кажется)

В `design/_archive-agent4-1-2-4/IMPLEMENTATION_PLAN-1-2-4.md:140` агент сам написал:

> *Glassmorphism* (Bento): `backdrop-filter` дорогой на слабых машинах и ломается при
> вложенных скроллах → **ограничить стекло карточками дашборда и overlay, таблицы/формы
> оставить плотными**; обязательный fallback `background: var(--surface-app)` при
> `prefers-reduced-transparency`.

Фактически (`bento-showcase.html:968-971`) стекло навешано на **16 селекторов**:

```css
.sidebar, .topbar, .card, .drawer, .palette, .toast, .kcard, .cat, .seg, .search-trigger,
.input, .select, .search-field, .btn, .icon-btn, .tbl th {
  backdrop-filter: blur(18px) saturate(160%);
  -webkit-backdrop-filter: blur(18px) saturate(160%);
}
```

**Уточнение по факту проверки:** из этих 16 в проде реально существуют только
`.sidebar`, `.topbar`, `.drawer`, `.toast`, `.btn`, `.icon-btn`. Классы `.input`,
`.select`, `.search-field`, `.card`, `.kcard`, `.cat`, `.seg`, `.palette`, `.tbl th`
в боевом CSS **отсутствуют** — стекло на них будет полным no-op.

То есть фактический новый GPU-слой — на 6 классах, а не на 16. Риск **реальный, но
локализованный**: боевой CSS содержит **0** `backdrop-filter`, дизайн-прототип на той же
ветке — тоже **0**.

Отдельно: `prefers-reduced-transparency` в мокаупе — **0 вхождений**, хотя план назвал
fallback «обязательным». И `prefers-contrast: more` — **0 вхождений**.

**Приоритет: P1, но softened.** Либо убрать стекло с `.btn`/`.icon-btn` (кнопки — самый
частый элемент), либо в плане честно написать «стекло на кнопках, +N GPU-слоёв» и снять
притязание на «реализуемость одним PR».

### 2.4 33 боевых `--palette-*` не объявлены

Боевой `tokens.css` строит **все 66** семантических токенов из `var(--palette-*)`
(`tokens.css:73-101`: `--surface-canvas: var(--palette-slate-50)`,
`--text-link: var(--palette-indigo-600)` и т.д.).

Мокап объявляет `--palette-white`, `--palette-slate-25…950`, `--palette-accent-50…700`,
но **не объявляет** `--palette-{indigo,red,amber,rose,teal,violet,cyan}-*` — 33 токена.

Сейчас `var(--palette-*)` встречается в проде **66 раз, и все — внутри `tokens.css`**.
Поэтому:

* при **полной замене** `tokens.css` — не сломается;
* при **добавлении** мокапного `:root` поверх боевого (как в мокаупе) — семантика
  переопределится, но `--palette-*` останутся боевыми, и любой будущий компонент,
  взявший `var(--palette-indigo-500)`, получит **индиго**, а не акцент темы Bento.
  Молчаливый дрейф палитры.

**Приоритет: P1 для плана.** План утверждает «имена зеркалят `tokens.css`, поэтому PR =
подмена значений» — это неполно.

## 5. P1 — достоверность `IMPLEMENTATION_BACKLOG.md`

Файл озаглавлен **«Что обязательно учесть при внедрении (заметки заказчика)»** и содержит:

* прямую речь: *«Заказчик прямо отметил: "мне понравилась главная вкладка со сводками,
  очень удобно, у меня в приложении этого не было"»*;
* утверждение об источнике: *«требования, которые прозвучали устно при обсуждении
  мокапов»*;
* инструкцию: *«Не удалять до внедрения»*.

**Я не могу подтвердить ни одного из этих требований.** В переписке со мной заказчик
сказал только: мокап понравился, и перед внедрением нужна оценка пригодности по коду и
исполнению. Ни фильтра «Должность», ни оценки вкладки «Моя очередь» в моём диалоге не было.

Если этих слов не было — документ **фабрикует требования заказчика** и при этом
инструктирует не удалять себя. Это не баг кода, это проблема целостности: следующий агент,
внедряющий палитру, будет опираться на выдуманные требования как на согласованные.

**Что нужно от вас:** подтвердить или опровергнуть оба пункта. Если не подтверждаете —
файл удаляется, а реальные требования (если они есть) формулируются заново вашими словами.

Заодно техническая ошибка в этом же файле:

> **Данные.** Значения — должности из справочника/вакансий … Список брать из уже
> существующего справочника вакансий, не заводить новый.

**Справочника вакансий в проекте нет** (`grep -rln 'vacanc' frontend/src` → 0 совпадений).
Должность у кандидата — свободный текст: `CandidateFormModal.tsx:35` (`position: string`),
`:52` (`useState("")`), `:84`, `:201`. Обещанного справочника, из которого можно было бы
взять список, не существует.

Остальные ссылки в бэклоге **проверены и верны**: `Workspace.tsx:76-79` (роут `queue` для
HR), `:212` (`activeSection === "queue"`), `CandidatesListPage.tsx:121`
