# Задача: вложения DOCX/PDF в карточке кандидата

Репозиторий: `https://github.com/sledovatel61/HR-Manager`  
Рабочая ветка: `arena/<id>-candidate-attachments`, один PR в актуальный `main`.  
Это отдельный PR: не объединять с импортом Excel, графиком выхода или установщиком.

## Контекст и пример файла

В каталоге владельца есть пример реальной анкеты:

`C:\Users\User\Documents\HR\HR Manager Desktop\LLM\30.09.2026\Анкета соискателя Баев К.Р.docx`

Папку `Скрины проблем программы` не открывать и не изменять. Реальный DOCX не
коммитить и не помещать в тестовые fixtures: в нём могут быть персональные данные.
Удалённая Арена не имеет автоматического доступа к Windows-пути: пример передаётся
приватным вложением при необходимости; без него не заявлять проверку этого файла.

Нужно добавить в карточку кандидата защищённые вложения анкет и сканов:
`.docx`, `.pdf` (при необходимости также явно разрешить только согласованный
набор безопасных расширений, но не принимать произвольные файлы).

## Пользовательский сценарий

- В карточке кандидата появляется блок «Документы и анкеты».
- Пользователь с правом видеть кандидата может увидеть список: имя файла, тип,
  размер, дата загрузки, кто загрузил.
- Пользователь с правом редактировать/документировать кандидата может нажать
  «Загрузить», выбрать файл стандартным диалогом Windows и подтвердить загрузку.
- Сервер проверяет расширение, MIME, размер и сигнатуру файла; нельзя доверять
  только имени или `Content-Type`. Запрещены исполняемые файлы, архивы, макросы,
  HTML и path traversal.
- Имя файла очищается и не может задавать путь. Не раскрывать пользователю
  внутренний путь хранения.
- Документ хранится безопасно и привязан к конкретному кандидату. Не хранить
  файлы в публичном frontend-каталоге и не отдавать их без проверки сессии,
  CSRF/прав и принадлежности кандидата.
- Скачивание идёт через защищённый endpoint с `Content-Disposition` и исходным
  безопасным именем. Перед скачиванием пользователь может задать имя файла.
  Если имя/место выбираются браузером, использовать стандартный диалог сохранения
  Windows и не пытаться подменять локальный путь на сервере.
- После скачивания интерфейс должен показать понятную кнопку «Открыть скачанный
  файл» или максимально близкое к этому действие. Важно: обычный браузер не может
  универсально открыть произвольный локальный путь системной программой. Не
  изображать невозможную гарантию: использовать поддерживаемый браузером механизм
  (File System Access API при наличии для выбора имени/места и подтверждения
  записи; fallback — скачивание браузером). Учитывать localhost и HTTP LAN:
  API выбора места может быть недоступен в небезопасном контексте. Отмена сохранения
  не считается успехом. Этот API не запускает Word/Acrobat. «Открыть скачанный»
  показывать только при реальной возможности открыть именно сохранённые байты;
  серверный просмотр называть «Просмотреть вложение», не выдавать его за локальный.
  Для открытия в Word использовать действие «Открыть» в загрузках браузера и
  короткую подсказку. Явно описать это ограничение в PR и UI. Не применять небезопасные
  `file://`-хаки.
- Пользователь может удалить вложение только при наличии соответствующего права;
  удаление аудируется. Физическое удаление и retention согласовать с текущей
  политикой проекта, не удалять данные молча.
- При поиске кандидата в существующей картотеке карточка должна показывать его
  вложения; поиск должен находить самого кандидата по имеющимся полям, но не
  индексировать содержимое DOCX/PDF без отдельного решения.

## Хранение и безопасность

- Сначала изучить действующий backend, модель прав, backup/restore и Docker
  volumes. Выбрать реализацию, совместимую с текущей схемой и пилотом: защищённое
  файловое хранилище вне публичных каталогов либо BLOB в PostgreSQL.
- Учитывать backup/restore, обновление и uninstall: вложения не должны случайно
  исчезать при обновлении; поведение uninstall и хранения данных документировать.
- Ограничить размер одного файла и общее количество/объём на кандидата. Лимиты
  вынести в конфигурацию с безопасными значениями для пилота.
- Не логировать содержимое файла, ФИО из документа, токены и локальные пути.
- Проверить DOCX как ZIP-контейнер: не распаковывать небезопасно, не допускать Zip
  Slip. Не выполнять макросы и внешние связи. Для PDF не выполнять JavaScript.
- Скачать/просмотреть документ может только пользователь, которому сервер уже
  разрешает доступ к кандидату. Скрытие кнопки во frontend не является защитой.
- Добавить audit-события загрузки, скачивания и удаления без текста документа и
  без лишних персональных данных.

## Технические требования

- Новая миграция должна иметь upgrade/downgrade и PostgreSQL integration test с
  нуля. Не ломать старые миграции.
- API должен поддерживать список, загрузку, скачивание и удаление вложения с
  корректными кодами 401/403/404/409/413/415.
- Загрузка должна быть потоковой или иметь контролируемый лимит памяти; не
  загружать неограниченный файл целиком в RAM.
- Конфликты имён, повторная загрузка и параллельное удаление обработать явно.
- Не добавлять внешние библиотеки без необходимости; если библиотека нужна,
  закрепить версию и объяснить её назначение.

## Тесты обязательны

- Backend unit/integration: разрешённые DOCX/PDF, неверная сигнатура, слишком
  большой файл, запрещённый тип, очистка имени, path traversal, права разных
  ролей, скачивание без утечки пути, удаление, аудит, backup/restore контракт.
- Frontend Vitest: список, загрузка, прогресс/ошибка, имя файла, скачивание,
  кнопка открытия/fallback, недоступность действий без прав.
- Использовать обезличенные минимальные DOCX/PDF fixtures, созданные специально
  для тестов. Не коммитить файл Баева К.Р. и никакие реальные ПДн.
- Полный CI, миграции и Compose smoke должны остаться зелёными.

## Ограничения и отчёт

- Не трогать `installer/`, `infra/windows/`, импорт Excel и папку `Скрины проблем программы`.
- Это сознательно расширяет прежнюю границу Phase 16 «без файлов». Зафиксировать
  новую границу в документации проекта и не оставлять противоречивую формулировку,
  будто файловые вложения по-прежнему запрещены.
- В PR коротко описать хранение, права, лимиты, backup/restore, ограничения
  браузера для открытия локального файла и ручные шаги проверки.
