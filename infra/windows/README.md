# Движок HR Manager для Windows (phase 12)

Локальный пилот HR Manager на одной машине Windows 10/11 x64: Postgres,
бэкенд, фронтенд, worker и бэкапы в Linux-контейнерах Docker Desktop/WSL2,
единый проект Compose `hr-manager-pilot`, публикация только на
`http://127.0.0.1:<port>`.

Обычному пользователю движок не нужен: он устанавливает приложение через
графический мастер `HR Manager Setup.exe` (см. `installer/README.md`) и
работает в браузере. Движок — единая точка автоматизации под мастером, а
также консольный инструмент администратора (установка, обновление,
диагностика). **Никаких команд Docker/Postgres/Alembic вручную.**

## Действия

```
powershell -ExecutionPolicy Bypass -File hr-manager.ps1 -Action install
powershell -File hr-manager.ps1 -Action start | stop | status | open | restart
powershell -File hr-manager.ps1 -Action update -ReleaseDir D:\hr-manager-1.1.0
powershell -File hr-manager.ps1 -Action update-preview -ReleaseDir D:\hr-manager-1.1.0
powershell -File hr-manager.ps1 -Action diagnostics [-Json]
powershell -File hr-manager.ps1 -Action uninstall [-PurgeData]
powershell -File hr-manager.ps1 -Action resume
# Диагностика Docker, supervisor и трей
powershell -File hr-manager.ps1 -Action prepare            # проверить среду; запускается только уже установленный Docker Desktop
powershell -File hr-manager.ps1 -Action docker-status      # состояние Docker Desktop и Engine
powershell -File hr-manager.ps1 -Action docker-start       # запустить уже установленный Docker Desktop и дождаться Engine
powershell -File hr-manager.ps1 -Action supervise          # один supervisor (mutex), файл состояния
powershell -File hr-manager.ps1 -Action tray               # значок в трее (Windows Forms)
powershell -File hr-manager.ps1 -Action autostart [-Enable|-Disable]
```

| Действие | Что делает |
|---|---|
| `install` | Полная установка/восстановление: предполётные проверки, генерация секретов (однократно), копирование снимка, сборка образов, подъём контейнеров, первый запуск. Требует вручную установленный и запущенный Docker Desktop; если его нет, движок завершится с официальной ссылкой и не запустит установщик Docker. |
| `start` / `stop` | Запуск/остановка контейнеров. Данные (тома `pilot_pgdata`, `pilot_backups`) сохраняются. |
| `status` | Короткий статус: контейнеры, готовность фронтенда/бэкенда, версия в работе. |
| `open` | Открыть приложение в браузере (запускает, если остановлено). |
| `update` | Обновление из доверенного каталога релиза `-ReleaseDir` (см. «Обновление»). |
| `diagnostics` | Агрегированная диагностика (см. «Состояния»). Всегда с редакцией секретов. |
| `uninstall` | Остановка и снятие контейнеров; **данные и бэкапы сохраняются**. `-PurgeData` удаляет только `pilot_pgdata` после точной фразы-подтверждения, свежего шифрованного бэкапа и успешного deep check; отказ от backup или ошибка запрещают удаление. `pilot_backups` и StateDir сохраняются; `down -v` не используется. Docker Desktop/WSL2 не удаляются никогда. |
| `resume` | Возобновить прерванное обновление по журналу фаз или незавершённую первичную установку HR Manager. Не возобновляет и не управляет ручной установкой Docker Desktop. |

Параметры: `-SourceDir`, `-ReleaseDir`, `-InstallDir`
(по умолчанию `%LOCALAPPDATA%\Programs\HRManager`), `-StateDir`
(по умолчанию `%LOCALAPPDATA%\HRManager`), `-Port`
(по умолчанию 8080; `-Port` > `HRM_PILOT_PORT` > 8080),
`-NonInteractive`, `-OpenBrowser`.

## Порт публикации и занятый порт (регрессия 12.10.2026)

Порт публикации — не «настройка по умолчанию», а применённое состояние.
Если порт занят ЧУЖИМ приложением (например, старым development-стеком
HR Manager на 8080), движок подбирает свободный порт и применяет его
согласованно — во всех местах сразу:

1. `Invoke-HrmDockerPrepare` (engine\Docker.psm1) возвращает эффективный
   порт (`port`, `port_changed`); раньше свободный порт только упоминался
   в журнале, а `$port` не менялся — стек публиковался на занятом порту,
   и в браузере оказывался чужой стек;
2. `Sync-HrmPortAfterPrepare` (engine\Install.psm1) пишет порт в запись
   установки (`installed.json`);
3. `pilot.env` перегенерируется с `HRM_PILOT_PORT` = этот порт
   (`Write-HrmPilotEnv` без явного порта берёт его из записи установки);
4. Compose (`infra\compose.pilot.yml`) публикует фронтенд на нём;
5. supervisor (`supervisor.json`: `port`, `url`), readiness, ссылка
   первого запуска и ярлык читают порт из записи установки.

Порт, занятый СОБСТВЕННЫМ работающим пилотом, сохраняется: он проверяется
запросом `/api/ops/status` (обязательно `environment=pilot`). Чужой
`development`-стек пилотом не считается, автоматически ничего не
останавливается и не удаляется. Если свободного порта нет (проверяются
20 портов подряд), установка честно останавливается с состоянием
`port_busy` и понятным сообщением — публикации на занятом порту не будет.

## Принадлежность и готовность (ярлык, `open`, readiness)

HTTP 200 на порту — это ещё не наше приложение:

- `Test-HrmBackendReady` требует, чтобы `/api/health` вернул JSON с
  `environment=pilot` (запрос идёт через фронтенд-прокси, то есть
  проверяется весь стек, а не отдельная программа на порту);
- `Wait-HrmReady -ExpectedReleaseSha <sha>` дополнительно требует, чтобы
  `/api/ops/status` сообщил ожидаемый `release_sha`; при расхождении
  выбрасывается понятная ошибка («в работе ДРУГАЯ версия…»), а не
  открывается чужое или устаревшее приложение;
- `Open-HrmApp` (ярлык, `-Action open`) проверяет состояние стека
  (`partial`/`degraded` больше НЕ считаются запущенным приложением),
  готовность и принадлежность. Если стек не полностью запущен или
  файлы/образы разошлись с версией в работе, приложение приводится к
  установленному снимку (пересборка образов и пересоздание контейнеров,
  тома не удаляются), и только затем открывается браузер.

## Первый запуск

Движок сам **не создаёт** администратора. После подъёма контейнеров
выполняется одноразовый обмен по loopback:

1. Движок читает данные владельца (фамилия, роль, часовой пояс) из
   защищённого файла `%LOCALAPPDATA%\HRManager\first-run-input.json`
   (его пишет мастер установки) или запрашивает их в консоли.
2. `POST http://127.0.0.1:<port>/api/setup/owner/claim` с заголовком
   `X-Real-IP: 127.0.0.1` и одноразовым токеном обмена. Бэкенд хранит
   только SHA-256 токена (одноразовый, атомарно потребляемый, аудируемый,
   отключается после создания владельца).
3. Бэкенд выдаёт одноразовый тикет; движок открывает браузер на
   `http://127.0.0.1:<port>/#setup=<ticket>`. Пароль (не менее 12 символов),
   часовой пояс, рабочие дни и тихие часы пользователь задаёт в защищённом
   UI первого запуска. Единственная учётная запись получает роль `admin` и
   явный грант `pilot_full_access` (все скоупы phase 11); режим работы —
   поле профиля (`users.working_mode`), а не ослабление RBAC. Позже можно
   назначить обычные роли.

В неинтерактивном режиме (`-NonInteractive`) браузер не открывается, а
одноразовая ссылка записывается в защищённый файл
`first-run-url.txt` в каталоге состояния. Флаг `-OpenBrowser`
(используется мастером установки) сохраняет ссылку **и** открывает браузер.

## Секреты

| Секрет | Формат | Назначение |
|---|---|---|
| `HRM_POSTGRES_PASSWORD` | 32 hex | пароль БД |
| `HRM_SIGNING_KEY` | 64 hex | подпись сессий/CSRF (`SECRET_KEY`) |
| `HRM_BOOTSTRAP_ADMIN_PASSWORD` | 32 hex | запасной bootstrap-пароль (при обмене не используется) |
| `HRM_BACKUP_KEY` | 64 hex | ключ шифрования бэкапов (`BACKUP_ENC_KEY`) |
| `HRM_BACKUP_KEY_ID` | `pilot-` + 8 hex | идентификатор ключа бэкапа |
| `HRM_EXCHANGE_TOKEN` | 32 hex | одноразовый токен первого запуска |

- Генерируются **один раз** (`secrets.json` в каталоге состояния),
  при повторных запусках никогда не перегенерируются.
- Хранятся только в каталоге состояния с ACL «только текущий
  пользователь» (`<user>:(OI)(CI)F` для каталога и `<user>:F` для файлов);
  в репозиторий они не добавляются и в `.gitignore` есть правило на случай
  копии рядом с кодом.
- В контейнеры передаются только через `docker compose --env-file
  <state>\pilot.env` (файл тоже под ACL). **Никогда** — в командной строке
  процесса, выводе, журналах, диагностике, URL.
- После создания владельца токен обмена заменяется случайной
  неиспользуемой заглушкой (`retired-…`): compose-файл требует непустое
  значение `${HRM_EXCHANGE_TOKEN:?}`, а сервер его не применяет (обмен
  закрыт, пользователи существуют).
- Весь вывод проходит редакцию секретов (`<redacted>`).

## Предполётная проверка

Честные проверки без молчаливых «согласий»:

1. Windows 10/11; 2. PowerShell 5.1+ x64; 3. Docker Desktop и Docker CLI должны быть установлены вручную;
4. демон Docker (Docker Desktop запущен); 5. Docker Compose v2 ≥ 2.24
(тег `!reset`); 6. порт свободен (порт собственного работающего пилота —
норма); 7. каталог состояния доступен для записи; 8. свободное место
≥ 5 ГБ; 9. конфигурация compose валидна (`docker compose … config
--quiet` с env-файлом).

### Docker Desktop — только ручная установка

Движок HR Manager **не скачивает, не устанавливает и не запускает установщик**
Docker Desktop и не принимает лицензию от имени пользователя. Установите Docker
Desktop самостоятельно с [официального сайта Docker](https://www.docker.com/products/docker-desktop/),
прочитайте и примите лицензию сами, затем запустите Docker Desktop и дождитесь
готовности Docker Engine.

Если дистрибутив содержит `DockerDesktopInstaller.exe` рядом с `Setup.exe`, мастер
может скопировать этот внешний sidecar в `{app}\docker\DockerDesktopInstaller.exe`.
`build.ps1` помещает один и тот же объект `docker_desktop_installer` с URL/available/
SHA256 в `{app}\release.json` и `release-manifest.json`; `SHA256SUMS.txt` тоже
фиксирует sidecar, если он есть. Движок показывает локальный путь только при
`available=true` и совпадении фактического `Get-HrmFileSha256` с SHA256 из
`release.json`. При отсутствующем pin/метаданных или несовпадении путь скрывается,
пишется предупреждение `warn` и остаётся официальный URL — hash-проверка сама по
себе не создаёт отдельный отказ установки. HR Manager никогда не запускает sidecar;
запустить файл при желании можно только самостоятельно.

Подпись проверяется вне движка только для локального файла:
`infra/windows/tools/Assert-HrmDockerInstallerSignature.ps1` требует явный SHA256,
проверяет хеш, Authenticode `Status=Valid`, точный Subject и thumbprint Docker и
возвращает `0` (совпало), `1` (сигнатура/hash/publisher alert) или `2` (не удалось
проверить). Он не скачивает файл и не вызывается движком. `pilot-release` запускает
его после pinned download только при заданном SHA256 в ручном `workflow_dispatch`;
PR/push sidecar не скачивают. Полная команда и exact pins приведены в
`installer/README.md`.

Ручная установка Docker может потребовать UAC или перезагрузки Windows. HR Manager
не создаёт для этого `docker-pending.json` и не возобновляет установку Docker после
перезагрузки. Действие `resume` относится только к прерванной установке/обновлению
самого HR Manager. После готовности Engine откройте HR Manager: если Setup успел
скопировать файлы, но не создал `installed.json`, ярлык завершит первичную настройку
из этих файлов. `prepare` только проверяет среду, а `start` требует существующую
запись установки; ни одна из команд не устанавливает Docker.

Таймаут пробы **не выдаётся** за отсутствие Docker (дефект P5.3): проверки
«Docker CLI» и «демон Docker» различают истёкшее ожидание (`TimedOut`, код 124)
и отказ команды. «Docker CLI не ответил за N с: программа найдена и запущена, но
ответ не получен» — это ожидание готовности/перезапуск Docker Desktop, а не
переустановка; «Демон Docker не ответил за N с» — это ожидание ответа, а не
отсутствие работающего демона (заново запускать Docker Desktop не требуется).
Прежние тексты при таймауте отправляли человека переустанавливать Docker Desktop.
Отсутствие CLI (код 127) по-прежнему сообщает «Docker CLI не найден» с
инструкцией ручной установки с официального сайта Docker.

### Порядок «prepare → preflight» (первичная установка)

`Invoke-HrmDockerPrepare` идёт ПЕРЕД `Assert-HrmPreflight`
(`engine\Install.psm1`). Это компромисс, и вот почему он выбран:

1. **Порт.** Prepare первым определяет эффективный порт публикации: занятый
   чужим приложением порт заменяется свободным. Предполётная проверка
   выполняется уже с этим портом и поэтому не отказывает на «порт занят» там,
   где выход есть. Обратный порядок давал бы ложный отказ ещё до подбора.
2. **Среда.** Предполётные проверки CLI, демона и Compose выполняются после
   `prepare`. Если Docker Desktop отсутствует, prepare завершится отказом с
   ручными шагами; автоматического скачивания/установки нет. Если Desktop уже
   установлен, prepare запускает только его и ждёт Engine.
3. **Порядок.** До предполётных проверок выполняются только выбор свободного
   порта и диагностика/запуск имеющегося Docker Desktop. Ничего не отключается:
   preflight выполняется следом, может отказать до `compose up` и до записи
   установки; сам prepare проверяет WSL2, виртуализацию и свободное место.

Альтернатива «preflight раньше prepare» отклонена: она отказала бы на
неподготовленной среде до попытки запустить уже установленный Docker Desktop
и на занятом порту — до подбора свободного порта.

Поиск Docker Desktop учитывает и пользовательскую установку без
администратора: `%LOCALAPPDATA%\Programs\DockerDesktop\Docker Desktop.exe`
и CLI `%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin\docker.exe`
(подтверждено на живой машине 12.10.2026), а также реестр,
`%ProgramFiles%` и PATH. В постоянный журнал пишутся выбранный путь,
факт запуска, PID и результат; если процесс Docker Desktop завершился
сразу после запуска, движок сообщает это с кодом возврата и причиной
вместо неинформативного ожидания 300 секунд.

Найденный путь CLI — это и есть путь вызова (регрессия 12.10.2026,
коммит R2): резолвер `Get-HrmDockerCliPath` (`engine\Docker.psm1`) один
на движок, а `Invoke-HrmDocker` (`engine\Common.psm1`) разрешает имя в
этот путь и запускает его через `Invoke-HrmExternal`. Раньше вызовы шли
голым именем и резолвились только через `PATH` процесса: при
пользовательской установке Docker Desktop детекция сообщала
«установлен», а вызов падал с `Win32Exception` или заканчивался
таймаутом (особенно из elevated-процесса). Если CLI не найден нигде,
`Invoke-HrmDocker` возвращает структурированный отказ (`ExitCode 127`,
понятный текст и перечень проверенных мест) вместо исключения
`Process.Start`: диагностика честно сообщает `missing`, готовность
Engine → `false`, предполётная проверка — отказ с текстом. Выбранный
путь пишется в постоянный журнал один раз на процесс; без
`-IgnoreExitCode` отказ остаётся исключением, иначе вызовы вида
`Invoke-HrmCompose … | Out-Null` молча продолжали бы работу без движка
контейнеров.

## Обновление

- **Доверенная граница:** `-ReleaseDir` — каталог, куда пользователь
  положил проверенный снимок релиза (`infra/`, `backend/`, `frontend/`,
  `release.json` с `release_sha`), например распакованный официальный
  `HR Manager Setup.exe` или копию тега репозитория. Всё содержимое
  каталога считается доверенным кодом.
- **Блокировка:** `update.lock` в каталоге состояния; свежая блокировка
  (< 4 ч) не пускает параллельное обновление, старая (прерванное
  обновление) разрешает перехват через `resume`.
- **Журнал фаз:** `update-journal.json` → `prepare → backup → build →
  switch → migrate → smoke → done`; после сбоя/перезагрузки `resume`
  продолжает с прерванной фазы (бэкап не повторяется).
- **Бэкап-ворота:** перед миграцией — `backup-now` + `backup-check
  --deep` (проверка целостности шифрованного бэкапа). Ошибка
  останавливает обновление до миграции.
- **Сборка без разрушения:** новые образы собираются, работающее
  приложение не останавливается; `up -d` пересоздаёт контейнеры. Образы
  несут метку `hrmanager.release_sha` (`build.labels` в
  `infra\compose.pilot.yml`), поэтому после сборки видно, из какого
  снимка они собраны.
- **Миграция:** однократный `alembic upgrade head`. Даунгрейд БД не
  выполняется никогда.
- **Smoke:** ограниченное ожидание готовности фронтенда и `/api/health`,
  затем `/api/ops/status` (release_sha, миграции), `worker-check`,
  сверка головы миграций (отсутствие дрейфа). Только после прохождения
  предыдущая версия считается заменённой.
- **Откат:** при провале — возврат к предыдущим образам (перетегирование
  по сохранённым ID), приложение снова работает на прежней версии; БД не
  даунгрейдится (схема совместима вверх). Если база уже ушла на ревизию,
  которой прежний образ не знает, откат НЕ запускает контейнеры вслепую
  (см. «Схема базы и образ»), а сообщает об этом и сохраняет журнал и
  бэкапы.

### Образ ↔ снимок ↔ база (регрессия 12.10.2026)

`Start-HrmStack` (engine\Compose.psm1) перед запуском контейнеров:

1. **Согласует `pilot.env` со снимком:** `release_sha` и порт публикации
   приводятся к значениям развёрнутого снимка (`{app}\release.json`) и
   записи установки. Иначе метка новой сборки осталась бы старой, а
   публикация вернулась бы на прежний порт;
2. **Сверяет образ со снимком:** если метка `hrmanager.release_sha` образа
   не совпадает с `release.json` в `{app}` (так бывает, когда Setup.exe уже
   скопировал новые файлы, а движок не успел обновить образы, или когда
   откат вернул старые теги), образы пересобираются — при любом состоянии
   стека, включая `partial`/`degraded`. Раньше в этих состояниях
   `Repair-HrmStack`/`up` поднимали контейнеры из устаревших образов;
3. **Проверяет схему базы против образа ДО запуска приложения:** ревизия из
   `alembic_version` должна быть известна alembic-скриптам образа (для
   остановленного стека контейнер базы временно поднимается только для
   чтения ревизии). Положительно установленная несовместимость — отказ
   `schema_incompatible` с ревизиями базы и образа и подсказкой, что делать;
   никакой crash-loop «Can't locate revision identified by '0022'» и
   никакого удаления данных. Любая неопределённость (нет тома, база не
   читается, образ недоступен) запуск не блокирует и честно сообщается в
   журнале.

### Установка поверх существующей (`-Action install`)

Поведение движка в этой ветке (важно: код возврата мастера Inno Setup —
это код мастера, а не подтверждение успешной установки, потому что движок
запускается мастером отдельной записью `[Run]`):

- **файлы в `{app}` уже заменены мастером** — снимок прежней версии
  сохраняется помощником мастера ДО перезаписи (см. `snapshot-previous`);
- **версия в `SourceDir`/`{app}` отличается от записи установки** —
  выполняется ПОЛНОЕ обновление: снимок прежней версии → бэкап + deep
  check → сборка новых образов → замена файлов → миграция → smoke;
- **та же версия** — движок не «просто перезапускает существующий стек», а
  приводит его к развёрнутому снимку: согласует `pilot.env`, пересобирает
  образы при расхождении метки со снимком, пересоздаёт контейнеры
  (`up -d`, `partial`/`degraded` не считаются запущенным приложением),
  после чего подтверждает готовность И принадлежность ожидаемому
  `release_sha`. Повторная установка ничего не удаляет: тома
  `pilot_pgdata`/`pilot_backups` и секреты сохраняются;
- **идёт чужое приложение на порту** — порт заменяется свободным (см.
  выше); чужие стеки не останавливаются и не удаляются автоматически.

## Состояния диагностики

`-Action diagnostics` различает обязательные состояния контракта:

| Поле | Значения |
|---|---|
| `docker` | `missing` (нет CLI) / `daemon_down` / `ok` |
| `app` | `stopped` / `starting` / `ready` / `degraded` |
| `database` | `unknown` / `ok` / `down` |
| `migration` | `ok` / `drift` / `unknown` (+ текущая/ожидаемая ревизии) |
| `worker` | `ok` / `stale` / `unknown` |
| `backup` | `ok` / `stale` / `failed` / `missing` / `unknown` |
| `version` | `match` / `mismatch` / `unknown` (установленная vs работающая) |
| `smtp` / `telegram` | `not_configured` (в пилоте внешние каналы выключены по умолчанию) |

Источники: `GET /api/ops/status` и `GET /api/ops/backup-health` через
loopback-прокси (вывод проходит редакцию секретов; 503 — честный сигнал деградации).
Сам отчёт для поддержки редакцию не переоценивает: секреты, адреса почты и телефоны
вырезаются регулярками, а имена и свободный текст из журналов — нет, поэтому внутрь
архива кладётся `README-ПЕРЕД-ОТПРАВКОЙ.txt` с требованием просмотреть архив перед
отправкой владельцу по закрытому каналу.

## Модель доверия loopback (кратко)

Пилот обслуживает обычный `http://127.0.0.1` — трафик не покидает машину,
поэтому сессионные/CSRF-куки не-Secure (`SESSION_COOKIE_SECURE=false`),
но все остальные производственные ограничения сохранены: `APP_DEBUG=false`,
сильные сгенерированные секреты, без dev-паролей, внешние SMTP/Telegram
выключены, порт опубликован только на `127.0.0.1`. Продакшн-контур
(`infra/compose.prod.yml`) не ослаблен и по-прежнему требует Secure-куки.
Подробности — в заголовке `infra/compose.pilot.yml`.

## Ревизия стабильности установщика (12.10.2026)

Пилотный отказ («Состояние: Запускается», «Предпроверка не пройдена: compose…»,
десятки `powershell.exe`, `vmmemWSL` ≈ 1.8 ГБ) разобран по первопричинам в
`docs/windows-installer-stability-2026-10-12.md`. Ниже — как движок ведёт себя
после исправлений и как это проверить на машине. Детали прежнего ожидания/запуска
Docker installer в том датированном разборе исторические: в актуальном движке
остались только таймауты внешних Docker/Compose-команд и ожидание Engine.

### Таймауты и отмена внешних команд

Каждая внешняя команда идёт через `Invoke-HrmExternal` (`engine/Common.psm1`) и
имеет потолок ожидания. Раньше `WaitForExit()` вызывался без аргумента, а трубы
читались последовательно (`ReadToEnd` stdout, затем stderr): зависший CLI
контейнеров держал процесс движка вечно, а полный буфер stderr (~64 КБ) давал
deadlock родителя даже без зависания. Так в диспетчере задач накапливались
десятки `powershell.exe`.

Контракт теперь:

- stdout и stderr читаются **асинхронно и параллельно** (`ReadToEndAsync` до
  ожидания), stdin пишется асинхронно и ограниченно;
- ожидание ограничено: `WaitForExit(таймаут)`;
- по таймауту останавливается **дерево** процессов (`Stop-HrmProcessTree` →
  `taskkill.exe /PID <pid> /T /F`): у CLI контейнеров есть потомки (`wsl.exe`,
  buildx), и убийство одного корня оставляло их живыми. `.NET Framework`
  (Windows PowerShell 5.1) не умеет убивать дерево (`Process.Kill($true)` появился
  только в .NET Core), поэтому используется системная команда; это единственный
  вызов `taskkill.exe` в движке, он внесён в белый список внешних команд
  (`tests/static.tests.ps1`) с обоснованием;
- если `taskkill` не сработал (нет прав), корень закрывается штатным `Kill()`;
- результат структурирован — `[pscustomobject]@{ Name; ExitCode; Stdout; Stderr; TimedOut;
  TimeoutSeconds }`, при таймауте `ExitCode = 124` (соглашение GNU `timeout`:
  отличается и от 127 «CLI не найден», и от кодов самой команды), а в `Stderr` и
  в журнал пишется объяснение и следующее действие; без `-IgnoreExitCode` то же
  сообщение становится единственным исключением;
- процесс освобождается (`Dispose`) в `finally` — дескрипторы не текут.

Классы таймаутов (`Get-HrmExternalTimeoutSeconds`) и их обоснование:

| Класс | Секунды | Что сюда попадает | Почему столько |
|---|---|---|---|
| probe | 60 | `docker --version`, `docker info`, `compose version/ps/config/ls`, `inspect`, `images`, `wsl --status/--list` | Это опрос состояния. Исправный Docker отвечает за секунды; 60 с — запас на холодный старт WSL2. Дальше ждать бессмысленно: среда не отвечает. |
| compose | 900 | `compose up/down/run/exec/logs/stop/start/restart/pull/push` | Запуск стека и миграции на пилотной машине. Четверть часа покрывает медленный диск и первый прогрев, но не позволяет «висеть вечно». |
| build | 3600 | `compose build` | Первая сборка образов тянет npm/pip-зависимости; на машине пилота это десятки минут. Час — потолок, после которого сборка считается зависшей. |
| kill | 20 | `taskkill.exe` | Остановка дерева обязана быть быстрой: она происходит, когда время уже потеряно. |
| default | 120 | `icacls.exe`, `git.exe`, `netsh` и прочее | Локальные служебные команды. |

Аргументы сопоставляются **точным элементом массива**, а не поиском подстроки в
склеенной командной строке: путь к compose-файлу может содержать слово `build`, и
команда получила бы чужой (часовой) таймаут. Порядок выбора: явный
`-TimeoutSeconds` вызывающего → `HRM_EXTERNAL_TIMEOUT_SECONDS` (аварийный шов) →
класс команды.

Ожидания готовности Docker остаются ограниченными: `Wait-HrmDockerEngine` —
300 с с интервалом 5 с, `Start-HrmDockerDesktop` — 300 с, `Wait-HrmReady` —
180 с. Таймаут относится к запуску уже установленного Docker Desktop и к
готовности Engine; HR Manager не создаёт/ожидает elevated installer process.
Самостоятельно запущенный Docker installer не контролируется и не завершается
движком.

Проверяется `tests/docker.tests.ps1`: отказ при отсутствии Docker включает
официальный URL; sidecar-путь виден только при совпадении hash с `release.json`, а
отсутствующий файл, отсутствующий pin и несовпадение SHA не запускают sidecar и не
превращаются в отдельную ошибку проверки. `static.tests.ps1` разбирает локальный
Authenticode tool и проверяет его BOM/pins, а также build/workflow contract;
диагностические проверки Engine, WSL2, портов, Compose и ожидания запуска остаются.

### Единственность цикла движка

Критерий приёмки: **два подряд входа в Windows (или повторный запуск `Setup.exe`)
дают один цикл движка**, а не два параллельных `compose build/up`.

- `Invoke-HrmSupervisorCycle` берёт именованный мьютекс
  `Local\HRManagerPilotEngineCycle` (имя — `Get-HrmEngineCycleMutexName`,
  переопределяется `HRM_ENGINE_CYCLE_MUTEX`). Мьютекс значка
  (`Local\HRManagerPilotSupervisor`) для этого **не** подходит: значок держит его
  всё время своей жизни, и цикл движка оказался бы запрещён навсегда.
- Затем проверяется `Test-HrmEngineOperationInFlight`: живая блокировка действия
  (`action.lock` с живым pid), свежая отметка мастера установки/обновления
  (`setup-run.json`, `update-journal.json`) или `supervisor.json` с `busy` и живым
  чужим pid. Отказ — честный: `{ ok = $false; state = "busy"; already_running =
  $true }` **без записи ошибки в состояние** (иначе вторая попытка затёрла бы ход
  настоящей операции, и значок показал бы «Ошибка» вместо «Запускается»).
- `hrm-tray.ps1` выполняет ту же проверку **до** порождения скрытого процесса
  движка и пишет в журнал «Движок не запускается: операция HR Manager уже
  выполняется (…)». Проверка и запуск **атомарны** (дефект P5.1):
  `Start-HrmTrayEngineProcess` (`engine/Tray.psm1`) берёт блокировку действия до
  порождения и передаёт её потомку — `Enter-HrmActionLock -Action "engine"` →
  `Start-HrmEngineProcess` → `Update-HrmActionLockProcess` (pid потомка). Раньше
  между проверкой и запуском второй значок (два входа в Windows подряд, повторный
  запуск `Setup.exe`) успевал пройти ту же проверку, и первые секунды работали
  два движка. Если pid потомка получить не удалось, блокировка снимается: запись
  без pid не описывает идущую операцию.
- Важная деталь: `busy` в `supervisor.json` значок пишет со **своим** pid (это
  обещание «операция началась»), поэтому внутри цикла движка проверка идёт с
  `-IgnoreBusyState` — иначе только что порождённый значком движок отказывал бы
  сам себе навсегда. Со стороны значка/спавнера `busy` с живым чужим pid
  учитывается как идущая операция.
- Блокировка действия (`Enter-HrmActionLock`) больше не «протухает» молча: пока
  pid владельца жив, блокировка держится, а при возрасте ≥ 60 минут
  (`ActionLockStallMinutes`) в журнал и в `supervisor.json` пишется состояние
  `error` с кодом `action_stalled`, pid операции и действием для человека
  (закрыть окно/завершить процесс в диспетчере задач и повторить). Мёртвый pid —
  блокировка снимается с записью в журнал.
- Повторный вход в свою блокировку разрешён: значок передаёт блокировку
  порождённому процессу (`action = "engine"`, pid процесса движка), и движок
  внутри действия (`open`, `restart`, …) входит в неё повторно. Раньше он
  отказывал сам себе, поэтому пункт меню «Открыть HR Manager» молча ничего не
  открывал (`Install.psm1`, `Enter-HrmActionLock -Action "open"` внутри
  `Start-HrmApp`). Повторный вход **перезаписывает** запись блокировки
  (дефект P5.2): владелец (`pid`) и отсчёт возраста (`started_at`) описывают
  процесс, который реально выполняет операцию, а не момент, когда значок её
  задумал. Без перезаписи процесс работал по записи, созданной другим процессом,
  а завершающий `Exit-HrmActionLock` удалял файл, описывавший решение значка:
  защита от второй операции исчезала, пока первая ещё шла, а порог «зависла»
  (≥ 60 мин) считался не от начала работы. Имя действия в записи сохраняется
  намеренно: служебную отметку `action = "engine"` читают другие процессы (отказ
  «Операция уже выполняется (engine)»), и по ней же разрешён повторный вход для
  той же операции (контракт D10 — «та же операция тем же процессом»). Чужая
  живая блокировка по-прежнему не пускает вторую операцию (перезапись возможна
  только для своего pid), и правило «зависла» работает только для чужого живого
  pid.

Проверено тестами: `tests/supervisor.tests.ps1` (мьютекс цикла занят другим
процессом → `busy` и ноль обращений к Docker; идущая установка → `busy`; блокировка
живого процесса не протухает; повторный вход; план значка `busy`; атомарное
порождение движка значком — блокировка существует в момент запуска процесса и
передаётся потомку, второй значок не порождает второй движок; перезапись
владельца и отсчёта возраста при повторном входе, сохранение служебной отметки
`engine` и отказ при чужой живой блокировке).

### Поведение значка в трее

- Тик не перекрывает сам себя: флаг `$refreshState.running` и `finally`-сброс.
  Раньше опрос каждые 5 с при медленном Docker накладывался друг на друга — это
  второй источник накопления процессов CLI.
- В Docker **не идут**, пока идёт операция значка или движка: состояние берётся из
  `supervisor.json` (его пишет выполняющийся процесс). Критерий приёмки: в покое
  не больше 4 опросов `docker compose ps` в минуту.
- Интервал опроса зависит от состояния (`Get-HrmTrayRefreshIntervalMs`): 5 с при
  запуске/идущей операции (обратная связь важнее экономии), 30 с в покое
  («Готово»), 60 с в остановке и в ошибке (делать нечего, состояние не меняется).
  Прежние 5 с в покое — это 12 опросов в минуту.
- Состояние значка — `Get-HrmTrayEffectiveState`: ошибка, записанная **другим**
  живым процессом (движком), не затирается планом «Запускается». Именно так
  возникал симптом пилота: движок отказал на предполётной проверке, а значок
  продолжал показывать «Запускается».
- Подряд идущие отказы считаются (`failure_count` в `supervisor.json`): после
  трёх (`SupervisorMaxConsecutiveFailures`) значок перестаёт бесконечно
  перезапускать движок и показывает «Ошибка» с причиной и действием (создать
  отчёт для поддержки; повторить вручную — пункт меню). Счётчик **не стирается
  началом новой попытки** (дефект P2): правило `Set-HrmSupervisorState` —
  явно заданное `-FailureCount` применяется как есть, `error` увеличивает
  счётчик, `ready` обнуляет, любое другое состояние (`starting`, `stopped`, …)
  **сохраняет** прежнее значение. Каждая попытка движка начинается записью
  `starting` (цикл, установка, продолжение операции, значок, диспетчер), а
  прежнее правило «не error — значит ноль» стирало историю отказов: счётчик ходил
  0 → 1 → 0 → 1, порог трёх подряд был недостижим, ветка `retry_exhausted` была
  мёртвой, и значок запускал движок на каждом входе в Windows при той же самой
  причине отказа. Обнуление — только успех (`ready`) и явное действие человека
  (пункт меню / `Reset-HrmSupervisorFailureCount`). Счётчик не накручивается
  ручной проверкой состояния («Проверить состояние» — не попытка запуска) и
  отсутствием установки («HR Manager не установлен» — не отказ движка).
- Всплывающее уведомление укладывается в пределы Windows (заголовок 63 символа,
  текст 255 — `Limit-HrmBalloonText`), и обрезается **причина**, а не весь текст:
  действие «Нажмите «Создать отчёт для поддержки»» остаётся в уведомлении всегда.
  Полный текст причины (перечень каталогов плагинов, версия, stderr пробы) — в
  пункте меню «Состояние», в журнале и в отчёте для поддержки.

Проверено тестами: `tests/supervisor.tests.ps1` (тик без Docker при идущей
операции, интервалы, «Ошибка» вместо «Запускается», остановка повторов, длинная
причина не вытесняет действие из уведомления, три настоящих прохода движка
«план значка → цикл → отказ» дают `retry_exhausted` и `start_engine = $false`).

### Плагин compose и CLI контейнеров: диагностика отказов

`Test-HrmComposeVersion` больше не сводит все отказы к одному тексту. Вердикты
(`Get-HrmComposeVersionVerdict`, чистая функция):

| Вердикт | Что означает | Что видит пользователь |
|---|---|---|
| `cli_missing` | CLI контейнеров не найден или не запускается (код 127) | какой путь пробовался и что делать (установка Docker Desktop с docker.com) |
| `plugin_missing` | CLI работает, команды `compose` в нём нет | **перечень проверенных каталогов плагинов** с содержимым и куда положить `docker-compose.exe` |
| `version_unparsable` | ответ получен, версия не разобрана | фактический ответ CLI |
| `version_old` | версия ниже 2.24 (в файле пилота используется тег `!reset`) | требуемая и найденная версии |
| `probe_failed` | другая ошибка (демон не запущен, права, таймаут) | stderr и код возврата |
| `ok` | compose ≥ 2.24 | версия |

Проверка **не ослаблена до предупреждения**: без compose стек не поднимется, а
«предупреждение» оставило бы пользователя с вечным «Запускается».

Каталоги плагинов compose на Windows (по убыванию приоритета, docker/cli#1534):

1. `%USERPROFILE%\.docker\cli-plugins` — ищется всеми версиями CLI;
2. `%ProgramData%\Docker\cli-plugins` — **не ищется Docker CLI 29.2.0 и новее**:
   каталог по умолчанию не создаётся, и любой локальный пользователь мог положить
   туда свой `docker-compose.exe` и получить повышение привилегий
   (GHSA-p436-gjf2-799p, исправлено docker/cli#6713). Поэтому в отказе движок
   честно пишет оба каталога и помечает, что новый CLI второй игнорирует — совет
   «положите плагин в ProgramData» был бы нерабочим.

Каталог **рядом с `docker.exe`** CLI не ищет (в отличие от Linux): класть плагин
туда бессмысленно. Имя файла плагина — `docker-compose.exe`.

Сравнение версий выполняет `Compare-HrmCliVersion` (числовые разряды как числа,
релиз больше предпоиска, пустая версия меньше любой). Прежнее правило
`major >= 2 -and minor >= 24` отвергло бы Docker Compose 5.1.0 (major 5, minor 1)
— то есть сломалось бы на первом мажорном обновлении плагина.

Выбор CLI контейнеров (`Select-HrmDockerCliCandidate`, правило зафиксировано
комментарием и тестом) — по убыванию приоритета:

1. кандидат из **того же корня установки**, что и `Docker Desktop.exe`
   (`Get-HrmDockerInstallRoot`);
2. наибольшая версия файла (`ProductVersion`, иначе `FileVersion`);
3. самая свежая дата изменения файла;
4. исходный порядок поиска (известные каталоги Docker Desktop, затем `PATH`).

Прежде возвращался **первый** найденный файл: при двух установках Docker Desktop
(устаревшая машинная в `Program Files` и актуальная пользовательская в
`%LOCALAPPDATA%\Programs\DockerDesktop`) детекция считала Docker установленным по
одной установке, а вызовы шли в CLI другой — версии расходились, плагин compose
мог отсутствовать, и отказ не объяснял причину.

Все найденные кандидаты пишутся в журнал **один раз на процесс** рядом с выбранным
путём (`Resolve-HrmDockerCli` в `Common.psm1`), а полный набор фактов (пути,
источник, версии файлов, корни установок, правило выбора, проба `--version`,
каталоги плагинов) доступен через `Get-HrmDockerCliFacts` и попадает в
`-Action diagnostics` (`docker_cli`, `docker_cli_candidates`,
`docker_cli_chosen_reason`, `compose_reason`, `compose_plugin_found`,
`compose_plugin_dirs`). Проба версии выполняется только в диагностике и только для
выбранного CLI: проба всех кандидатов на горячем пути — это лишние процессы CLI,
то есть ровно тот симптом, который чинится.

Кэш выбранного пути (`Reset-HrmDockerCliChoiceCache`) хранит только **успешный**
выбор и сбрасывается перед ожиданием готовности Docker Engine: после запуска
или перезапуска установленного Desktop выполняется свежая диагностика CLI.

### Установка не завершается «наполовину»

Запись установки (`installed.json`) пишется **после** полной предполётной
проверки (включая доступность compose и валидность конфигурации). Раньше запись
создавалась первой: при отсутствующем плагине compose установка «завершалась» с
записью, но без работающего стека — значок показывал «Запускается» (запись есть,
приложения нет), а повторный запуск `Setup.exe` шёл по ветке обновления. Теперь:

- отказ предполётной проверки останавливает установку **до** записи;
- причина попадает в само сообщение (`Assert-HrmPreflight` перечисляет проваленные
  проверки с их текстом, обрезка 300 символов — полностью она остаётся в журнале и
  в отчёте для поддержки);
- отказ записывается в `supervisor.json` как `error` (значок показывает «Ошибка» с
  действием), а не остаётся «Запускается»;
- ветка повторной установки тоже проходит предполётную проверку до запуска стека.

### Память WSL2 (`vmmemWSL`)

Ожидаемый диапазон при работающем стеке пилота — **1–2 ГБ**: `vmmemWSL` — это
виртуальная машина WSL2, внутри которой живут демон Docker, контейнеры пилота
(Postgres, backend, frontend, worker) и кэш сборки образов. WSL2 по умолчанию
разрешено занимать до 50% ОЗУ хоста, поэтому 1.8 ГБ на машине с 8–16 ГБ — норма,
а не утечка HR Manager. Наблюдаемое значение — факт диагностики
(`wsl_memory_mb`, `wsl_memory_processes`, `host_memory_total_mb`,
`host_memory_free_mb` в `-Action diagnostics`), а не дефект.

Что делает движок, чтобы память не росла из-за него самого:

- единственный цикл движка (мьютекс + блокировка действия) — нет параллельных
  `compose build/up`, которые удваивают нагрузку на Docker и WSL2;
- значок не опрашивает Docker при идущей операции и опрашивает редко в покое — нет
  накопления процессов CLI, каждый из которых держит память;
- зависшие процессы CLI и их потомки останавливаются деревом по таймауту.

Чего движок **не делает никогда**: не удаляет и не пересоздаёт окружение
пользователя (контейнеры, тома, дистрибутивы WSL, `wsl --shutdown`,
`wsl --unregister`), не правит `.wslconfig`. Ограничение памяти WSL2 — решение
владельца машины; пилоту это не требуется.

### Сбор фактов с пилотной машины (Этап 1)

`infra/windows/tools/Collect-HrmPilotFacts.ps1` — единственный скрипт, который
нужно запустить на машине с проблемой **до** любых изменений:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File infra\windows\tools\Collect-HrmPilotFacts.ps1
```

Он снимает все факты, по которым движок принимает решения: каждый найденный CLI
контейнеров и его `--version`, `docker compose version --short` с полным stderr и
кодом возврата, содержимое каталогов плагинов, `docker info`, `wsl --status` /
`--list --verbose` / `--version`, память `vmmemWSL` и топ процессов, **все**
`powershell.exe` через `Get-CimInstance Win32_Process` (Id, ParentProcessId,
CreationDate, CommandLine, рабочий набор), контейнеры и compose-проекты, список
файлов `%LOCALAPPDATA%\HRManager` с содержимым JSON-состояний и хвостами
журналов, а также план значка и признак идущей операции.

Скрипт ничего не устанавливает, не останавливает и не удаляет; содержимое
`secrets.json`, `pilot.env`, `license_public_key.b64` и `first-run-input.json` не
читается, остальной текст проходит редакцию секретов (`Redact-HrmText`). Каждая
внешняя команда ограничена таймаутом, поэтому на «подвешенной» машине скрипт
завершится, а не зависнет вместе с ней. Результат — JSON-файл (путь печатается) и
короткая сводка. Файл содержит пути машины (в них — имя пользователя): передавайте
его разработчику, не публикуйте в открытых тикетах.

### Наблюдатель канала обновлений

`Start-HrmChannelWatch` (`engine/Channel.psm1`) — блокирующий, но ограниченный
цикл: предел числа циклов (`-MaxCycles` / `HRM_CHANNEL_WATCH_MAX_CYCLES`), предел
времени (`-MaxMinutes` / `HRM_CHANNEL_WATCH_MAX_MINUTES`), файл-сигнал остановки
`channel-watch.stop` (проверяется и между циклами, и во время сна — поэтому
остановка не ждёт полный интервал) и выход при замене pid-файла другим
наблюдателем. `Stop-HrmChannelWatch` пишет сигнал **до** попытки `Stop-Process`,
поэтому остановка работает и без прав на завершение процесса. Единственный путь
запуска — явная команда человека или инструмента:
`hr-manager.ps1 -Action channel -Watch` (одноразовая проверка — без `-Watch`).
Пределы наблюдателя задаются ключами самой входной точки (`-MaxCycles`,
`-MaxMinutes`; дефект P4 — раньше комментарий к `param` обещал эти ключи, а в
`param` их не было, и ложная документация расходилась с кодом) либо переменными
окружения: насквозь переданный `0` означает «не задано», и тогда действует
переменная окружения. Значения по умолчанию не изменены.
Прежде цикл был `while ($true)` без единого выхода, а функция-спавнер в
`Common.psm1` не вызывалась ниоткуда (мёртвый код удалён); комментарий в
`installer/installer.iss` утверждал, что наблюдатель «запускается supervisor'ом»,
что не соответствовало коду — исправлен.
