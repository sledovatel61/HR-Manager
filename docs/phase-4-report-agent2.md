## Что сделано

### Backend: контракт передачи ответственности

- **Миграция `0004_candidate_transfers`** (после `0003_candidates`,
  обратимая): таблица `candidate_transfers` — неизменяемая бизнес-история
  (инициатор, старый и новый ответственные, причина, время), CHECK
  `ck_candidate_transfers_reason_not_blank`, FK: кандидат `CASCADE`,
  пользователи `RESTRICT`, индексы. Audit log остаётся журналом
  безопасности и **не** является бизнес-историей кандидата.
- **`POST /candidates/{id}/transfer`** (`{new_owner_user_id, reason}`):
  - одна транзакция: проверка видимости (чужой/удалённый — принятый 404),
    блокировка строки `SELECT … FOR UPDATE` с повторным чтением
    (`execution_options(populate_existing=True)` — найденная и закрытая
    проблема кеша identity map) и повторной проверкой видимости/владельца;
    конкурентная передача не может потерять или перезаписать историю
    (проигравший получает 409 или 404 в зависимости от момента — оба
    исхода корректны и покрыты тестом);
  - новый владелец — только другой **активный HR** (неактивный/manager/
    admin/несуществующий → 422); передача самому себе → 400; пустая или
    состоящая из пробелов причина → 422 (Pydantic + CHECK в БД);
  - HR передаёт только своего кандидата (иначе 404, существование не
    раскрывается); manager/admin — любого видимого;
  - атомарно меняется `owner_user_id`, пишется строка истории и
    аудит-событие `candidate_transferred` (`candidate_id`, в `details` —
    только id `to=`/`from=`, **без** PII и без текста причины);
  - ответ `{transfer, candidate}` — UI обновляется без повторной загрузки.
- **`GET /candidates/{id}/transfers`** — пагинируемая история передач
  (старые первыми) с правилами видимости карточки: после передачи бывший
  HR получает 404 и по карточке, и по истории.
- **`GET /candidates?include_deleted=true`** — серверный список мягко
  удалённых (семантика: скоуп именно на удалённых, видимость как у
  обычного списка); используется экраном «Удалённые».
- **`GET /admin/users/hr`** — минимальный безопасный справочник активных
  HR (`id/username/full_name/role/is_active`, без админ-полей) для выбора
  ответственного; зарегистрирован до `/{user_id}`, чтобы не конфликтовать
  с UUID-параметром.

### Frontend: production-экраны на реальном API (без mockData)

- **`design-system/`** — перенесены токены (`tokens.css`, semantic-переменные
  + dark-тема + density), `global.css` (focus-ring только через
  `:focus-visible`, skip-link, `prefers-reduced-motion`), единый набор
  inline-SVG иконок, примитивы `Button/IconButton`, `Field/TextInput/
  SelectInput`, `Modal`, `Drawer`, `ConfirmDialog`, `Tabs` (roving
  tabindex), `StatusChip/StageChip` (+`STAGE_TONE` с тоном для `started`),
  `StateViews` (Empty/Error/PermissionDenied/SessionExpired/Skeleton),
  `Toast` (+вынесенный `ToastContext`), общий `useFocusTrap`. Новых
  runtime-зависимостей нет; React Router и state-библиотеки не добавлялись.
- **Shell** (`app-shell/Workspace`): hash-навигация без роутера
  (`useWorkspaceSection`), разделы по роли — HR: «Моя очередь» / «Kanban» /
  «Удалённые»; manager/admin: «Кандидаты» / «Kanban» / «Удалённые»;
  текущий пользователь, роль и рабочий выход; любой `401` вне
  `/auth/login` через `api.onUnauthorized` возвращает на экран входа, `403`
  — состояние недостаточных прав.
- **Таблица** (`CandidatesListPage`): колонки ФИО (с телефоном/email),
  должность, этап (чип), источник, ответственный (только manager/admin),
  дата обновления; серверные `query/stage/source/owner_id/sort/direction/
  limit/offset`; поиск с debounce 300 мс и защитой от ответов не по
  порядку; скелетон/empty/error+retry; пагинация «Назад/Вперёд»; состояние
  страницы сохраняется при открытии/закрытии карточки (drawer поверх
  страницы, без размонтирования); удаление — только с подтверждением.
- **Kanban** (`KanbanPage`): колонки строго из `CANDIDATE_STAGE_ORDER`/
  `STAGE_LABELS`, включая «Вышел»; загрузка **постранично внутри колонок**
  (по 20, кнопка «Показать ещё (N)» — задокументированная ограниченная
  стратегия, доска не запрашивает всю базу); нативный HTML5 DnD +
  обязательная keyboard-альтернатива (select этапа на каждой карточке);
  смена этапа — реальный `PATCH` с оптимистичным переносом, блокировкой
  повтора (`busy`) и жёстким откатом при ошибке.
- **Карточка** (`CandidateDrawer`): доступный drawer (focus trap/restore,
  Escape, возврат фокуса), вкладки «Сведения» (просмотр + редактирование
  полей реального API с клиентской валидацией и серверными ошибками;
  смена этапа select'ом с оптимизмом и откатом), «Взаимодействия»
  (пагинация + добавление записи, новая запись появляется сразу без
  перезагрузки), «Передачи» (история + кнопка передачи).
- **Передача** (`TransferDialog`) — двухшаговый сценарий: выбор нового HR
  из реального справочника + обязательная причина → отдельное
  подтверждение со старым/новым именем; при конфликте/ошибке возврат на
  шаг 1 с сообщением, ничего визуально не считается переданным; после
  успешной передачи собственного кандидата HR карточка закрывается, список
  обновляется, показывается подтверждение.
- **Дубли** (`DuplicateResolveDialog`) — общий для создания и
  редактирования: показывает найденные совпадения (ФИО, этап,
  ответственный), позволяет открыть совпадение либо явно подтвердить
  повторную отправку с `confirm_duplicate: true`.
- **Удалённые** — отдельный экран (`include_deleted=true`) с пагинацией и
  восстановлением; физическое удаление отсутствует.

## Ключевые решения (задокументированы)

1. **Конкурентная передача:** `SELECT … FOR UPDATE` + `populate_existing`
   (обход кеша identity map SQLAlchemy, из-за которого первая версия
   пропускала чужие изменения — поймано integration-тестом) + повторная
   проверка видимости/владельца на залоченной строке; проигравший — 409
   (заметил изменение на залоченной строке) или 404 (изменение случилось
   до его проверки видимости) — оба исхода сохраняют инвариант «ровно
   одна история, согласованная с финальным владельцем».
2. **Стратегия загрузки Kanban:** пагинация внутри колонок
   (`GET /candidates?stage=…&limit=20&offset=…`, «Показать ещё») вместо
   полной выгрузки базы; на старте — 11 запросов первых страниц.
3. **`include_deleted=true` скоупит список именно на удалённых** (не
   «объединение») — иначе экран «Удалённые» нельзя было бы реализовать
   серверно с пагинацией; задокументировано в README/ARCHITECTURE.
4. **Навигация и состояние:** hash-роутер на `useWorkspaceSection` и
   локальные хуки — без React Router и state-библиотек; DnD — нативный
   HTML5 + обязательный keyboard-select.
5. **Дубли:** один общий `DuplicateResolveDialog` для создания и
   редактирования; подтверждение всегда пересылает исходный payload с
   `confirm_duplicate: true`.

## Известные ограничения

- Календарь/события, аналитика, шаблоны, импорт/экспорт, документы,
  backup — вне scope этапа (по промпту).
- Command Palette не реализован: промпт разрешает его только как
  навигацию по реальным разделам, а она уже есть в sidebar; дублировать
  базу кандидатов в нём запрещено.
- Глобальный поиск есть в таблице, но не в Kanban (там — только фильтр по
  владельцу для manager/admin).
- Маскирование PII в UI (`phoneMasked`/`emailMasked` из дизайн-прототипа)
  не выполнялось (как и в этапе 3): авторизованные пользователи видят
  контакты в своей зоне видимости; логи и аудит PII не пишут.
- Раскладка интерфейса рассчитана на контрольные ширины дизайн-системы
  (таблица — горизонтальный скролл, sidebar схлопывается на ≤1024px);
  мобильное приложение не требуется по ТЗ.
