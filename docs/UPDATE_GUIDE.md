# Обновление HR Manager поверх работающей версии (пилот 0.15.0)

Документ для владельца (кто передаёт обновление) и для Перепечай (кто его ставит).
Обновление делается **одним файлом** `HR-Manager-Setup-<новая версия>.exe` запущенным **поверх** установленной версии.
Никаких команд Docker, PowerShell и ручной работы с базой не требуется.

---

## 1. Что видит Перепечай

1. Владелец присылает новый `HR-Manager-Setup-<версия>.exe` (проверенный, с SHA256 в сообщении).
2. Двойной клик → SmartScreen (как при первой установке) → **Подробнее** → **Выполнить в любом случае**.
3. Мастер показывает **до начала работ**:
   * **установленная версия → новая версия**;
   * **что нового** (список изменений из сборки);
   * **предупреждение о данных**: «Перед обновлением автоматически создаётся резервная копия. Пользователи, настройки, вложения и лицензия сохраняются.»;
   * проверки «светофором»:
     * **Свободное место** — нужно не меньше 5 ГБ,
     * **Лицензия и ключ проверки** — ключ проверки должен быть на месте,
     * **Настройки и пользователи** — хранятся в базе, сохраняются,
     * **Порт и доступ по сети** — порт и включённый доступ по сети остаются прежними,
     * **Готовность рабочей среды** — Docker Engine должен отвечать,
     * **Хранилище резервных копий** — том `pilot_backups` на месте.
4. Кнопка **Обновить**. Дальше всё автоматически, с понятными надписями:
   * «Проверяем состояние…»,
   * «Создаём резервную копию…» *(шифрованный бэкап базы данных + проверка целостности)*,
   * «Готовим новую версию…» *(новые образы собираются, работающее приложение при этом не останавливается)*,
   * «Запускаем новую версию…», «Выполняем миграции…», «Проверяем приложение…».
5. В конце в окне: **«Обновление завершено»** и новая версия открывается в браузере (или кнопка **Открыть приложение**).
6. Если что-то пошло не так: **«Обновление не удалось, восстановлена прежняя версия»** + причина простыми словами.
   Данные и лицензия остаются на месте; нужно создать **отчёт для поддержки** (трей → «Создать отчёт для поддержки») и отправить владельцу.

Порт (обычно 8080), адрес (`127.0.0.1` или включая доступ по сети), пароли и **лицензия** при обновлении не меняются.

---

## 2. Что гарантированно НЕ трогается при обычном обновлении

* том PostgreSQL **`hr-manager-pilot_pilot_pgdata`** (пользователи, кандидаты, настройки, история),
* том резервных копий **`hr-manager-pilot_pilot_backups`** (прежние бэкапы остаются),
* вложения кандидатов (хранятся в томе базы),
* лицензия и её публичный ключ (файл в каталоге состояния),
* настройка доступа по сети (`lan.json`) и порт (`install.json`),
* секреты установки (пароль базы, ключи шифрования бэкапов) — каталог состояния.

Защита встроена в движок: при обновлении **не вызываются** `docker compose down -v`, `docker volume rm/prune`и любые
команды, удаляющие тома. Это проверяется автотестами (`infra/windows/tests/stack.tests.ps1`,
`pilot-final.tests.ps1` — «обновление поверх сохраняет лицензию, порт, LAN и не удаляет тома данных»).

## 3. Что необратимо и как восстанавливаться

| Что меняется | Обратимо? | Как восстановить |
| --- | --- | --- |
| Файлы приложения, образы | Да, автоматически | Откат возвращает файлы из снимка `previous-snapshot`, перетегирует прежние образы (`:previous`) и возвращает прежний `release_sha` в окружении, затем поднимает старую версию и **проверяет, что она отвечает** |
| Лицензия, настройки, пользователи | Не меняются | Ничего делать не нужно |
| **Схема базы данных (миграции)** | **Нет: `alembic downgrade` не выполняется** | Восстановление из бэкапа, созданного перед обновлением (см. `docs/RECOVERY_GUIDE.md`) |
| Тома данных и бэкапов | Не меняются | — |

Снимок прежней версии (`%LOCALAPPDATA%\HRManager\previous-snapshot` — файлы `infra/`, `backend/`, `frontend/`, `release.json`)
создаётся **до** того, как файлы установки будут перезаписаны:

* мастер установки перед копированием новых файлов выполняет скрытое действие движка `snapshot-previous`
  (см. `installer/installer.iss`, шаг `ssInstall`) — так прежняя версия сохраняется даже при обновлении через `Setup.exe`;
* если запуск обновления идёт командами движка, он делает тот же снимок сам в фазе `prepare`;
* копия нового релиза под управлением движка лежит в `%LOCALAPPDATA%\HRManager\release-staging` —
  благодаря ей фазы обновления повторяемы, даже если исходный каталог релиза исчез (мастер установки
  удаляет свой временный каталог при выходе).
* если файлы `{app}` уже заменены новой версией, а снимок прежней версии сохранить не успели (например,
  `Setup.exe` был прерван), движок продолжает обновление сознательно — откатить файлы уже нечем, и политика
  отката честно сообщает об этом (`unknown_schema` → `rollback_failed`), а не выдаёт новую версию за прежнюю.

Смысл правила: откат возвращает **рабочий код** прежней версии, а база остаётся уже мигрированной —
поэтому старая версия продолжает работать с новой схемой (миграции пишутся совместимыми).
Если схема всё-таки повреждена — поднимаем бэкап, а не откатываем миграции вручную.

Бэкап перед обновлением создаётся **всегда** и проверяется (`backup-now` + `backup-check --deep`); если проверка не прошла — обновление не начинается.

## 4. Что делает владелец перед отправкой обновления

1. Собрать релиз (CI, workflow `Pilot release` или `installer/build.ps1 -Version <новая версия>`).
   В сборку автоматически попадает `release.json`: версия, `release_sha`, `built_at`, список изменений (`changelog`) —
   именно его показывает мастер на шаге 3.
2. Записать **SHA256** файла `Setup.exe` и передать его Перепечай вместе с файлом (для сверки).
   ```powershell
   Get-FileHash .\HR-Manager-Setup-0.15.0.exe -Algorithm SHA256
   ```
   Перепечай может проверить файл сама: правая кнопка по файлу → **Свойства** → вкладка **Подписи** не работает без сертификата,
   поэтому для пилота проверка SHA256 — задача владельца; при сомнениях просто перезапросите файл.
3. Предупредить, что будет запрос UAC (если ставится Docker) и, возможно, перезагрузка.
4. После обновления попросить Перепечай подтвердить: открывается раздел **Кандидаты**, лицензия на месте, версия в разделе **Готовность пилота** — новая.

## 5. Как воспроизвести успех и откат (для разработчика)

* **N → N+1 успешно** (автотест, Pester на Windows): `infra/windows/tests/pilot-final.tests.ps1`
  — «Install-HrmApp с новой версией ведёт через Update-HrmApp (бэкап → откат)» и
  «обновление поверх сохраняет лицензию, порт, LAN и не удаляет тома данных».
* **Сломанное обновление → откат** (автотест): там же — «обновление с падающей миграцией откатывается…»
  (+ проверка записи `update-result.json`: `rolled_back` и подтверждённая готовность прежней версии).
* **Политика отката и безопасная установка** (автотест): `infra/windows/tests/iteration14.tests.ps1` —
  одинаковые/вложенные пути источника и назначения, ошибка копирования, снимок прежней версии,
  `rollback_failed` при неподтверждённом восстановлении, повторный запуск после отката (`phase = "rollback"`),
  поведение значка в трее во время установки и сохранение выключенного автозапуска.
* **Предпросмотр обновления** (автотест): «предпросмотр обновления: текущая/новая версия, changelog, проверки и предупреждение о данных».
* **Ручной прогон на Windows** — `docs/WINDOWS_ACCEPTANCE_CHECKLIST.md`, разделы «Обновление N → N+1» и «Откат».

Запуск: `powershell -ExecutionPolicy Bypass -File infra/windows/tests/run-tests.ps1` (Windows PowerShell 5.1) или CI-джоб
`windows-installer`; тесты не трогают реальную машину — внешние команды замоканы.

## 6. Если обновление не удалось

1. Ничего не удалять и не переустанавливать «с нуля».
2. Трей → **Проверить состояние** → что написано в окне.
3. Трей → **Создать отчёт для поддержки** → файл на рабочем столе → отправить владельцу.
4. Владелец: посмотреть `[StateDir]\update-result.json` (статус и причина) и `update-journal.json`
   (на какой фазе остановилось), затем передать исправленный релиз или восстановить из **проверенной** резервной копии
   по `docs/RECOVERY_GUIDE.md`.

### 6.1. Что именно делает движок (политика отката)

Движок не объявляет «восстановлено» вслепую. Решение принимает `Get-HrmRollbackPlan`
(`infra/windows/engine/Update.psm1`) по фазе сбоя, признаку применённой миграции и ревизии схемы базы данных:

| План | Когда | Что делает движок | Статус в `update-result.json` |
| --- | --- | --- | --- |
| `no_changes` | сбой до замены файлов (`prepare`/`backup`/`build`) | установленная версия не менялась; возвращает только теги прежних образов | `failed` — «Установленная версия не изменялась и продолжает работать, данные в порядке» |
| `restore_previous` | сбой после замены файлов, но схема БД осталась на прежней ревизии | возвращает файлы из `previous-snapshot`, прежние образы, прежний `release_sha`; поднимает стек и ждёт готовности | `rolled_back` только если прежняя версия **ответила** и в работе НЕ сбойный релиз |
| `restore_previous_after_migration` | миграции уже применены (ревизия схемы изменилась) | то же самое, даунгрейда БД нет | `rolled_back` с явным предупреждением: «Схема базы данных остаётся на новой ревизии, данные не удалялись; если приложение прежней версии сообщит об ошибке, восстановите базу из проверенной резервной копии» |
| `unknown_schema` | снимок прежней версии сохранён не был (файлы `{app}` уже заменены установщиком) или ревизию схемы прочитать не удалось | вернуть прежнюю версию нечем: движок не объявляет успех, журнал и бэкапы сохраняются | `rollback_failed`, `needs_backup_restore = true` |
| восстановление не подтвердилось | прежняя версия не запустилась, не ответила или в работе осталась сбойная версия | ничего не объявляет успешным; журнал и бэкапы сохраняются | `rollback_failed`, `recovery_confirmed = false`, `needs_backup_restore = true` |

Что важно знать про эти статусы:

* `rolled_back` означает **проверенный** откат: файлы и образы прежней версии вернулись, приложение отвечает,
  а в `/api/ops/status` не сбойный релиз. Ложного «прежняя версия восстановлена» больше нет;
* `rollback_failed` (в том числе `recovery_confirmed = false`) — честная остановка: обновление не применено,
  но и прежняя версия не подтверждена. Что делать: не удалять каталог состояния, создать отчёт для поддержки
  и восстановить базу из **проверенной** резервной копии по `docs/RECOVERY_GUIDE.md`;
* блокировка обновления (`update.lock`) снимается всегда: после отката исправленный релиз можно поставить повторно,
  а незавершённая попытка видна в `update-journal.json` (`phase = "rollback"`). Повторный запуск начинается с фазы
  `prepare` заново и **не** повторяет откат;
* если `Setup.exe` прервался (перезагрузка, закрытие мастера), установка продолжается автоматически:
  трей показывает «Продолжаем установку HR Manager…», а движок берёт копию релиза из `release-staging`.

Каталог состояния: `%LOCALAPPDATA%\HRManager` (там же `update-result.json`, `supervisor.json`, `logs`).
