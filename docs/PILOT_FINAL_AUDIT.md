| D3 | `Docker` не запускается автоматически | После перезагрузки приложение не поднимается, пользователь думает, что «сломалось» | Supervisor стартует Docker Desktop и ждёт Engine с прогрессом |

## 2. Можно ли использовать текущий Windows engine как supervisor

**Да, частично.** `infra/windows/hr-manager.ps1` уже является единственной точкой
автоматизации: префлайт, секреты, compose, обновление, откат, диагностика,
отчёт. Он сознательно построен так, что все внешние вызовы идут через
`Invoke-HrmExternal`/`Invoke-HrmHttp` (мокабельно), а состояние лежит в
`StateDir`.

Чего ему не хватало для роли supervisor:

1. **Долгоживущего процесса** с состоянием и GUI — движок «одноразовый».
2. **Docker-жизненного цикла**: старт Docker Desktop и ожидание Engine.
3. **Гарантии единственности** — нет mutex.

Решение: движок остаётся **единственным** исполнителем операций, а сверху
появляется тонкий управляющий слой:

- `engine/Docker.psm1` — жизненный цикл Docker Desktop (обнаружение, установка
  по кнопке, старт, ожидание готовности, ремонт стека);
- `engine/Supervisor.psm1` — состояние supervisor'а (`StateDir/supervisor.json`),
  single-instance, запуск/остановка, автоматический сценарий подъёма;
- `engine/Tray.psm1` + `infra/windows/hrm-tray.ps1` — значок в трее (WinForms
  `NotifyIcon`), который **только показывает состояние и вызывает движок**.

## 3. Почему трей — PowerShell/WinForms, а не отдельный C#-сервис

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| PowerShell + `System.Windows.Forms.NotifyIcon` | Нет нового тулчейна; .NET Framework/WinForms есть в Windows 10/11; тот же движок и те же моки; легко читается владельцем; нет компиляции в CI | Требует PowerShell (уже обязателен) | **Выбран** |
| Отдельный C#-exe (сборка в CI) | «Настоящий» exe | Новый тулчейн и новый артефакт, дублирование логики движка, рост поверхности отказа, отсутствие dotnet SDK в этом окружении | Отклонён для пилота |
| Windows-служба (LocalSystem) | Запуск до входа пользователя | Требует админ-прав, не видит пользовательские тома Docker Desktop (контекст пользователя!), UAC на каждую установку/обновление | Отклонён: Docker Desktop работает в контексте пользователя |
| Windows Task Scheduler | Автозапуск | Не даёт трея и состояния, легко дублировать задачу | Отклонён (используется только ярлык автозагрузки → supervisor) |

Отдельная ответственность сохранена: installer ≠ supervisor ≠ backend ≠ frontend ≠
license issuer. Supervisor **не** ходит в БД и не подменяет backend.

## 4. Нужен ли Docker Desktop для пилота

Кратко: **да, с текущей архитектурой**, и альтернативы рассматривались честно.

| Runtime | Технически | Юридически | Решение |
|---|---|---|---|
| Docker Desktop (WSL2) | Полностью подходит; уже используется и проверен в phase 12–14 | Бесплатен для малых организаций/личного использования; требует принятия лицензии **самим пользователем**, установка требует UAC и часто перезагрузки | **Оставляем** и честно документируем это |
| Docker Engine в WSL2 без Docker Desktop (Ubuntu + `docker-ce` + compose plugin) | Работает, но в задаче явно ограничен LAN/HTTPS, а управление томами и обновление — сложнее; нужен WSL-дистрибутив и systemd | Лицензия docker-ce свободна (Apache-2.0) | Возможен как будущий вариант; **не меняем runtime** в пилоте без отдельного решения владельца |
| Podman Desktop | Есть Windows-инсталлятор, но compose-совместимость и поведение WSL отличаются; `!reset` тег и поведение healthcheck нужно проверять заново | Apache-2.0 | Отклонено для пилота: смена runtime = повторная приёмка |
| Нативная сборка под Windows (без контейнеров) | Нет | Нет | Отклонено: вне рамок задачи |

Практическое следствие: пилот **не** обещает «полностью автоматическую установку
Docker» — UAC и лицензию принимает человек. Всё, что можно автоматизировать
(обнаружение, официальный установщик, ожидание Engine, продолжение), автоматизировано.

## 6. Необратимые изменения базы и как обеспечивается восстановление

Общее правило пилота: **даунгрейд схемы не выполняется никогда**
(`Update.psm1`: «даунгрейд БД не выполняется никогда»). Откат возвращает
**образы** приложения, а схема остаётся новее. Это безопасно, пока новая схема
совместима вниз по чтению/записи, но есть изменения, которые откатить нельзя.

| Тип изменения | Пример | Обратимо? | Что делается |
|---|---|---|---|
| `CREATE TABLE/INDEX/COLUMN` (nullable/default) | миграции `0001`–`0022` | Да, старый образ просто не видит новые объекты | Автоматический откат образов |
| `NOT NULL` без default на существующей большой таблице | потенциальная будущая миграция | Нет (откат старого образа не вернёт данные) | Перед обновлением обязательный шифрованный бэкап + deep check (`Invoke-HrmBackupGate`) |
| `DROP COLUMN`/`DROP TABLE`/сужение типа | потенциальная будущая миграция | Нет | Только с бэкапом; восстановление = restore бэкапа (`docs/backup-and-restore.md`), потеря изменений после бэкапа |
| Необратимая миграция данных (например, пересчёт, схлопывание записей) | нет в текущем head | Нет | Запрещено делать в одной миграции: сначала бэкап, затем отдельный согласованный шаг; документируется в миграции |
| Изменение формата бэкапа (ключ шифрования) | `HRM_BACKUP_KEY` не ротируется автоматически | — | Ключ хранится в `StateDir/secrets.json`, переживает обновление; потеря ключа = потеря восстановления старых бэкапов |

Восстановление при неудачном обновлении:

1. Автоматический откат образов к тегу `:previous` (уже реализовано).
2. Если БД уже мигрирована и старая версия не работает — восстановление из
   последнего бэкапа (`backup restore`), данные после бэкапа теряются; поэтому
   бэкап-ворота стоят **до** миграции.
3. Если откат образов не помог — кнопка «Создать отчёт для поддержки» в трее и
   `docs/PILOT_RECOVERY_GUIDE.md`.

| Действие | Кто подтверждает | Почему нельзя обойти |
|---|---|---|
| Установка Docker Desktop (скачивание, запуск установщика) | Пользователь + **UAC** | Установщик Docker требует повышения прав |
| Принятие лицензионного соглашения Docker Desktop | Пользователь | Юридическое требование Docker |
| Перезагрузка Windows после включения WSL2/виртуализации | Пользователь | Требование Windows |
| Включение аппаратной виртуализации в BIOS/UEFI | Пользователь | Windows/ПО не могут сделать это за пользователя |
| Включение доступа по локальной сети (Firewall) | **UAC** (один раз) | Правило Firewall требует прав администратора |
| Удаление данных (`-PurgeData`) | Пользователь (фраза подтверждения) | Необратимая потеря данных |

## 8. Ограничения проверки в этом окружении (честно)

- Среда разработки — Linux, PowerShell/pwsh недоступны (загрузка бинарника
  PowerShell из GitHub Releases блокируется сетевыми ограничениями песочницы).
  Поэтому PowerShell-тесты (`infra/windows/tests/run-tests.ps1`) **здесь не
  запускались**; их прогоняет CI на `windows-latest`
  (`.github/workflows/ci.yml`, job `windows-installer`).
- Docker/Docker Desktop недоступны: живые сценарии «Docker установлен/не готов»,
  «compose запущен/сломан», реальное обновление и откат на Windows в этой среде
  не выполнялись и не выдаются за выполненные.
- Доступны и запускаются: Python-линтер движка, backend pytest (unit) и
  структурные проверки compose/installer.
- Итоговый GO/NO-GO возможен только после ручной приёмки по
  `docs/PILOT_ACCEPTANCE_CHECKLIST_WINDOWS.md` на чистой Windows 10/11.
