## Маркер и журнал

Без журнала поражённой машины **точная причина оставшегося running неизвестна**.
Разбор кода подтвердил уязвимые пути, но не доказывает, какой из них сработал:

1. Импорт модулей был вне общего try/catch.
2. В catch сначала выполнялись вывод/логирование, и лишь затем запись failed;
   исключение в самом обработчике могло прервать запись маркера.
3. Старый `update-result.json` мог заменить текущую причину отказа.
4. Прямой запуск из Inno `[Run]` не задавал `HRM_LOG_FILE`; это делает только
   Start-HrmEngineProcess (трей). Поэтому даже сбор существующих `logs/*.log`
   сам по себе не гарантировал журнал именно установки.
5. Inno нормализовал running в failed только в GetCustomSetupExitCode, то есть
   **после** показа Finish page.

Импорт теперь внутри catch boundary, install/update владеют маркером; failed
пишется первым и независимо от журнала/supervisor. Текущая ошибка не заменяется
старым update-result. Прямой запуск создаёт StateDir/logs/<action>-timestamp.log,
фатальная запись включает redacted ScriptStackTrace. При успехе маркер удаляется.
Inno нормализует оборванный running до выбора Finish-текста. Если сам процесс не
загрузился/был убит или запись недоступна, нельзя выдумать точную причину:
резервное сообщение сообщает отсутствие итогового результата, а не обвиняет Docker.
Полный отказ диска/ACL не позволяет гарантировать запись файла; это не успешная установка.

Support bundle содержит `logs-engine.txt`: не более 5 `*.log`, по LogTail
строк (200 по умолчанию), через Redact-HrmText и Redact-HrmPii. Сначала берутся
самые свежие `install-*`/`update-*`, оставшиеся места заполняются самыми свежими
остальными журналами. Если журналов установки/обновления уже пять или больше,
выбираются пять последних из них. Повторные `open-*` из ярлыка больше не
вытесняют более старый журнал неудачной установки. Реестр секретов
загружается до чтения журналов, даже при недоступной диагностике. Сам файл
секретов, env и дампы не копируются. Свободные имена/названия организаций всё
ещё могут остаться — архив отправлять только по закрытому каналу.

### Осознанное изменение текста отказа после отката (P3.3)

Раньше общий catch `hr-manager.ps1` заменял сообщение текущего исключения
текстом `update-result.json`, если такой файл существовал. Это касалось в том
числе **успешного отката после неудачного обновления**: движок завершался с
ненулевым кодом, но маркер показывал «прежняя версия восстановлена и отвечает»
вместе с сообщением из update-result. Теперь `setup-run.json` получает текущую
причину исключения и `failed`; подтверждённый откат остаётся отдельным фактом
в `update-result.json` и журнале обновления. Сам алгоритм отката и запись
`rolled_back` не менялись.

Прежнее поведение хуже тем, что общий обработчик не проверял принадлежность
update-result именно этой попытке: сообщение о восстановлении от прошлой
операции могло скрыть новый отказ установки/обновления. Поэтому даже при
успешном откате не возвращаем безусловную подстановку. Если позже понадобится
показывать оба факта в маркере, понадобится привязка результата к ID текущей
операции, а не чтение любого существующего файла. В этом follow-up обработчик
ошибок не менялся; решение предыдущего патча сохранено явно.

### Причина и исправление

База публикует frontend на `127.0.0.1:8080:8080`. Обычный список ports в pilot
добавлял к нему выбранный порт (8081), не заменяя базу. Занятый чужим dev-стеком
8080 блокировал запуск frontend даже при свободном 8081. Теперь frontend
использует **`ports: !override`**, не `!reset` (последний удалил бы публикацию
целиком). Минимум Compose поднят до **2.24.4**, включая диагностическое сообщение
и default version verdict. Сравнение patch/prerelease покрыто новыми тестами.

Сценарий I1 чек-листа больше не блокируется наследованием 8080 **по конфигурации**;
живой прогон I1 после этой правки ещё обязателен. При реальном bind-конфликте
`Start-HrmStack` и обе попытки `Repair-HrmStack` возвращают `port_conflict` с
HOST-портом и следующим шагом, а не ждут HTTP readiness. Ошибка networking без
`already allocated`/`address already in use` даёт `container_network_failed`,
не утверждая недоказанную занятость порта. Сырые ошибки psql не печатаются,
парольная механика, маркеры и readiness не менялись.

### Один безопасный диагностический заход на Windows (до и после)

Движок читает compose из **InstallDir**, а не из текущего каталога запуска.
Зафиксировать SHA снимка/Setup и SHA256 обоих фактически используемых compose.
Для приёмки нового кода установить свежий Setup либо явно задать InstallDir
на проверенный снимок (передать `-InstallDir`/`HRM_INSTALL_DIR`); запуск одного
нового hr-manager.ps1 со старыми compose в установленной папке невалиден.

В PowerShell, без вывода полного env/config и без изменения контейнеров:

```powershell
$install = Join-Path $env:LOCALAPPDATA 'Programs\HRManager'
$state = Join-Path $env:LOCALAPPDATA 'HRManager'
$base = Join-Path $install 'infra\docker-compose.yml'
$pilot = Join-Path $install 'infra\compose.pilot.yml'
Get-FileHash $base, $pilot -Algorithm SHA256
docker port hr-manager-pilot-frontend-1
docker inspect hr-manager-pilot-frontend-1 --format '{{json .NetworkSettings.Ports}}'
Get-NetTCPConnection -LocalPort 8080,8081 -State Listen -ErrorAction SilentlyContinue |
    Select-Object LocalAddress,LocalPort,OwningProcess
curl.exe -s -o NUL -w '%{http_code}' http://127.0.0.1:8080/
curl.exe -s -o NUL -w '%{http_code}' http://127.0.0.1:8081/
# Весь config содержит секреты: только переменная в памяти, не transcript/file.
$json = docker compose --project-name hr-manager-pilot --env-file (Join-Path $state 'pilot.env') -f $base -f $pilot config --format json 2>$null
if ($LASTEXITCODE -ne 0) { throw 'Compose config failed; do not publish raw config/stderr' }
$config = ($json -join "`n") | ConvertFrom-Json
$config.services.frontend.ports | Select-Object host_ip,published,target,protocol
Remove-Variable json,config
```
