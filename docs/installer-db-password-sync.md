## Маркер и журнал

Без журнала поражённой машины **точная причина оставшегося running неизвестна**.
Разбор кода подтвердил уязвимые пути, но не доказывает, какой из них сработал:

1. Импорт модулей был вне общего try/catch.
2. В catch сначала выполнялись вывод/логирование, и лишь затем запись failed;
   исключение в самом обработчике могло прервать запись маркера.
3. Старый `update-result.json` мог заменить текущую причину отказа.
4. Прямой запуск из Inno `[Run]` не задавал `HRM_LOG_FILE`; это делает только
   Start-HrmEngineProcess (трей). Поэтому даже сбор существующих `logs/*.log`
   сам по себе не гарантировал журнал именно установки.
5. Inno нормализовал running в failed только в GetCustomSetupExitCode, то есть
   **после** показа Finish page.

Импорт теперь внутри catch boundary, install/update владеют маркером; failed
пишется первым и независимо от журнала/supervisor. Текущая ошибка не заменяется
старым update-result. Прямой запуск создаёт StateDir/logs/<action>-timestamp.log,
фатальная запись включает redacted ScriptStackTrace. При успехе маркер удаляется.
Inno нормализует оборванный running до выбора Finish-текста. Если сам процесс не
загрузился/был убит или запись недоступна, нельзя выдумать точную причину:
резервное сообщение сообщает отсутствие итогового результата, а не обвиняет Docker.
Полный отказ диска/ACL не позволяет гарантировать запись файла; это не успешная установка.

Support bundle содержит `logs-engine.txt`: последние 5 `*.log`, по LogTail
строк (200 по умолчанию), через Redact-HrmText и Redact-HrmPii. Реестр секретов
загружается до чтения журналов, даже при недоступной диагностике. Сам файл
секретов, env и дампы не копируются. Свободные имена/названия организаций всё
ещё могут остаться — архив отправлять только по закрытому каналу.

## Обязательная реальная приёмка — пока BLOCKED / NO-GO

Проводить на изолированной Windows-машине с Docker Desktop, на копии данных,
не на единственном томе пользователя. Секреты и bundle не коммитить.

1. До исправления: стек старого SHA, существующий pilot_pgdata со старым
   credential и контрольными синтетическими строками. Зафиксировать ID тома,
   revision, counts и контрольные ID строк в закрытом evidence.
2. Сохранить исходный StateDir защищённо. На тестовой машине дать движку свежий
   StateDir с новым секретом при том же томе. Старый движок должен воспроизвести
   `FATAL: password authentication failed`. Не удалять/пересоздавать том.
3. Установить Setup, собранный **из SHA данного PR**. Зафиксировать SHA256 Setup,
   engine log, отсутствие running-маркера по завершении, healthy backend,
   работающие worker/backup, страницу и браузер `http://127.0.0.1:8081`.
4. Сверить ID тома, контрольные строки/таблицы/counts до/после. Повторный start
   идемпотентен. Реальные пароли нигде в evidence не раскрывать.
5. Запустить `infra\windows\tests\run-tests.ps1` целиком без Skip на этой
   машине, сохранить весь вывод. В sandbox/CI реальную приёмку не подменять.
6. Создать support bundle, убедиться, что там журнал именно install и нет
   пароля (включая SQL-escaped вид); проверить отказ с недоступным сокетом на
   тестовом стенде: failed + причина, ненулевой exit, данные целы.
7. Независимый reviewer сверяет SHA/CI/артефакты. До evidence решение NO-GO.

### Известное ограничение (не исправляется здесь)

Потеря StateDir означает потерю не только пароля PostgreSQL, но и
`HRM_BACKUP_KEY`. Согласование роли **не восстанавливает** прежний ключ:
старые зашифрованные backup без него не расшифровать. StateDir/ключи хранить
защищённо; не удалять их ради переустановки. Код backup/лицензии не менялся.
