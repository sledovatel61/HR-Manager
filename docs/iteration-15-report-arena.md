## 2. Что исправлено

### 2.1 Находка 1 — снимок прежней версии строго ДО первой перезаписи `{app}`

Мастер обязан сохранить прежнюю версию **до** того, как разложит файлы новой, и не
имеет права полагаться на установленный движок (старая версия может не знать нового
действия и формата). Реализовано:

* `infra/windows/hrm-snapshot.ps1` + `engine/Snapshot.psm1` распаковываются мастером
  из **своего же** пакета в `{tmp}` (записи `[Files]` с `Flags: dontcopy noencryption`)
  и запускаются как отдельный процесс; импорт идёт по пути рядом со скриптом, поэтому
  распаковка «плоская». Установленный движок не участвует вообще.
* Контракт CLI: `-InstallDir -StateDir -ResultFile -ModuleDir`; коды возврата
  `0` — продолжать (`verified` либо `skipped`), `3` — снимок нужен, но не вышел,
  `1` — непредвиденная ошибка.
* `installer/installer.iss`: `PrepareToInstall` = `PreservePreviousSnapshot()` →
  `HrmVerifySnapshotGuard()`; порядок закреплён тестами (обратный порядок
  останавливал бы любое обновление ещё до попытки снимка). Повторная проверка — в
  `CurStepChanged(ssInstall)` через `RaiseException`, то есть **до** копирования файлов.
* Первая установка (`{app}` без файлов программы) вообще не запускает помощник:
  `skipped` / `reason=no_program_files`, решение пишется в журнал мастера строкой
  `HRM: snapshot decision needed=0 status=skipped reason=no_program_files …` и в
  `%LOCALAPPDATA%\HRManager\setup-snapshot.json` (schema `hrm-setup-snapshot-1`).
  Признак «есть что сохранять» — файлы программы (`release.json`,
  `infra\compose.pilot.yml`, `infra\windows\hr-manager.ps1`), а **не** запись
  установки: каталог состояния может остаться от прошлой установки.
* Невозможность снимка при существующей установке (нет прав, не распаковался
  помощник, отказ `Resolve-HrmPreviousSnapshot`) — останов мастера до перезаписи,
  с русским текстом и записью причины в `setup-snapshot.json`/журнал.

### 2.2 Находка 2 — ошибка после замены файлов не маскируется под «ничего не менялось»

`Setup.exe` копирует файлы до запуска движка, поэтому сбой на первых фазах
(бэкап/сборка) раньше возвращал ложное «Установленная версия не изменялась»
(`plan=no_changes`). Теперь в `Update-HrmApp` замена файлов доказывается **по файлам**,
а не по журналу:

* `$filesReplacedEvidence = (текущий release_sha в {app} ≠ release_sha записи установки)`,
  плюс второе доказательство для старых записей без `release_sha` — расхождение
  версии (`release.json`), и `$filesSwitched = … -or $filesReplacedEvidence`.
* Признак сохраняется в журнал (`files_switched`) и учитывается при `-Resume`.

### 2.3 Находка 3 — идентичность отката проверяется явно

`Restore-HrmPreviousVersion` теперь требует **точного совпадения** ожидаемого
`release_sha` прежней версии **и** подтверждённой готовности. Ожидаемый
идентификатор вычисляется явно до отката: журнал обновления (`previous_release_sha`),
иначе запись установки, а при пустой записи — проверенный снимок мастера; он же
передаётся в проверку.

* пустой `release_sha` в ответе приложения при известном ожидаемом — провал
  («прежняя версия не подтверждена»), чужой — провал;
* версия сбойной сборки в работе (`FailedReleaseSha`) — провал («откат не применился»);
* успех (`rolled_back`) — только точное совпадение `sha` **и** `Wait-HrmReady`/ответ
  `/api/ops/status`;
* иначе `rollback_failed` + `needs_backup_restore=true` и явный список причин;
* для legacy-версий без `release_sha` — отдельный строгий документированный фолбэк
  (`docs/UPDATE_GUIDE.md`, «Правило прежней идентичности»): нужен проверенный
  снимок с версией, известный `release_sha` сбойной сборки, отсутствие чужого
  `release_sha` в ответе и совпадение версии в работе с версией снимка; файлы до и
  после восстановления сверяются с манифестом снимка.

### 2.4 Дополнительно в этой итерации: единственный красный прогон CI

Прогон `37761734634` (`e8e311c`) упал на шаге «Silent install and uninstall smoke»:
шаг завершился за ~1 с с кодом 1 и **не оставил ни одной аннотации** — по check-run
видно только «Process completed with exit code 1». Причина (подтверждена байтами и
поведением):

* Раннер пишет временный скрипт шага в UTF-8 **без BOM**, а Windows PowerShell 5.1
  читает такой файл в ANSI-кодировке. Часть кириллицы при этом превращается в
  символы, которые парсер PowerShell считает строковыми кавычками: «ф» (D1 94) →
  U+201D, «у» → U+201C, «т» → U+2019, «в» → U+201A, «д» → U+201E.
* В старом теле шага посчитано 1065 не-ASCII символов и **73** таких «кавычки», из
  них три U+201E — внутри строк в двойных кавычках (слово «файлов»/«файлы» в
  `throw "…"`). Такая кавычка закрывает строку раньше времени, скрипт не
  разбирается целиком и умирает до первого оператора.
* Поведенческие данные согласуются: `8d88539` — тело шага 16 строк, 0 не-ASCII →
  шаг зелёный; `e8e311c` — 83 строки, 1065 не-ASCII → шаг красный за 1 с без
  вывода; `0178280` — тело шага снова ASCII (сценарий в файле репозитория с BOM) →
  зелёный с полным набором аннотаций (`37764014302`). Другой шаг того же джоба с
  `shell: powershell` и русским текстом (проверка trust store, 443 не-ASCII)
  проходил всё время, потому что его «кавычки» попадают только в комментарии и в
  строки другого типа — то есть опасность зависит от места, а не от наличия
  кириллицы вообще.

Что сделано по этому классу сбоев:

* сценарий смоука живёт в `infra/windows/tests/ci-silent-smoke.ps1` (UTF-8 + BOM),
  шаг workflow — тонкая ASCII-обёртка, которая печатает ход и при ненулевом коде
  отдаёт хвост вывода одной аннотацией `::error`;
* все оставшиеся `run`-блоки шагов `shell: powershell` переведены в ASCII
  (`ci.yml`: trust store и аудит издателя Docker; `update-channel.yml`: шаг подписи);
* `infra/windows/tests/lint-engine.py` теперь **валит** сборку, если в `run`-блоке
  шага `shell: powershell` появится не-ASCII;
* `backend/tests/test_workflow_step_encoding.py` закрепляет правило фикстурами и
  проверяет реальные workflow; тест падает на прежней реализации (функции проверки
  там нет — `AttributeError`).

### 2.5 Расхождение SHA256 у `Setup.exe` (находка по хешам)

В аннотациях прогона было видно два разных хеша одного файла: «build output» и
«uploaded artifact». Разобрано:

* `installer/build.ps1` пишет в `release-manifest.json` хеш **до** подписи;
* `installer/sign.ps1` подписывает файл **на месте** (`installer/output`), поэтому
  хеш файла на диске — уже другой, и он **меняется от прогона к прогону**: CI
  генерирует эфемерный тестовый сертификат заново каждый запуск. Это не «сборка
  невоспроизводима», а следствие подписи.

Чтобы это перестало быть вопросом доверия к тексту, добавлено настоящее
доказательство: шаг `Publish the installer hashes` печатает оба хеша как разные
факты (build output без подписи / файл на диске после подписи) и **падает**, если
хеш файла на диске не совпадает с хешем в `installer/authenticode-attestation.json`,
то есть если отгружен не тот файл, подпись которого была проверена `sign.ps1`.

## 3. Почему «старый движок» безопасен

* Помощник снимка берётся **из нового пакета** мастера (записи `dontcopy` +
  `ExtractTemporaryFile` в `{tmp}`), а не из установленного приложения; импорт
  модулей идёт по пути рядом со скриптом. Старая версия движка не вызывается и её
  возможности не требуются.
* Мастер проверяет **код возврата** помощника (`exec` → `SnapshotExitCode`) И
  содержимое файла результата (`status` ∈ {`verified`, `skipped`}); пустой/чужой
  статус = останов до перезаписи.
* Совместимость форматов: снимок описывается файлом `previous-snapshot.json`
  (schema `hrm-previous-snapshot-1`, `origin` ∈ `engine|installer|adopted`), который
  читает и новый движок (`Resolve-HrmPreviousSnapshot`), и мастер; движок читает
  снимок мастера, а мастер — снимок движка. Для версий, выпущенных **до** этого
  исправления (без описания снимка), мастер создаёт снимок сам и помечает его
  `origin` как созданный мастером, а движок умеет принимать такой снимок (иначе
  первое же обновление существующей установки останавливалось бы до снимка).
* Чужие записи читаются безопасно: `Get-HrmInstallRecordField` вместо прямого
  `$record.<field>` (StrictMode 2.0), `PSObject.Properties[…]`-проверки.

## 4. Как гарантируется снимок до перезаписи

1. `PrepareToInstall` (вызывается и в неинтерактивном режиме) → сначала снимок.
2. Снимок пишется во временный каталог `previous-snapshot.tmp-<8hex>` и подменяет
   `previous-snapshot` только после проверки манифеста (у старых каталогов остаётся
   `.old`), поэтому «полуснимок» не может быть принят за проверенный.
3. `HrmVerifySnapshotGuard` принимает только `verified`/`skipped` и требование
   `verified=true` в `previous-snapshot.json`; иначе — останов.
4. Дополнительно `CurStepChanged(ssInstall)` бросает исключение до копирования файлов.
5. Движок (`Update-HrmApp`) повторно использует проверенный снимок мастера
   (`Test-HrmPreviousSnapshotMatches`) и **не делает** новый снимок из уже
   перезаписанного `{app}`; если файлы заменены, а снимка нет — обновление
   продолжается (единственный способ получить работающую версию), но политика
   отката честно сообщает `rollback_failed`/`unknown_schema` и требует восстановления
   из бэкапа БД, а не выдаёт ложный успех.
6. Снимок не создаётся и не портится на первой установке: помощник не запускается
   вовсе (`no_program_files`), файлы не читаются.

## 5. Как проверяется идентичность отката

* Ожидаемый `release_sha` прежней версии передаётся в проверку **явно** (журнал
  обновления `previous_release_sha` → запись установки → проверенный снимок
  мастера); пустой ожидаемый идентификатор — отдельная документированная ветка, а
  не «любой сойдёт».
* Снимок до перезаписи обязан пройти `Resolve-HrmPreviousSnapshot` с этим
  идентификатором: чужой/повреждённый/неполный снимок работу не перезаписывает.
* Успех отката = `Wait-HrmReady` + ответ `/api/ops/status` + **точное** совпадение
  версии в работе с ожидаемой (или, для legacy без `release_sha`, все четыре условия
  строгого фолбэка из §2.3). Иначе — `rollback_failed`, `needs_backup_restore=true`
  и причины в отчёте; `update.lock` снимается всегда.

## 8. Ограничения, риски и что осталось непроверенным

Честно, без выдачи непроверенного за проверенное:

1. **Содержимое скачанных артефактов не проверено из песочницы.** Скачивание
   артефактов GitHub заблокировано политикой egress: запрос
   `…/actions/artifacts/<id>/zip` отвечает `302` на
   `productionresultssa6.blob.core.windows.net`, соединение обрывается
   (`curl: (35) SSL_ERROR_SYSCALL`). Поэтому совпадение `SHA256SUMS.txt` и
   `release-manifest.json` **внутри** скачанного архива с файлами-артефактами не
   подтверждено; проверены значения, которые CI печатает аннотациями, и инвариант
   «файл на диске = attestation» (§2.5). Владельцу: сверить `SHA256SUMS.txt` из
   артефактов у себя на машине.
2. **VM-проверки не выполнены** (нет Windows-машины в этой среде): пункты
   `docs/WINDOWS_ACCEPTANCE_CHECKLIST.md` G10–G14 и H1/H2 (в том числе чистый
   обход установки/обновления на живой системе, поведение при отключённом Docker,
   предупреждение трея) остаются за человеком. Разрушительные сценарии (сбой
   посреди обновления, откат) выполнялись только в CI-дрилле на раннере и в
   юнит-тестах.
3. **Inno Setup локально не компилируется** — правки `installer.iss` проверены
   структурно (баланс `begin/end`, `try/except`, статические тесты) и фактической
   сборкой в CI, но не локальным компилятором.
4. **Побайтовая воспроизводимость сборки НЕ подтверждена, и по коду её сейчас
   нет.** Запустить повторный прогон того же коммита из песочницы не удалось:
   `gh workflow run` → `403 Resource not accessible by integration`, `gh run rerun`
   → «cannot be rerun» (у токена нет `actions: write`). При этом причина видна в
   коде: `installer/build.ps1:156` пишет в **упакованный** `release.json` поле
   `built_at = (Get-Date).ToString("o")` — настенное время внутри пакета, поэтому
   две сборки одного коммита заведомо дают разные байты (плюс Inno Setup хранит в
   пакете метаданные исходных файлов). Наблюдения согласуются: хеши и размер
   `Setup.exe 0.13.0` меняются от прогона к прогону (2859336 / 2860008 байт).
   Что это значит для приёмки: критерий «воспроизводимая сборка» в смысле
   побайтовой идентичности **не выполнен**; фактическая гарантия, которая есть
   сейчас, — зафиксированный SHA256 отгружаемого файла (`SHA256SUMS.txt` +
   notice-аннотация) и attestation подписи, при расхождении с которой CI падает
   (§2.5). Предложение владельцу (отдельная задача): детерминировать сборку
   (брать `built_at` из даты коммита, нормализовать метки времени staged-файлов)
   и добавить джоб «собрать дважды и сравнить хеши»; это меняет содержимое
   релизного payload, поэтому решение — за владельцем.
5. **Риск хрупкости кодировок сохраняется концептуально** для будущих правок: любое
   копирование русского текста прямо в `run:` шага `shell: powershell` снова
   сломает шаг. Смягчение — правило линта + pytest; для `pwsh`/`bash` шагов
   ограничение не нужно (они читают UTF-8 без BOM корректно).
6. **`Set-HrmInstallRecord` на legacy-записи** без юнит-теста — остаётся в списке
   рисков с итерации 14 (покрыто косвенно тестами обновления).
7. **Проверки подписи в CI — тестовые**: эфемерный сертификат, продакшн-подпись и
   Release/tag не запускались (решение владельца от 2026-09-29).
8. **Автоматическое восстановление БД** при `rollback_failed` не выполняется
   намеренно: отчёт говорит `needs_backup_restore=true`, восстановление — по
   `docs/RECOVERY_GUIDE.md`. Это осознанное ограничение, а не недоделка.
