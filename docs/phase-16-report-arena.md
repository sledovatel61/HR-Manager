## 2. Что сделано

### 2.1 Модель данных (S1)

Миграция `backend/alembic/versions/0015_document_templates.py`, ревизия `0015`
(← `0014`), создаёт три таблицы:

- `document_templates` — `kind` (управляемый ключ, `^[a-z][a-z0-9_-]{0,31}$`),
  `scope` (`''` = все этапы, иначе этап кандидата), `name` ≤ 120 (редактируется
  отдельно от версий), `revision` (optimistic counter), FK автора `RESTRICT`,
  индекс `(scope, kind)`;
- `document_template_versions` — `number`, `state` ∈ `draft/active/archived`,
  `title` ≤ 200, `body` 1…20 000, JSON-список использованных плейсхолдеров,
  `activated_at`, уникальность `(template_id, number)` и частичный уникальный
  индекс «не более одной активной версии на шаблон»;
- `candidate_document_generations` — неизменяемый снимок: номер/имя/заголовок
  версии, вид, ревизия документа, `body_text`, `body_html`, `content_sha256`,
  ключ идемпотентности, автор; уникальность `(candidate_id, revision)` и
  частичный уникальный индекс по ключу идемпотентности.

PostgreSQL-гарды (`phase16_generation_immutable`,
`phase16_version_immutable`, `phase16_template_immutable`) запрещают на уровне
БД то, что нельзя гарантировать кодом: изменение/удаление снимка, изменение
содержимого версии (разрешены только `state` и `activated_at`), удаление
шаблона и смену `kind`/`scope` (переименование разрешено — оно аудируется).
`downgrade()` удаляет только собственные объекты, поэтому цикл
`upgrade head → downgrade base → upgrade head` воспроизводим.

Проверка на живой PostgreSQL 16.2 выявила и устранила конфликт имён: констрейнты
и частичные индексы уникальны в схеме, а Phase 11 уже занимала имена
`document_versions_*`. Объекты Phase 16 переименованы в `template_versions_*`;
конфликт виден только на PostgreSQL и был бы пропущен SQLite-тестами.

### 2.2 Рендерер и allowlist плейсхолдеров (S2)

`backend/app/template_render.py` — чистый модуль без I/O: каталог разрешённых
токенов, валидаторы (`kind`, `title`, `body`), извлечение токенов, подстановка,
мини-разметка и рендер автономного HTML. Ключевые свойства:

- подстановка только по allowlist; неизвестный токен, одиночные `{`/`}`,
  управляющие символы и превышение лимитов → 422 с перечислением проблем;
- значения экранируются (`&lt;`, `&amp;`, `&quot;`), пустые значения → «—»;
- `**полужирный**` применяется к **экранированному** тексту и **до** подстановки
  значений, поэтому разметка может прийти только из самого шаблона: значение
  вида `**x**` или `<b>` останется текстом;
- поддерживаются только абзацы, строки `- ` и полужирный;
- лимиты: тело ≤ 20 000, заголовок ≤ 200, имя ≤ 120, ≤ 100 версий на шаблон,
  ключ идемпотентности 8…128 символов.

Полный справочник: [`docs/document-placeholders.md`](document-placeholders.md).

### 2.3 API шаблонов и версий (S3)

`backend/app/document_templates.py` (операции) и
`backend/app/routers/document_templates.py` (маршруты):

| Метод и путь | Назначение |
| --- | --- |
| `GET /document-templates` | Список шаблонов; не-управляющим видны только опубликованные версии, флаг `can_manage` |
| `POST /document-templates` | Новый шаблон + первый черновик |
| `PATCH /document-templates/{id}` | Переименование (`expected_revision`) |
| `POST /document-templates/{id}/versions` | Новая версия-черновик (`expected_revision`) |
| `POST /document-templates/{id}/versions/{vid}/activate` | Публикация; предыдущая активная → архив |
| `POST /document-templates/{id}/versions/{vid}/archive` | Архивация |
| `GET /document-templates/placeholders` | Каталог разрешённых плейсхолдеров |
| `POST /candidates/{cid}/generated-documents/preview` | Рендер без сохранения |
| `POST /candidates/{cid}/generated-documents` | Сохранить неизменяемый снимок (идемпотентно) |
| `GET /candidates/{cid}/generated-documents` | История документов кандидата (пагинация ≤ 100) |
| `GET /candidates/{cid}/generated-documents/{gid}` | Один снимок |
| `GET /candidates/{cid}/generated-documents/{gid}/download?format=html\|txt` | Скачивание артефакта |

Управление — администратор или действующий grant `document_lists_manage`
(иначе 403). Документы кандидата — по существующей owner-based политике
`can_access`: чужой или удалённый кандидат даёт 404 (anti-IDOR), расширенный
доступ — только через подтверждённый `candidate_documents_all`. `expected_revision`
даёт optimistic 409; занятый «одновременно» номер версии сериализуется блокировкой
строки, а генерация — advisory-локом, поэтому конкурентные запросы получают
разные ревизии, а повтор с тем же ключом идемпотентности возвращает тот же
документ (200 вместо 201). Ключ, привязанный к другой версии шаблона, — 409.

### 2.4 Аудит

Новые действия (без текста документов и лишних ПДн): `document_template_created`,
`document_template_renamed`, `template_version_created`,
`template_version_activated`, `template_version_archived`, `document_generated`,
`document_downloaded`. В `details` попадают только идентификаторы, номер версии
и первые 16 символов SHA-256; скачивание дополнительно фиксирует `format`.
Тела документов и значения плейсхолдеров в аудит и логи не попадают (проверено
тестом).

**Осознанное ограничение по длине.** Имена действий уровня версии удержаны в
пределах 32 символов: `downgrade()` миграции `0010` сужает `audit_log.action` до
`VARCHAR(32)`, и слишком длинное значение, оставленное поздней фазой, ломает
`alembic downgrade base`. В Phase 15–16 такие значения не создаются. В самом
Phase 10 уже есть более длинные имена (`candidate_channel_consent_updated` и
др.), поэтому даунгрейд ниже `0010` при наличии таких строк в БД упадёт — это
пре-существующий дефект миграции, вынесенный в отдельную техническую задачу
(см. §9), а не изменённый здесь.

### 2.5 Интерфейс (S5)

- Новый раздел `#/templates` («Шаблоны документов») для всех ролей: список
  шаблонов с видом, областью, ревизией и статусами версий; создание,
  переименование, новая версия, публикация и архивация; каталог плейсхолдеров с
  кнопками вставки в текст; при `can_manage = false` элементы управления
  отключены и показана причина.
- В карточке кандидата — вкладка «По шаблону»: выбор опубликованной версии,
  предпросмотр (ничего не сохраняется), сохранение неизменяемого снимка и
  скачивание HTML/текста через object URL. HTML открывается в браузере и
  печатается в PDF средствами браузера.
- Частичный уникальный индекс по активной версии означает: после архивации
  последней активной версии шаблон исчезает из выдачи обычных пользователей —
  это ожидаемое поведение, а не ошибка.

## 4. Открытые вопросы

- **F1. «Загружает» — текст или файл?** `PRODUCT_SPEC.md` §7 и `ROADMAP.md`
  («с загрузкой через админку») допускают два чтения. Реализовано текстовое:
  администратор вводит и сохраняет новую версию через интерфейс. Чтение
  «загружает файл DOCX/PDF» **не** покрыто: нужен отдельный мини-дизайн
  (хранилище, антивирус, права, ретенция, версионирование бинарников).
- **F2. Дефект `update_channel_manage`.** В Phase 13 scope принимается моделью,
  схемами и `change_grant`, но PG CHECK-констрейнт из `0012` допускает только
  три scope (`document_lists_manage`, `candidate_documents_all`,
  `pilot_full_access`), поэтому вставка падает на PostgreSQL; SQLite-тесты этого
  не видят. В Phase 16 дефект **не** исправлялся и отдельный PR не открывался —
  это follow-up.
- **F3. Ретенция и удаление ПДн.** Сгенерированные документы содержат ФИО,
  телефон и email кандидата. Приложение не удаляет снимки физически
  (append-only), а шифрованные backup-файлы живут вне PostgreSQL. Сроки
  хранения, порядок удаления по требованию субъекта и обработка таких файлов —
  решение заказчика; здесь оно только документируется.
- **F4. Строго admin-only или grant?** `INFORMATION_ARCHITECTURE.md` говорит
  «публикация — только admin». Реализация переиспользует существующий
  `document_lists_manage` (решение Q8) и не вводит новый scope. Если заказчик
  требует строго admin-only, достаточно сузить `require_manage` — модель данных
  и API не изменятся.
