# Стабильность установщика Windows: разбор отказа пилота 12.10.2026

Статус документа: разбор первопричин и перечень исправлений ревизии
`arena/8b7949e6-hr-manager`. Документ описывает поведение движка **до**
исправлений (номера строк даны по базовому коммиту `5f172426`) и то, что
изменено. Машинные проверки — в `docs/WINDOWS_ACCEPTANCE_CHECKLIST.md`, раздел K;
поведение после исправлений — в `infra/windows/README.md`, раздел «Ревизия
стабильности установщика (12.10.2026)».

## 1. Что наблюдалось на пилотной машине

Со слов владельца машины и скриншота значка:

1. значок HR Manager в трее показывает **«Состояние: Запускается»** длительное
   время и не переходит ни в «Готово», ни в «Ошибка»;
2. в подробностях — **«Предпроверка не пройдена: compose…»** (текст обрезан,
   причину и следующее действие не видно);
3. в диспетчере задач **десятки процессов `powershell.exe`**, которые не
   завершаются;
4. процесс **`vmmemWSL` занимает ≈ 1.8 ГБ** памяти.

Отдельно по коду (не по машине) обнаружен пятый дефект — пункт меню значка
«Открыть HR Manager» молча ничего не открывал (раздел 3, D10).

## 2. Как собирались данные

**Честно: пилотная машина в распоряжении не было.** Все выводы раздела 3 сделаны
чтением кода базового коммита и существующих тестов; там, где вывод опирается на
наблюдение владельца машины, это отмечено. Проверить выводы на живой машине
предназначен скрипт `infra/windows/tools/Collect-HrmPilotFacts.ps1` (этап 1): он
снимает всех кандидатов CLI контейнеров с `--version`, ответ
`docker compose version --short` с полным stderr и кодом возврата, содержимое
каталогов плагинов, `docker info`, состояние WSL2, память `vmmemWSL`, все
`powershell.exe` с командными строками и временем создания, а также файлы и
журналы `%LOCALAPPDATA%\HRManager`. До запуска этого скрипта утверждения о
состоянии конкретной машины остаются гипотезами.

Внешние факты, использованные в разборе:

- docker/cli#1534 «CLI Plugins Design» — каталоги поиска плагинов CLI на Windows
  по убыванию приоритета: `%USERPROFILE%\.docker\cli-plugins`,
  `C:\ProgramData\Docker\cli-plugins`; каталог рядом с `docker.exe` **не**
  просматривается;
- GHSA-p436-gjf2-799p (high, опубликовано 2026-03-05) — «Docker CLI Plugins:
  Uncontrolled Search Path Element Leads to Local Privilege Escalation on
  Windows»: машинный каталог `C:\ProgramData\Docker\cli-plugins` по умолчанию не
  создаётся, и локальный пользователь без прав мог положить туда свой
  `docker-compose.exe`/`docker-buildx.exe`. Затронуты Docker CLI до 29.1.5
  включительно, исправлено в 29.2.0 (docker/cli#6713, коммит
  `13759330b1f7e7cb0d67047ea42c5482548ba7fa` — legacy-каталог удалён из поиска).
  Отсюда требование: в отказе перечислять проверенные каталоги и честно помечать,
  что новый CLI машинный каталог больше не ищет.

## 3. Находки по критичности

Критичность: **S1** — отказ установки/«вечное» зависание; **S2** — неверная
диагностика, из-за которой причину невозможно найти; **S3** — поведение, которое
усиливает S1/S2 или вводит в заблуждение.

### S1-1 (D1). Внешние команды ждали вечно и могли deadlock'ить родителя

`infra/windows/engine/Common.psm1:228-230` (до исправления):

```powershell
$stdout = $process.StandardOutput.ReadToEnd()
$stderr = $process.StandardError.ReadToEnd()
$process.WaitForExit()
```

Причина → симптом:

- `WaitForExit()` **без аргумента** ждёт вечно. Зависший CLI контейнеров (Docker
  Desktop не отвечал, WSL2 не поднялась, `compose build` встал на сети) держал
  процесс движка бесконечно. Движок не мог ни записать состояние `error`, ни
  освободить блокировку действия — значок оставался в «Запускается» навсегда
  (симптом 1).
- Последовательное `ReadToEnd()` двух труб deadlock'ит родителя, когда ребёнок
  заполнил буфер stderr (~64 КБ) и ждёт, пока его прочитают, а родитель в это
  время читает stdout. Это независимый способ зависнуть **даже с исправным
  Docker**.
- Убийство только корня процесса оставляло потомков (`wsl.exe`, buildx) живыми:
  `.NET Framework` (Windows PowerShell 5.1) не умеет убивать дерево
  (`Process.Kill($true)` есть только в .NET Core).

То же в `Start-HrmElevatedAndWait` (`Common.psm1:547,568`): ожидание установщика
Docker Desktop было бесконечным — закрытое пользователем окно мастера оставляло
движок висеть.

Исправление: асинхронное параллельное чтение труб (`ReadToEndAsync` до ожидания),
ограниченное ожидание `WaitForExit(таймаут)`, ограниченная запись stdin, по
таймауту — остановка **дерева** процессов (`Stop-HrmProcessTree` →
`taskkill.exe /PID <pid> /T /F`, единственный вызов в движке, внесён в белый
список внешних команд с обоснованием), затем штатный `Kill()` корня, если
`taskkill` не сработал; структурированный результат с `ExitCode = 124`
(соглашение GNU `timeout`), `TimedOut = $true`, объяснением в `Stderr` и записью в
журнал; без `-IgnoreExitCode` — одно исключение с тем же текстом; `Dispose()` в
`finally`. Классы таймаутов (probe 60 с / compose 900 с / build 3600 с / kill 20 с
/ default 120 с) с обоснованием — в README; аргументы сопоставляются точным
элементом массива, а не подстрокой командной строки. Ожидание установщика Docker
ограничено 3600 с, при этом движок **никогда не убивает** официальный установщик
(возвращает `ExitCode = -1` и честное сообщение).

Прежние ожидания **не увеличены**: `Wait-HrmDockerEngine` 300 с,
`Start-HrmDockerDesktop` 300 с, `Wait-HrmReady` 180 с — это фиксирует тест.

Тесты: `tests/engine.tests.ps1` — «D1: зависшая внешняя команда…», «D1: таймаут
без -IgnoreExitCode…», «D1: классы таймаутов…».

### S1-2 (D2). Параллельные циклы движка

`infra/windows/engine/Supervisor.psm1:409` (`Invoke-HrmSupervisorCycle`) и
`infra/windows/hrm-tray.ps1:70` (запуск движка значком).

Причина → симптом: цикл движка не имел никакой защиты от второго одновременного
цикла. Мьютекс значка (`Local\HRManagerPilotSupervisor`) защищает только второй
значок, а `action.lock` проверялся **внутри** цикла, уже после входа. Значок
порождал скрытый процесс движка при каждом входе в Windows и при каждом
`ResumePending`, не спрашивая, идёт ли уже операция; `installer/installer.iss`
запускает значок (`nowait`) и установочный движок параллельно, а повторный запуск
`Setup.exe` добавляет ещё одну пару. Два цикла — это два параллельных
`compose build/up`: гонка за порт и образы, двойная нагрузка на Docker/WSL2 и
процессы, которые никто не завершает (симптом 3).

Исправление: цикл берёт именованный мьютекс `Local\HRManagerPilotEngineCycle`
(`Get-HrmEngineCycleMutexName`, переопределение `HRM_ENGINE_CYCLE_MUTEX`), затем
проверяет `Test-HrmEngineOperationInFlight` (живая блокировка действия, свежая
отметка мастера установки/обновления, `supervisor.json` с `busy` и живым чужим
pid) и только потом входит в блокировку действия. Отказ — честный
(`state = "busy"`, `already_running = $true`) и **без** записи ошибки в состояние.
`hrm-tray.ps1` выполняет ту же проверку до порождения процесса и пишет в журнал
«Движок не запускается: операция HR Manager уже выполняется (…)». Мьютекс значка
для этого не переиспользуется: значок держит его всю жизнь, и цикл оказался бы
запрещён навсегда. Отдельная деталь — `busy` значок пишет со своим pid, поэтому
внутри цикла проверка идёт с `-IgnoreBusyState` (иначе только что порождённый
движок отказывал бы сам себе).

Тесты: `tests/supervisor.tests.ps1` — «D2: второй параллельный цикл движка не
начинается…», «D2: цикл не начинается, пока идёт операция движка…», «D2: значок не
порождает второй движок…».

### S1-3 (D3). Блокировка действия молча «протухала» при живом процессе

`infra/windows/engine/Supervisor.psm1:148,166` (до исправления):

```powershell
try { $fresh = (((Get-Date) - [datetime]::Parse($startedAt)).TotalMinutes -lt 60) } catch { $fresh = $true }
```

Причина → симптом: блокировка считалась устаревшей по **возрасту**, а не по
живости владельца. Через 60 минут новая операция снимала чужую блокировку и
запускалась параллельно с живой (ещё один источник параллельных compose). Обратный
случай тоже был плох: если операция действительно зависла, пользователь не видел
ни причины, ни действия — блокировка держалась вечно, а состояние оставалось
«Запускается».

Исправление: пока pid владельца жив, блокировка держится **независимо от
возраста**; при возрасте ≥ `ActionLockStallMinutes` (60) в журнал и в
`supervisor.json` пишется состояние `error` с кодом `action_stalled`, pid
операции и действием для человека (закрыть окно/завершить процесс в диспетчере
задач и повторить). Мёртвый pid — блокировка снимается с записью в журнал.
Добавлен повторный вход в свою блокировку (см. D10).

Тесты: `tests/supervisor.tests.ps1` — «D3: блокировка действия не «протухает»,
пока процесс операции жив».

### S1-4 (D7). Установка завершалась «наполовину»

`infra/windows/engine/Install.psm1:393` (`Set-HrmInstallRecord`) **до**
`Install.psm1:405` (`Assert-HrmPreflight` с compose); ветка повторной установки
(`Install.psm1:288+`) предполётной проверки не имела вовсе.

Причина → симптом: запись `installed.json` создавалась до проверки доступности
compose и валидности конфигурации. При отказе установка «завершалась» с записью,
но без работающего стека: значок видел запись и показывал «Запускается»
(симптом 1), повторный запуск `Setup.exe` шёл по ветке обновления поверх
несуществующего приложения, а причина отказа оставалась только в журнале.

Исправление: полная предполётная проверка (включая compose и конфигурацию)
выполняется **до** записи установки; отказ пишется в `supervisor.json` как `error`
с точной причиной; ветка повторной установки проходит ту же проверку до запуска
стека. Порядок безопасен: `pilot.env` не требует записи установки
(`pilot_created = false` — токен первого запуска генерируется), порт передаётся
явно. `Assert-HrmPreflight` теперь перечисляет в сообщении **причины** проваленных
проверок (обрезка 300 символов; полностью — в журнале и в отчёте для поддержки).

Тесты: `tests/engine.tests.ps1` — «D7: без плагина compose установка не
завершается наполовину…».

### S1-5 (D8). Наблюдатель канала: недостижимый неостановимый цикл

`infra/windows/engine/Channel.psm1:348` — `while ($true) { … Start-Sleep … }` без
единого условия выхода; `infra/windows/engine/Common.psm1:407` —
`Start-HrmChannelWatcherProcess`, которого не вызывал никто (мёртвый код);
`installer/installer.iss:127-128` — комментарий «Наблюдатель канала обновлений
больше НЕ запускается из установщика: его запускает supervisor один раз», не
соответствующий коду (supervisor наблюдатель не запускал).

Причина → симптом: единственной точкой запуска наблюдателя был явный
`hr-manager.ps1 -Action channel -Watch`, но запущенный так процесс невозможно
было остановить иначе, чем убийством из другого процесса (сон 30 с между
циклами, выхода нет). Мёртвый спавнер при этом выглядел как рабочая возможность
порождать скрытый `powershell.exe` — потенциальный источник «лишних» процессов
(симптом 3) и ложное утверждение в установщике.

Исправление: мёртвый спавнер удалён из `Common.psm1` (на его месте — комментарий,
куда переехала ответственность); цикл наблюдателя ограничен (предел циклов
`-MaxCycles`/`HRM_CHANNEL_WATCH_MAX_CYCLES`, предел времени
`-MaxMinutes`/`HRM_CHANNEL_WATCH_MAX_MINUTES`, файл-сигнал `channel-watch.stop`,
проверяемый и во время сна, выход при замене pid-файла); `Stop-HrmChannelWatch`
пишет сигнал **до** `Stop-Process`, поэтому остановка работает и без прав на
завершение процесса; комментарий в `installer.iss` приведён в соответствие с кодом.

Тесты: `tests/channel.tests.ps1` — «D8: наблюдатель канала завершается сам…».

### S2-1 (D5). Отказ по compose не различал причин

`infra/windows/engine/Preflight.psm1:84-105` (до исправления): любой ненулевой код
возврата `docker compose version --short` превращался в один текст «Плагин Docker
Compose v2 не найден», а сравнение версии было `($major -ge 2) -and
($minor -ge 24)`.

Причина → симптом: по тексту «Предпроверка не пройдена: compose…» (симптом 2)
нельзя было отличить «CLI не запустился» от «плагина нет ни в одном каталоге» и от
«плагин есть, но старый»; каталоги поиска не перечислялись, поэтому совет
пользователю дать было нечем. Отдельная мина: правило `minor >= 24` отвергло бы
Docker Compose 3.x и 5.x (major 5, minor 1 → «старый»), то есть сломалось бы на
первом мажорном обновлении плагина.

Исправление: чистая функция `Get-HrmComposeVersionVerdict` различает
`cli_missing | plugin_missing | version_unparsable | version_old | probe_failed |
ok`; отказ перечисляет проверенные каталоги плагинов (`%USERPROFILE%\.docker\
cli-plugins` и `%ProgramData%\Docker\cli-plugins`) с содержимым и честно помечает,
что машинный каталог не ищется Docker CLI 29.2.0+ (GHSA-p436-gjf2-799p); сравнение
версий — `Compare-HrmCliVersion`. Проверка **не ослаблена до предупреждения**: без
compose стек не поднимется, а предупреждение оставило бы пользователя с вечным
«Запускается».

Тесты: `tests/docker.tests.ps1` — «D5: классификация ответа compose…», «D5: отказ
по compose называет причину и проверенные каталоги плагинов…».

### S2-2 (D6). Резолвер CLI возвращал первый найденный файл

`infra/windows/engine/Docker.psm1:180-203` (до исправления): перебор известных
каталогов Docker Desktop, затем `PATH`, возврат **первого** существующего
`docker.exe`; найденные альтернативы не логировались.

Причина → симптом: при двух установках Docker Desktop (устаревшая машинная в
`Program Files\Docker\Docker` и актуальная пользовательская в
`%LOCALAPPDATA%\Programs\DockerDesktop` — вариант по умолчанию в 2026) детекция
«Docker установлен» и фактические вызовы расходились: выбирались CLI из разных
установок. У CLI из старой установки могло не быть плагина compose — и отказ
выглядел как «Docker сломался сам» (симптом 2). По журналу нельзя было сказать,
какие пути вообще найдены.

Исправление: `Get-HrmDockerCliCandidatePaths` собирает всех кандидатов,
`New-HrmDockerCliCandidate` снимает с каждого версию файла, дату и корень
установки, `Select-HrmDockerCliCandidate` (чистая функция, правило зафиксировано
комментарием и тестом) выбирает: тот же корень установки, что и
`Docker Desktop.exe` → наибольшая версия файла → самая свежая дата → прежний
порядок поиска. `Get-HrmDockerCliFacts` отдаёт полный набор фактов (в журнал,
диагностику и отчёт поддержки); все найденные кандидаты пишутся в журнал один раз
на процесс рядом с выбранным (`Resolve-HrmDockerCli`). Проба `--version`
(`Invoke-HrmDockerCliVersionProbe`) выполняется только в диагностике и только для
выбранного CLI: проба всех кандидатов на горячем пути — это лишние процессы CLI,
то есть усилила бы симптом 3. Кэш выбора хранит только успешный результат и
сбрасывается перед ожиданием готовности Docker Engine (установка Docker внутри
того же процесса обязана стать видимой).

Тесты: `tests/docker.tests.ps1` — «D6: корень установки Docker Desktop…», «D6:
правило выбора CLI…», «D6: сравнение версий…», «D6: резолвер перечисляет всех
кандидатов и не принимает путь со стороны», «D6: проба версии CLI…».

диагностику и отчёт для поддержки.

Тесты: `tests/pilot-final.tests.ps1` — «D9: диагностика сообщает память WSL2 и

### S3-1 (D4). Значок опрашивал Docker каждые 5 с, в том числе во время операции

`infra/windows/engine/Tray.psm1:418-419`:

```powershell
$timer.Interval = 5000
$timer.add_Tick($refresh)
```

Причина → симптом: тик каждые 5 с не имел защиты от наложения (медленный Docker →
несколько опросов одновременно), и опрос выполнялся даже тогда, когда операцию
делал движок, — то есть значок добавлял процессы CLI поверх зависших (симптом 3) и
нагружал Docker, который и так не отвечал. В покое это 12 обращений к
`docker compose ps` в минуту.

Исправление: флаг пересечения тиков с `finally`-сбросом; при идущей операции
значка или движка состояние берётся из `supervisor.json`, а в Docker значок не
идёт; интервал зависит от состояния (`Get-HrmTrayRefreshIntervalMs`): 5 с при
запуске/операции, 30 с в покое, 60 с в остановке и ошибке — в покое не больше 2
опросов в минуту при критерии «не больше 4».

Тесты: `tests/supervisor.tests.ps1` — «D4: значок не ходит в Docker при идущей

### S3-2 (D7, часть про значок). План значка затирал ошибку, записанную движком

`infra/windows/hrm-tray.ps1:60` (до исправления):

```powershell
Set-HrmSupervisorState -StateDir $StateDir -State $plan.state -Message $plan.message -Busy $plan.busy
```

Причина → симптом: значок при старте безусловно писал своё плановое состояние
(«Запускается») поверх состояния, которое успел записать движок, — в том числе
поверх `error` с причиной отказа. Пользователь видел «Запускается» и обрезанный
текст предполётной проверки (симптомы 1 и 2 одновременно).

процессом, имеет приоритет над планом (своя запись значка план не перезаписывает);
при отсутствии текста в плане причина берётся из состояния; счётчик подряд идущих
отказов сохраняется. Добавлен режим плана `retry_exhausted`: после трёх подряд
отказов значок перестаёт бесконечно перезапускать движок и показывает «Ошибка» с
причиной и действием; успех и явное действие человека сбрасывают счётчик, а ручная
проверка состояния его не накручивает.

остаётся в уведомлении даже при длинном перечне каталогов плагинов. Полный текст
причины — в пункте меню «Состояние», в журнале и в отчёте для поддержки.

### S3-3 (D10). Пункт меню «Открыть HR Manager» молча не работал

`infra/windows/engine/Install.psm1:542` (до исправления):

```powershell
$guard = Enter-HrmActionLock -StateDir $StateDir -Action "open"
if (-not $guard.acquired) {
    Write-HrmLog "info" $guard.message
    return
}
```

Причина → симптом: значок, запуская действие, берёт блокировку и **передаёт** её
порождённому процессу движка (`action = "engine"`, pid процесса движка). Движок
внутри `Start-HrmApp` пытался взять блокировку ещё раз — получал отказ «Операция
уже выполняется (engine)», писал его в журнал и молча возвращался. Для
пользователя пункт меню «Открыть HR Manager» (и повторный `install`, и `resume`)
выглядел как «ничего не происходит» — ещё один способ получить вечное
«Запускается».

Исправление: `Enter-HrmActionLock` разрешает повторный вход, если блокировка
принадлежит текущему процессу и запрошенное действие совпадает с записанным либо
записано `"engine"` (то есть блокировка передана значком). Чужие действия
по-прежнему отклоняются.

Тесты: `tests/supervisor.tests.ps1` — «D10: процесс операции входит в свою
блокировку повторно…».

## 4. Кто создаёт и держит лишние `powershell.exe`

Процессы `powershell.exe` в этой системе появляются из четырёх мест:

1. `installer/installer.iss`, секция `[Run]`: значок (`hrm-tray.ps1`, `nowait`) и
   установочный движок (`hr-manager.ps1 -Action install`) — **два процесса на
   каждый запуск мастера**. Это намеренно (значок обязан оставаться отзывчивым),
   но повторный запуск `Setup.exe` добавлял новую пару;
2. `hrm-tray.ps1` → `Start-HrmEngineProcess`: значок порождает скрытый процесс
   движка для `install`/`resume` при каждом входе в Windows (автозапуск через
   `{userstartup}`) и при `ResumePending`;
3. действия меню значка (`open`, `check`, `restart`, `support-bundle`, `stop`) —
   по скрытому процессу на действие;
4. ярлыки меню «Пуск» и рабочего стола (`[Icons]`) — каждый запуск ярлыка это
   отдельный `powershell.exe -File hr-manager.ps1 -Action …`.

**Держало** их отсутствие отмены (D1): процесс движка, зависший в
`Invoke-HrmExternal`, не завершался никогда, поэтому каждый новый вход в Windows и
каждый повторный запуск мастера добавляли ещё один вечно живой `powershell.exe`
плюс его потомков CLI (`docker.exe`, `wsl.exe`). **Плодили** — D2 (значок
порождал второй движок поверх работающего) и D4 (наложенные тики значка добавляли
процессы CLI). До десятков процессов это вырастает за несколько дней работы
машины с автозапуском: 2 процесса на запуск мастера + 1 на вход в Windows +
зависшие потомки, которые никто не убивает.

После исправлений: у каждой внешней команды есть потолок и остановка дерева
(D1), второй цикл движка не начинается (D2), значок не опрашивает Docker при
идущей операции и не накладывает тики (D4), а после трёх подряд отказов значок
перестаёт бесконечно перезапускать движок (D7). Проверить на машине: пункты K1–K3
и K7 чек-листа; в отчёте `Collect-HrmPilotFacts.ps1` для каждого `powershell.exe`
сохраняются `ParentProcessId`, `CreationDate` и `CommandLine` — по ним видно, кто
породил процесс и сколько он жив.

## 5. Оценка `vmmemWSL` ≈ 1.8 ГБ и Docker Desktop

**Вывод: значение ожидаемое, дефектом HR Manager не является.**

- `vmmemWSL` — процесс виртуальной машины WSL2, в которой живут демон Docker,
  контейнеры пилота (Postgres, backend, frontend, worker) и кэш сборки образов;
- WSL2 по умолчанию разрешено занимать до 50% ОЗУ хоста, и Docker Desktop держит
  машину поднятой, пока работает;
- 1–2 ГБ при работающем стеке — типичный диапазон; 1.8 ГБ укладывается в него.
  Тревожным было бы значение, близкое к пределу хоста при простаивающем стеке,
  или непрерывный рост без операций;
- первая сборка образов (`compose build`) поднимает потребление заметно выше: это
  пик, а не утечка.

Что сделано в движке, чтобы память не росла из-за него самого: единственный цикл
(D2), отсутствие параллельных compose-операций и опросов Docker при идущей
операции (D4), остановка зависших процессов деревом (D1), факты в диагностике
(D9: `wsl_memory_mb`, `wsl_memory_processes`, `host_memory_total_mb`,
`host_memory_free_mb`).

Чего движок **не делает никогда**: не удаляет и не пересоздаёт окружение
пользователя — ни контейнеры, ни тома (`pilot_pgdata`, `pilot_backups`), ни
дистрибутивы WSL; не вызывает `wsl --shutdown` и `wsl --unregister`; не создаёт и
не правит `.wslconfig`. Ограничение памяти WSL2 — решение владельца машины; для
пилота это не требуется.

Проверить на машине: пункт K11 чек-листа (сравнить диспетчер задач с
`wsl_memory_mb` в диагностике).
