# Snapshot guard: диагностика и штатный recovery незавершённой установки

## Границы и незакрытая приёмка

Это исправление guard-а, не доказательство живого recovery. Фактические `{app}/release.json`, staged `release.json` проблемного пакета, `installed.json` и журнал мастера находятся на машине владельца. Их значения здесь не приводятся и не подменяются гипотезой. Конкретные SHA/пути/сообщения из этих файлов должны оставаться только в приватном локальном отчёте, не в git, prompts, PR или чате.

В доступном checkout нет упомянутых в отчёте **незакоммиченных локальных правок Bootstrap.psm1 / Secrets.psm1** для exchange recovery. Они не реконструировались по догадке и не заменялись старыми версиями из ветки ревьюера. Для полной сборки оператор должен предоставить/зафиксировать именно кодовый diff этих правок (без StateDir, env, токенов и PII), включая их тесты. Данный патч эти два модуля, DB-password sync, Wait-HrmReady, Compose-проект, лицензионные ворота и данные не меняет.

До полной проверки на Windows PowerShell 5.1, pwsh, сборки из clean commit и живой приёмки статус **draft / NO-GO**. GitHub-публикация, публикация сборок, merge и release в этом этапе не требуются и не выполняются.

## 1. Read-only диагностика старого отказа

Указать **реальный каталог из мастера**, фактический StateDir и `release.json` именно того staging, из которого собран отказавший Setup. Не заменять staging новым checkout и не считать HEAD идентификатором dirty bytes.

Из checkout с патчем запустить `infra/windows/tools/Compare-HrmSnapshotInputs.ps1`, передав:

```powershell
# Переменные задаёт оператор локально; значения не публиковать.
& .\infra\windows\tools\Compare-HrmSnapshotInputs.ps1 `
    -InstallDir $actualAppDir -StateDir $actualStateDir `
    -PackageReleaseFile $actualPackageReleaseFile `
    -PrivateReportFile $privateComparisonFile
```

Каталог отчёта должен быть заранее создан с ограниченными ACL, вне InstallDir, StateDir и checkout. Скрипт отказывается перезаписывать файл, читает только три файла метаданных и не вызывает Docker, snapshot/adoption, SQL или генерацию секретов. В консоль выводятся только предикаты, без SHA/путей; полный whitelist-проекционный отчёт остаётся локальным.

При уже подтверждённом в локальном журнале отказе `files_replaced` старого helper:

- `file_equals_package=true` соответствует первой ветке;
- иначе непустые `file_sha != record_sha` — вторая ветка;
- `record_directory_equals_target=false` указывает на смешение каталогов;
- существующий пригодный/принимаемый снимок имеет приоритет перед этими предикатами: скрипт не вызывает изменяющую состояние adoption и не выдаёт предикаты за полное решение guard-а.

### Что предсказывает сравнение для пересборки из нового коммита

Setup, собранный из нового чистого коммита, имеет **другой** `release_sha`, чем установленный 0.15.0, поэтому ветки same-SHA (А — `build_digest`, Б — незавершённый повтор) на 8081 не задействуются. Guard идёт обычной веткой:

- `record_directory_equals_target=true` и `file_equals_record=true` → снимок копируется и проверяется (`saved`/`reused`), обновление продолжается;
- `record_directory_equals_target=false` → `install_dir_mismatch` с обоими каталогами; выбрать каталог из записи, запись не переписывать;
- `file_equals_record=false` при непустых SHA обоих файлов → по-прежнему отказ `files_replaced` (`guard_branch=record_identity_mismatch`), теперь с конкретными полями; простая пересборка его **не** снимает — нужны соответствующие записи файлы или проверенный снимок.

Это прогноз по коду, а не результат: подтверждается только самим приватным сравнением и затем живым запуском.

Сверить с двумя строками журнала мастера (`HRM: snapshot decision`, `HRM: снимок предыдущей версии`) **локально**. Если исходное staging отсутствует, значение пакета неизвестно — гипотезу не объявлять доказанной. Не отправлять отчёт или сырые строки журнала в репозиторий/чат.

## 2. Исправленная цепочка диагностики

Промежуточный helper-файл — UTF-8 BOM `key=value`, а не JSON. `setup-snapshot.json` создаёт Inno отдельно. Теперь поля проходят всю цепочку:

- `file_sha`, `new_release_sha`, `record_sha`;
- `record_install_dir`, `target_install_dir`, `record_pilot_created`;
- `message`, `guard_branch`, `new_build_digest`;
- прежние status/reason/release_sha/files/digest сохраняются в helper transport.

Все решения helper проходят единый writer. Переводы строк в значениях нейтрализуются, сообщения проходят Redact-HrmText. Inno экранирует JSON, сохраняет UTF-8 и пишет различающие поля в свой локальный журнал. CLI печатает конкретное сообщение, не только общий Format-HrmSnapshotReason. Inno выбирает сообщение по **reason**, а не по status (`failed` не равно `files_replaced`).

`guard_branch` различает наличие идентичности пакета, несовпадение с записью, другой каталог и несовпадение content digest. Для отсутствующего/небулева pilot flag применяется `unknown`, не ложное разрешение recovery. Сообщения больше не рекомендуют бессмысленный повтор Setup без изменения состояния.

Пути могут содержать имя пользователя; диагностические файлы — **приватные**, даже если в них нет паролей.

## 3. Идентичность и recovery: варианты А + Б

### А. Content digest кодового дерева

Сборка добавляет в `release.json` `build_digest` и `build_digest_schema=hrm-code-tree-1` после staging, встраивания публичного ключа и trust store, до ISCC. Та же функция вычисляет digest установленного кода.

Канонические строки: относительный путь с `/`, TAB, размер в invariant decimal, TAB, SHA256 файла; ordinal sorting, UTF-8, LF, завершающий LF. Включаются все файлы `infra/`, `backend/`, `frontend/`, в том числе внедрённые build-time файлы. Корневой `release.json` исключён: он содержит сам digest и изменчивые timestamps/описание. Это **идентичность кодового дерева**, не SHA256 всего EXE и не проверка подписи пакета.

При одинаковом release_sha другая проверенная кодовая идентичность позволяет сохранить текущие файлы как прежнюю версию. Если у установленного release.json уже есть build_digest, он обязан совпасть с реально посчитанным содержимым. Повреждённые/изменённые файлы со старой меткой дают `build_digest_mismatch`, а не разрешение.

Без build_digest у legacy-пакета сохраняется прежний строгий SHA-отказ, кроме узкого случая Б. Отсутствие release_sha/принадлежности записи не объявляется доказательством другого build.

### Б. Незавершённая установка

Повтор того же пакета допустим только если одновременно:

- `pilot_created` — явное булево **false**, не отсутствующее значение и не строка;
- `record.install_dir` задан и нормализованно совпадает с целевым каталогом;
- непустые record_sha и file_sha совпадают;
- нет обнаруженного противоречия build_digest;
- выполнено настоящее копирование и проверка снимка.

Один лишь `setup-run.json`, строковый/отсутствующий флаг или чужая запись не разрешают исключение. Завершённая установка с идентичным пакетом без прежнего пригодного снимка по-прежнему получает `files_replaced`.

Результат `incomplete_retry` явно означает: сохранены **существующие байты незавершённой установки**, а не доказана её работоспособность. `verified` относится к целостности копии, не к HTTP-ready/успеху установки.

### Привязка каталога и проверка копии

`install_dir_mismatch` проверяется до reuse/adoption и до копирования. Нельзя брать код из одного каталога и идентичность из записи другой установки. Следующий шаг — выбрать каталог из записи/правильный StateDir, а не переписать installed.json ради успеха.

Копия сравнивается с манифестом **источника до копирования**; исходный манифест перечитывается после копирования. Самопроверка копии по манифесту, вычисленному только из неё самой, больше не является единственным доказательством. Идентичность release.json проверяется до/после копирования; для content-aware решения копия также должна сохранить кодовый digest, проверенный guard-ом. Неполная/изменившаяся копия не получает verified. Секреты и Docker volumes не входят в snapshot и не меняются guard-ом.

## 4. Тесты и границы локального результата

Добавлен `snapshot-recovery.tests.ps1`: **21 новый кейс** (20 объявлений, одно — цикл на два значения). Полный счёт runner-а — **339 = 318 + 21**: 318 — аннотация CI `HRM engine tests` для базового коммита 97df390; 339 — аннотация CI для коммита 4ebda29 (`ВСЕ ТЕСТЫ ПРОЙДЕНЫ (339)`, Windows PowerShell 5.1, наборы до snapshot-recovery включительно). Существующие suites, включая отказы iteration14/iteration15, не удалены и не ослаблены. Новый процессный тест запускает helper тем же PowerShell host, что и новый suite.

CI-джоба `Windows engine tests + installer smoke` запускает runner **только в Windows PowerShell 5.1** и публикует счётчик аннотацией; там же ISCC компилирует `installer.iss`, а silent smoke выполняет установку и обновление собранным Setup. В том же CI-прогоне ISCC 6.7.3 скомпилировал изменённый `installer.iss`, а silent smoke прошёл установку и обновление (`setup-snapshot.json`: status=verified, reason=saved), то есть новый JSON с полями guard-а разбирается. Отдельная джоба `Windows engine tests (PowerShell 7 / pwsh)` запускает тот же runner в pwsh; аннотации runner-а (успех — `host=`, провалы — `passed`/`host` в заголовке списка) называют хост (`Desktop 5.1…` или `Core 7…`), поэтому счёт одного хоста не выдаётся за другой. CI собирает merge-коммит PR, а не точный коммит ветки; ограниченный режим раннера (без Linux-движка Docker) не покрывает сборку образов, стек, первый запуск и owner claim — это не замена живой приёмке на установке пилота.

Новые кейсы: канонический digest/метаданные, изменение содержимого/имени, один commit с другими байтами, идентичная завершённая установка, незавершённый и legacy retry, повторное reuse, missing/string pilot flag, отсутствие/расхождение/нормализация каталога, полный диагностический transport, конкретный CLI и процессный exit, чужой record SHA, повреждённый digest/копия, маскирование зарегистрированных секретов и защита transport от CR/LF, проводка Inno, выбор диалога `files_replaced` по `reason` без строки «Причина: failed / files_replaced» (runtime: helper пишет status=failed + reason=files_replaced; статика: исключающая цепочка сообщений в PreservePreviousSnapshot, на исходном installer.iss тест красный), чистота build и порядок content hashing.

`test_snapshot_contract.py` — **только source-wiring контракты**, не интерпретатор PowerShell. Локально: 8 failing на исходном экспорте → 8 passing после исправления. Дополнительно — структурный lint и синтаксический tree-sitter parse изменённых PowerShell-файлов. Это **не** доказательство прохождения 339 runtime-кейсов.

На Windows обязательно отдельно:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File infra\windows\tests\run-tests.ps1
# Проверить exit 0 и полный счётчик, сохранить вывод только приватно.
pwsh -NoProfile -File infra\windows\tests\run-tests.ps1
# То же, не выдавать прогон одного host за два.
```

Также воспроизвести новые поведенческие регрессы на baseline в отдельной приватной копии. Локальный red/green source-контрактов не заменяет этот шаг. PowerShell 5.1, pwsh, ISCC и Docker Desktop в Linux sandbox не доступны; Windows runtime, сборка Setup и живые сценарии там не выполнены.

## 5. Сборка и живая приёмка — только после фиксации исходников

1. Зафиксировать реальные локальные Bootstrap/Secrets-правки и этот патч. Не переносить StateDir/evidence в git. Правки извлекаются из того приватного checkout, где они лежат незакоммиченными, **как код** (а не восстанавливаются по памяти):

   ```powershell
   # В приватном checkout с незакоммиченными правками; $privateDir — каталог с ограниченными ACL вне checkout/StateDir.
   git status --short
   git diff --stat -- infra/windows/engine/Bootstrap.psm1 infra/windows/engine/Secrets.psm1 infra/windows/tests
   # Новые (неотслеживаемые) тест-файлы иначе не попадут в diff:
   git add -N -- <новые тест-файлы>
   # Файл пишет сам git: конвейер PowerShell превратил бы вывод в строки и испортил байты патча.
   git diff --binary ("--output=" + (Join-Path $privateDir "exchange-recovery.patch")) -- `
       infra/windows/engine/Bootstrap.psm1 infra/windows/engine/Secrets.psm1 <их тест-файлы>
   # Просмотреть патч: только код и тесты; нет токенов, паролей, значений env, путей StateDir, PII.
   # В чистом checkout ветки сессии (актуальный head):
   git apply --3way --check (Join-Path $privateDir "exchange-recovery.patch")
   git apply --3way (Join-Path $privateDir "exchange-recovery.patch")
   git add -- <изменённые файлы>; git commit -m "<что исправляет exchange recovery>"
   git push origin arena/3cadc6a9-hr-manager   # обычный push, без force
   ```

   Патч по содержимому применим и после переписывания истории: неизменённые файлы сохраняют те же blob. Если `--check` не проходит, разрешить конфликт вручную, не подменяя правки версиями из чужих веток. `build.ps1` теперь отказывает при dirty/untracked source, несоответствии HRM_RELEASE_SHA текущему commit, изменении HEAD/дерева во время staging. Простой выбор старого HEAD для маркировки dirty EXE больше не допускается.
2. Выполнить оба полных Windows-прогона. Из чистого checkout запустить `installer/build.ps1 -Version 0.15.0` с существующим штатным публичным ключом. Лицензионные требования/проверки подписей не ослаблять. Собранный EXE, его SHA256 и метаданные хранить только локально, без публикации.
3. На существующей установке перед Setup зафиксировать приватно идентичность/данные обоих томов и контрольные файлы состояния. Стандартный Setup на 8081 должен сначала получить verified/reused snapshot, затем пройти recovery → owner claim → установка пароля → вход. Проверить helper/Setup/engine exit codes, локальные setup-snapshot.json/setup-run.json/supervisor.json, реальную frontend-доступность, сохранность томов и идемпотентный повтор.
4. **Разделить проверки secrets.json:** вокруг snapshot-guard он должен быть побайтово неизменен. В полном exchange recovery ожидаемое изменение/очистка exchange token уже меняет байты файла — одновременно требовать byte-identical всего файла нельзя. За этим участком отдельно подтвердить, что менялось только разрешённое поле exchange token, а пароль БД, signing/backup keys и другие секреты не менялись. Не обходить owner claim ручной установкой пароля.
5. Genuinely clean install проводить с новым StateDir **в отдельной чистой Windows VM/изолированном Docker Engine**. Текущий движок явно задаёт фиксированный Compose project; переменная COMPOSE_PROJECT_NAME его не переопределяет. Новый StateDir на том же Engine **не изолирует** БД. Не менять Compose ради этой приёмки и не удалять существующие тома. Проверить отсутствие ресурсов пилота в тестовом Engine до установки; выполнять тот же штатный Setup и полный первый запуск, а не ручной compose up.

При любом отказе — честный локальный результат и причина, без подделки verified/installed.json/снимка. Ни guard, ни тома, ни лицензионные ворота не обходятся. До закрытия недостающих Windows/live-пунктов — **draft / NO-GO**.
