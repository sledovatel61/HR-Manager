# AGENTS.md — правила работы над HR Manager

Этот файл является главным рабочим документом для любого AI-агента. Если отдельная задача ему противоречит, приоритет имеют безопасность, этот файл и `PRODUCT_SPEC.md`.

## Продукт

HR Manager — многопользовательская внутренняя система подбора персонала. Это не локальная программа с общей папкой, а клиент-серверное приложение с единой PostgreSQL-базой.

## Целевой стек

Если в репозитории ещё нет обоснованного решения, использовать:

- Backend: Python 3.12+, FastAPI, SQLAlchemy 2, Alembic, Pydantic v2;
- Frontend: React, TypeScript, Vite, современная компонентная UI-библиотека;
- Database: PostgreSQL 16+;
- Background jobs: отдельный worker/cron-слой, не блокировать API;
- Tests: pytest для backend, Vitest/Playwright для frontend;
- Local run: Docker Compose;
- Deployment: Docker images, reverse proxy с HTTPS.

Не добавлять новые библиотеки без необходимости и не возвращать SQLite как production-БД.

## Правила данных и доступа

1. У каждого кандидата есть `owner_user_id` — ответственный HR.
2. Обычный HR по умолчанию видит свою рабочую очередь.
3. Руководитель и разрешённые роли могут видеть общий список и фильтровать по ответственному.
4. Передача кандидата — отдельная операция с причиной, инициатором, старым и новым ответственным и записью в audit log.
5. Удаление кандидатов — soft delete; физическое удаление запрещено обычному пользователю.
6. Все изменения статуса, владельца, персональных данных, экспорта, backup и прав доступа аудируются.
7. Сервер проверяет права на каждый запрос; скрытие кнопки во frontend не является защитой.

## Обязательная безопасность

- обязательный пароль при создании пользователя;
- хранить только Argon2id/bcrypt hash с безопасными параметрами;
- HTTPS в production;
- короткоживущие access-сессии и безопасное обновление сессии;
- защита от brute force, rate limiting и блокировка после серии неудачных входов;
- CSRF/XSS/SQL injection защита средствами framework и валидацией;
- минимальные права БД;
- маскирование персональных данных в логах;
- backup шифровать и регулярно проверять восстановлением;
- секреты только через environment/secret storage, не в git;
- не коммитить реальные персональные данные, `.env`, backup и дампы.

## Правила разработки агентом

- Сначала изучить существующую структуру и выполнить тесты.
- Не переписывать чужие изменения и не делать массовых косметических правок.
- Перед изменением схемы БД создать миграцию.
- Для каждой бизнес-функции добавить тесты: happy path, права доступа и ошибочный сценарий.
- API-контракты документировать и не ломать молча.
- Не оставлять заглушки, `pass`, TODO или фиктивные успешные ответы в принятом этапе.
- Не считать задачу выполненной без команд проверки и краткого отчёта о результатах.
- Каждый этап должен быть самостоятельным, запускаемым и понятным другому агенту.
- Перед началом новой фазы сначала проверить актуальный `origin/main` и точный SHA.
- После завершения разработки не выполнять merge в `main`: отправить свою ветку и открыть PR.
- Следующий агент обязан прочитать handoff и отчёт предыдущей фазы, а не восстанавливать контекст по истории коммитов.
- Для коммуникаций с кандидатами считать `accepted` только техническим принятием провайдером: это не равно доставке, открытию или прочтению.
- Запрещено передавать получателя, текст сообщения, email, Telegram ID или область доступа через клиентский запрос, если их можно определить на сервере.
- Любая отправка кандидатам должна повторно проверять согласие, права, актуальность объекта и возможность отмены непосредственно перед отправкой.

## Definition of Done

Этап готов, если:

1. Реализованы только заявленные в этапе функции.
2. Есть миграции и тесты.
3. Есть инструкция запуска.
4. Проверены права минимум для обычного HR и руководителя.
5. Нет секретов и персональных данных в репозитории.
6. Все доступные проверки проходят.
7. В отчёте указаны изменённые файлы, команды и ограничения.
